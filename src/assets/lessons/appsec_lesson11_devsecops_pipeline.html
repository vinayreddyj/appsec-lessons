DevSecOps
Pipeline

DevSecOps is the practice of embedding security controls directly into the software delivery pipeline so that security becomes automatic, continuous, and fast rather than a manual gate at the end. This lesson builds a complete DevSecOps pipeline from first principles: what it is and why it matters, each security gate in the CI/CD pipeline, how to tune gates to minimise friction, how to measure programme maturity, and a complete GitHub Actions implementation you can drop into any project.

🟢 Beginner — What DevSecOps Is
From "security at the end" to "security everywhere"
Traditional security is a tollgate at the end of a release. DevSecOps is a distribution of small security checks throughout every stage of the delivery pipeline. The cost difference is enormous.
⚠️
The cost of late detection: A vulnerability found by a developer in their IDE costs 5 minutes to fix. The same vulnerability found during a security review costs 1 hour (context switch, ticket, review, fix, re-review). Found in production after a breach: $4.45M average cost (IBM 2023). DevSecOps is fundamentally about moving detection as early as possible. The earlier you find it, the cheaper it is.
Dev → DevOps → DevSecOps — the evolution
Understanding where DevSecOps came from and why the previous models failed
▼
EraModelSecurity approachProblem
Pre-2010Waterfall DevSecurity team does a pentest before release. One big audit per year.Releases are 6-12 months apart. Pentest finds 50 issues 2 weeks before go-live. Ship anyway or delay. Dev team has no security context.
2010–2018DevOpsDev and Ops merged into one pipeline. Security still a separate "throw it over the wall" function.Teams deploy 50x/day. Security can't review each deployment. Security becomes a bottleneck or gets bypassed entirely.
2018–nowDevSecOpsSecurity controls embedded in the pipeline. Every commit triggers automated security checks. Security team writes policy-as-code, not manual reviews.Still evolving. Challenge: tuning automated tools to minimise false positives and developer friction.

The shift-left principle

A CI/CD pipeline runs from left (code commit) to right (production deployment). "Shift left" means moving security checks earlier in that pipeline — closer to the moment the code is written. Each step left dramatically reduces the cost of fixing a finding: pre-commit hooks catch issues before they're even committed to the repository. SAST in CI catches them before peer review. DAST in staging catches them before release. Production monitoring catches them after release — when they're most expensive.

1
Pre-commit hooks — catch issues before they hit the repo
Fastest feedback • Developer's machine
▼

Pre-commit hooks run on the developer's local machine before every git commit. They are the fastest possible feedback loop — the developer finds the issue before the code ever leaves their laptop. The pre-commit framework (pre-commit.com) manages hooks written in any language and ensures the same checks run on every developer's machine consistently.

What to put in pre-commit hooks
HookWhat it catchesSpeedWhy here
Secrets scanning (detect-secrets, gitleaks)AWS keys, API tokens, passwords in codeFast (<2s)Secrets committed to git are impossible to fully remove — git history is permanent. Catch before commit.
Basic SAST (Semgrep fast rules)Obvious SQLi, hardcoded passwords, dangerous function callsFast (<5s on changed files only)Immediate feedback before context switch. Developer can fix in the same coding session.
Linting / formattingCode quality, style violationsVery fastKeeps code review focused on logic, not style.
Large file checkAccidentally committed binaries, datasetsInstantPrevents repository bloat and potential data leaks.
.pre-commit-config.yaml
# Install: pip install pre-commit && pre-commit install
repos:
  # Secrets scanning — fastest, most critical gate
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks

  # Detect-secrets (alternative with allowlist support)
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.4.0
    hooks:
      - id: detect-secrets
        args: ['--baseline', '.secrets.baseline']

  # Semgrep — run only fast rules on changed files
  - repo: https://github.com/returntocorp/semgrep
    rev: v1.45.0
    hooks:
      - id: semgrep
        args: [
          '--config=p/python',         # Python security rules
          '--severity=ERROR',          # only block on errors, not warnings
          '--quiet',                   # minimal output (developer-friendly)
        ]

  # Built-in pre-commit hooks
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: check-added-large-files    # blocks files > 500KB
        args: ['--maxkb=500']
      - id: check-merge-conflict       # blocks unresolved merge conflicts
      - id: no-commit-to-branch        # prevents committing directly to main
        args: ['--branch', 'main']
💡
Developer experience tip: Pre-commit hooks that take more than 5 seconds will be bypassed with git commit --no-verify. Keep pre-commit hooks fast by only scanning changed files (--diff mode in Semgrep) and only running the fastest rules. Save comprehensive scans for CI.
2
SAST — Static Application Security Testing on every PR
Semgrep • CodeQL • Bandit
▼

SAST analyses source code without executing it, looking for patterns that indicate security vulnerabilities. In CI it runs on every PR, scanning the full codebase rather than just changed files. Unlike pre-commit hooks, CI SAST runs comprehensive rulesets and performs inter-procedural analysis (tracking data flow across functions).

Choosing the right SAST tool
ToolLanguagesStrengthsWhen to use
SemgrepPython, JS, Go, Java, Ruby, C, PHP, 30+Fast, customisable rules, excellent developer UX, free tier generousFirst choice for most teams. Write custom rules for your codebase.
CodeQLPython, JS, Java, C/C++, Go, Ruby, SwiftDeep dataflow analysis, finds complex multi-hop vulnerabilities, GitHub nativeGitHub-hosted repos, need deep analysis, complement to Semgrep
BanditPython onlyLightweight, fast, Python-specific, no setupPython projects wanting fast baseline scanning
SonarQube25+ languagesCode quality + security, rich dashboards, self-hostedEnterprise environments needing code quality metrics alongside security
GitHub Actions — SAST gate
# .github/workflows/sast.yml
name: SAST

on:
  pull_request: { branches: [main] }
  push: { branches: [main] }

jobs:
  semgrep:
    runs-on: ubuntu-latest
    container: { image: returntocorp/semgrep }
    steps:
      - uses: actions/checkout@v4

      - name: Semgrep SAST scan
        run: |
          semgrep ci \
            --config=p/python \
            --config=p/django \
            --config=p/secrets \
            --config=.semgrep/custom-rules.yml \   # your org's custom rules
            --severity=ERROR \
            --json > semgrep-results.json
        env:
          SEMGREP_APP_TOKEN: ${{ secrets.SEMGREP_APP_TOKEN }}

      - name: Enforce gate — fail on new findings
        run: |
          NEW=$(cat semgrep-results.json | \
            python3 -c "import json,sys; d=json.load(sys.stdin);
            new=[r for r in d['results'] if not r.get('is_ignored')];
            print(len(new))")
          echo "New findings: $NEW"
          [ "$NEW" -eq "0" ] || { echo "SAST gate FAILED"; exit 1; }

      - name: Upload SARIF to GitHub Security tab
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with: { sarif_file: semgrep-results.sarif }

  codeql:
    runs-on: ubuntu-latest
    permissions: { security-events: write, contents: read }
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with: { languages: python }
      - uses: github/codeql-action/autobuild@v3
      - uses: github/codeql-action/analyze@v3
        with: { category: /language:python }
Writing custom Semgrep rules for your codebase
.semgrep/custom-rules.yml
rules:
  # Rule 1: Detect our internal audit logging bypass
  - id: missing-audit-log
    patterns:
      - pattern: |
          def $FUNC(request, ...):
            ...
            return ...
      - pattern-not: |
          def $FUNC(request, ...):
            ...
            audit_log(...)
            ...
    message: >
      API handler $FUNC does not call audit_log().
      All handlers that modify data must log the action.
    languages: [python]
    severity: WARNING
    paths: { include: ["*/views.py", "*/api/*.py"] }

  # Rule 2: Detect our unsafe serialiser pattern
  - id: unsafe-serializer-all-fields
    pattern: |
      class $SERIALIZER(ModelSerializer):
        class Meta:
          fields = "__all__"
    message: >
      $SERIALIZER uses fields="__all__" which exposes all model fields.
      Use an explicit field list to prevent data exposure.
    languages: [python]
    severity: ERROR
3
Secrets scanning — the highest ROI gate in DevSecOps
TruffleHog • Gitleaks • GitHub Secret Scanning
▼

Hardcoded secrets in code are among the most common and most damaging security failures. A developer commits an AWS key in a test file, it gets pushed to GitHub, a secret-scanning bot finds it within seconds, and cloud resources are compromised within minutes. In 2023 GitGuardian found that 10 million secrets were exposed on GitHub. The fix — never commit secrets — costs nothing. Detecting leaks is fast and cheap. The impact of missing them is catastrophic.

What to scan for
.github/workflows/secrets-scan.yml
name: Secrets Scan

on:
  pull_request: {}
  push: { branches: [main] }
  schedule:
    - cron: '0 2 * * *'   # daily scan of full git history

jobs:
  trufflehog:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }   # fetch ALL history for full scan

      - name: TruffleHog scan (full git history)
        uses: trufflesecurity/trufflehog@main
        with:
          path: ./
          base: ${{ github.event.repository.default_branch }}
          head: HEAD
          extra_args: >-
            --only-verified
            --json
            --results=verified,unknown

      # Also: enable GitHub Secret Scanning (free for public repos)
      # Settings > Security > Secret scanning > Enable
      # Automatically notifies when AWS keys, GCP creds, etc. are detected
Responding to a detected secret
# Emergency response: secret found in git history

# Step 1: IMMEDIATELY revoke the credential (before any cleanup)
# AWS: IAM > Users > Access keys > Deactivate
# GitHub: Settings > Developer settings > Personal access tokens > Revoke
# The secret is already out. Revoking is the only thing that matters first.

# Step 2: Audit access logs for the compromised credential
# AWS: CloudTrail > Event history > filter by access key ID
# Determine if the credential was used by anyone other than the owner

# Step 3: Remove from git history (after revoking)
$ git filter-branch --force --index-filter \
    "git rm --cached --ignore-unmatch config/secrets.py" \
    --prune-empty --tag-name-filter cat -- --all
$ git push origin --force --all

# Better: use BFG Repo Cleaner (faster than filter-branch)
$ java -jar bfg.jar --delete-files secrets.py
$ git reflog expire --expire=now --all
$ git gc --prune=now --aggressive
$ git push --force

# Step 4: Add the secret pattern to your .secrets.baseline
# so it's recognised as a known false-positive if the cleaned version stays

# Prevention: store secrets in environment variables or secrets managers
# Never hardcode: AWS_SECRET_KEY, DATABASE_URL, API_KEY, PRIVATE_KEY
Highest ROI gateScan full git history, not just HEADRevoke first, clean second

SCA — dependency vulnerability scanning
Snyk • pip-audit • npm audit • Dependabot
▼

SCA checks every package in your dependency tree against CVE databases. Covered in depth in Lesson 6. In the DevSecOps pipeline context: SCA must run on PRs AND on a daily schedule. The PR scan catches new vulnerable packages being introduced. The daily scheduled scan catches newly published CVEs in your existing dependencies.

GitHub Actions — SCA gate
jobs:
  sca:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      # pip-audit: Python dependencies
      - name: pip-audit
        run: |
          pip install pip-audit
          pip-audit -r requirements.txt \
            --format json \
            --output pip-audit.json \
            --ignore-vuln PYSEC-2022-237    # known false positive, documented
          python3 -c "
          import json, sys
          data = json.load(open('pip-audit.json'))
          vulns = [v for d in data.get('dependencies',[])
                   for v in d.get('vulns',[]) if v.get('fix_versions')]
          print(f'Fixable vulnerabilities: {len(vulns)}')
          sys.exit(1 if vulns else 0)
          "

      # npm audit: Node.js dependencies
      - name: npm audit
        run: |
          npm ci
          npm audit --audit-level=high --json > npm-audit.json || true
          HIGH=$(cat npm-audit.json | jq \
            '.metadata.vulnerabilities.high + .metadata.vulnerabilities.critical')
          [ "$HIGH" -eq "0" ] || { echo "npm HIGH/CRITICAL vulns: $HIGH"; exit 1; }

IaC scanning — infrastructure security before it deploys
Checkov • tfsec • Trivy • KICS
▼

Infrastructure as Code (Terraform, CloudFormation, Kubernetes YAML, Dockerfile) defines your entire cloud environment. Misconfigurations in IaC are responsible for the majority of cloud breaches. IaC scanning runs in CI before any infrastructure is provisioned, catching misconfigs like open S3 buckets, unrestricted security groups, and missing encryption at rest before they reach the cloud.

  iac-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Checkov: Terraform + Kubernetes + Dockerfile + CloudFormation
      - name: Checkov IaC scan
        uses: bridgecrewio/checkov-action@master
        with:
          directory: .
          framework: terraform,kubernetes,dockerfile
          output_format: sarif
          output_file_path: checkov.sarif
          soft_fail: false
          check: >-
            CKV_AWS_20,CKV_AWS_24,CKV_AWS_17,
            CKV_DOCKER_4,CKV_K8S_6,CKV_K8S_11

      # Trivy: Dockerfile + K8s manifests + Terraform

        uses: aquasecurity/trivy-action@master
        with:
          scan-type: config
          scan-ref: .
          severity: HIGH,CRITICAL
          exit-code: 1
          format: sarif
          output: trivy-iac.sarif

      - name: Upload SARIF results
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with: { sarif_file: checkov.sarif }
6
Container image scanning — every layer before it ships
Trivy • Grype • Docker Scout
▼

Container images contain: your application code, all its dependencies, the OS base image, and system packages. Any of these layers can contain vulnerabilities. Container scanning checks every layer against CVE databases. It runs after the image is built but before it is pushed to a registry or deployed.

GitHub Actions — container scan
  container-scan:
    runs-on: ubuntu-latest
    needs: [test]   # only scan after tests pass
    steps:
      - uses: actions/checkout@v4

      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .

      # Trivy — scans OS packages, app dependencies, secrets in image
      - name: Trivy container scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: myapp:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: 1
          ignore-unfixed: true        # skip CVEs with no fix yet
          format: sarif
          output: trivy-image.sarif

      # Also scan the Dockerfile for best practice violations
      - name: Hadolint Dockerfile lint
        uses: hadolint/hadolint-action@v3.1.0
        with:
          dockerfile: Dockerfile
          failure-threshold: warning

      - name: Push to registry only if clean
        if: success()
        run: |
          docker tag myapp:${{ github.sha }} registry.io/myapp:${{ github.sha }}
          docker push registry.io/myapp:${{ github.sha }}
Secure Dockerfile best practices
Dockerfile
# BAD: large base image, root user, no pinned versions
FROM python:latest
COPY . /app
RUN pip install -r requirements.txt
CMD ["python", "app.py"]

# GOOD: minimal base, pinned versions, non-root user, multi-stage
FROM python:3.12-slim-bookworm AS builder  # pinned, minimal
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.12-slim-bookworm AS runtime
WORKDIR /app
COPY --from=builder /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
COPY --from=builder /app /app
RUN adduser --disabled-password --gecos "" appuser   # non-root user
USER appuser
EXPOSE 8000
CMD ["gunicorn", "app.wsgi:application"]
7
DAST — runtime security testing in staging
OWASP ZAP • Nuclei • Burp Suite Enterprise
▼

DAST attacks a running application from the outside, finding vulnerabilities that static analysis cannot. DAST runs in a staging environment after deployment but before production release. It finds: authentication bypasses, injection vulnerabilities that require a live database, misconfigured security headers, and business logic flaws in running API flows.

GitHub Actions — DAST gate (staging)
  dast:
    runs-on: ubuntu-latest
    environment: staging
    needs: [deploy-staging]
    steps:
      - uses: actions/checkout@v4

      # Get auth token for authenticated scanning
      - name: Get auth token
        id: auth
        run: |
          TOKEN=$(curl -s -X POST \
            https://staging.api.myapp.com/api/auth/login \
            -H "Content-Type: application/json" \
            -d '{"email":"dast@test.com","password":"${{ secrets.DAST_PASSWORD }}"}' \
            | jq -r '.token')
          echo "token=$TOKEN" >> $GITHUB_OUTPUT

      # ZAP API scan against OpenAPI spec
      - name: ZAP API scan
        run: |
          docker run --rm \
            ghcr.io/zaproxy/zaproxy:stable zap-api-scan.py \
            -t https://staging.api.myapp.com/openapi.json \
            -f openapi \
            -r zap-report.html \
            -J zap-report.json \
            -H "Authorization: Bearer ${{ steps.auth.outputs.token }}" \
            -z "-config scanner.strength=HIGH"

      # Parse ZAP results and enforce gate
      - name: Enforce DAST gate
        run: |
          HIGH=$(cat zap-report.json | jq \
            '[.site[].alerts[] | select(.riskdesc | startswith("High") or startswith("Critical"))] | length')
          echo "High/Critical findings: $HIGH"
          [ "$HIGH" -eq "0" ] || { echo "DAST gate FAILED: $HIGH issues"; exit 1; }

      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: dast-report, path: zap-report.html }

.github/workflows/devsecops.yml
name: DevSecOps Pipeline

on:
  pull_request: { branches: [main] }
  push: { branches: [main] }

# ═══ PERMISSIONS ═══════════════════════════════════════════════
permissions:
  contents: read
  security-events: write    # upload SARIF to GitHub Security tab
  pull-requests: write      # comment findings on PRs

jobs:

# ─────────────────────────────────────────────────────────────────
# GATE 1+3: Secrets scanning (fastest — runs first, blocks everything)
# ─────────────────────────────────────────────────────────────────
  secrets-scan:
    name: Secrets Scan
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - name: TruffleHog
        uses: trufflesecurity/trufflehog@main
        with: { path: ./, base: main, head: HEAD, extra_args: --only-verified }

# ─────────────────────────────────────────────────────────────────
# GATE 2: SAST
# ─────────────────────────────────────────────────────────────────
  sast:
    name: SAST (Semgrep + CodeQL)
    runs-on: ubuntu-latest
    needs: [secrets-scan]
    steps:
      - uses: actions/checkout@v4
      - name: Semgrep
        uses: returntocorp/semgrep-action@v1
        with:
          config: >-
            p/python
            p/django
            p/owasp-top-ten
            .semgrep/custom-rules.yml
          generateSarif: "1"
      - uses: github/codeql-action/upload-sarif@v3
        if: always()
        with: { sarif_file: semgrep.sarif }

      - uses: github/codeql-action/init@v3
        with: { languages: python }
      - uses: github/codeql-action/autobuild@v3
      - uses: github/codeql-action/analyze@v3

# ─────────────────────────────────────────────────────────────────
# GATE 4: SCA
# ─────────────────────────────────────────────────────────────────
  sca:
    name: SCA (Dependency Scanning)
    runs-on: ubuntu-latest
    needs: [secrets-scan]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }
      - run: pip install pip-audit
      - name: pip-audit
        run: |
          pip-audit -r requirements.txt --format json -o pip-audit.json
          python3 -c "
          import json,sys
          d=json.load(open('pip-audit.json'))
          v=[x for dep in d.get('dependencies',[]) for x in dep.get('vulns',[]) if x.get('fix_versions')]
          sys.exit(1 if v else 0)"
      - name: Snyk
        uses: snyk/actions/python@master
        env: { SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }} }
        with: { args: --severity-threshold=high --fail-on=upgradable }

# ─────────────────────────────────────────────────────────────────
# GATE 5: IaC scanning
# ─────────────────────────────────────────────────────────────────
  iac-scan:
    name: IaC Scan (Checkov + Trivy)
    runs-on: ubuntu-latest
    needs: [secrets-scan]
    steps:
      - uses: actions/checkout@v4
      - name: Checkov
        uses: bridgecrewio/checkov-action@master
        with: { directory: ., framework: terraform,kubernetes,dockerfile, soft_fail: false }
      - name: Trivy config
        uses: aquasecurity/trivy-action@master
        with: { scan-type: config, severity: HIGH,CRITICAL, exit-code: 1 }

# ─────────────────────────────────────────────────────────────────
# Build + GATE 6: Container scan (only on merge to main)
# ─────────────────────────────────────────────────────────────────
  build-and-scan:
    name: Build & Container Scan
    runs-on: ubuntu-latest
    needs: [sast, sca, iac-scan]
    if: github.ref == 'refs/heads/main'
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        id: build
        run: docker build -t myapp:${{ github.sha }} .
      - name: Trivy container scan

🔴 Advanced — Tuning & Reducing Friction
Making security gates developers actually respect
A security gate that produces constant false positives will be disabled or bypassed. Tuning is the most important operational skill in DevSecOps. Here is the systematic approach.
📌
The 90/10 rule of security tooling: Untuned security tools produce 80-90% false positives. An untuned Semgrep scan on a Django project generates 200 findings — of which 180 are false positives. Developers learn to ignore the output entirely. The correct approach: spend 2-3 weeks after introduction tuning every rule category to below 10% false positive rate before enforcing as a hard block.
Systematic tuning process — from 80% FP to near zero
The 6-step process for making every security gate trustworthy
▼

1. Run in monitor modeEnable the tool but don't block on its output. Collect findings for 2 weeks against real PRs.Zero developer time. 2 weeks elapsed.
2. Categorise findingsFor each finding category: is it a real vulnerability or false positive? Document the verdict and reasoning.1-2 days (security engineer)
3. Write suppressionsFor confirmed false positives: add inline suppression comments with justification, or add to the tool's ignore config.1 day
4. Start with warn-onlyEnable blocking only on CRITICAL/HIGH with near-zero false positive rates. WARNING findings appear but don't block.0 developer time
5. Expand blockingAfter 2 weeks of blocking CRITICAL/HIGH with zero complaints, expand blocking to MEDIUM for specific high-confidence rules.Incremental
6. Monitor and iterateTrack false positive rate as a metric. Target: <5% FP rate for any blocking rule. Review suppressions quarterly — some may become valid when code changes.30 min/month

Security-as-Policy — blocking deployment with Open Policy Agent
Codifying your security requirements as machine-enforceable policies
▼

Open Policy Agent (OPA) + Rego lets you write security policies as code that evaluate structured data (JSON results from your security tools) and return a pass/fail decision. This separates policy from tooling: you can change tools without changing your blocking logic, and you can audit exactly what rules caused a deployment to be blocked.

Rego / OPA
# security-policy.rego
package devsecops

# Policy: block deployment if any CRITICAL findings exist
deny[msg] {
    finding := input.sast_results[_]
    finding.severity == "CRITICAL"
    msg := sprintf("SAST CRITICAL: %s at %s:%d",
        [finding.message, finding.path, finding.line])
}

# Policy: block if any CVE with available fix exists
deny[msg] {
    dep := input.sca_results.dependencies[_]
    vuln := dep.vulns[_]
    count(vuln.fix_versions) > 0
    msg := sprintf("SCA: %s has %s, fix: %s",
        [dep.name, vuln.id, vuln.fix_versions[0]])
}

# Policy: block if secrets found
deny[msg] {
    secret := input.secrets_results[_]
    msg := sprintf("Secret detected: %s in %s",
        [secret.type, secret.file])
}

# Policy: block if container image runs as root
deny[msg] {
    input.container_scan.image_config.User == ""
    msg := "Container image runs as root (no USER directive)"
}

allow {
    count(deny) == 0
}

Knowledge Check
DevSecOps interview questions
These questions appear in DevSecOps engineer and AppSec engineer interviews.
Q1. A developer asks: "Why do we need secrets scanning in CI if we already have pre-commit hooks?" What is the correct answer?
We don't — pre-commit hooks are sufficient if all developers have them installed
Pre-commit hooks can be bypassed with git commit --no-verify, skipped on a new developer's machine before setup, or absent when code is committed from a CI bot or IDE without the hook installed. CI secrets scanning runs on every push unconditionally and cannot be bypassed. Defence in depth: pre-commit for fast feedback, CI for enforcement.
CI scanning is only needed for scanning third-party code, not developer-written code
Pre-commit hooks scan for secrets but CI scans for vulnerabilities — they are different tools
Pre-commit hooks are the first line of defence and provide the fastest feedback (developer's machine). But they are voluntary — any developer can bypass them. New developers may not have them installed. CI/CD automation often commits code without running local hooks. The correct model: pre-commit for fast developer feedback, CI for unconditional enforcement. Both are needed. The same principle applies to all security gates: local tooling accelerates developer feedback, CI provides the hard gate that cannot be bypassed.
Q2. Your SAST tool produces 200 findings per PR, 80% of which are false positives. The development team has stopped reading the output. What is your remediation plan?
Switch to a different SAST tool that has fewer findings
Lower the severity threshold so fewer findings are reported
Switch to monitor mode (don't block), categorise all 200 findings, add suppression comments with justification for confirmed false positives, reduce blocking to only CRITICAL with near-zero FP rate, then gradually expand. The goal is developer trust: every finding they see must be real. One trusted real finding is worth 100 ignored false positives.
Make findings mandatory for developers to review and close before merging
This is the most common DevSecOps failure mode. The instinct to add more gates and more rules produces noise that gets ignored. The correct response is to step back: disable blocking temporarily, run in monitor/warn mode, and spend time categorising every finding. Suppress confirmed false positives with documented justification. Only then re-enable blocking, starting with only your highest-confidence rules. The measure of success is not "findings reported" but "findings that changed developer behaviour." A low-volume, high-precision scanner changes behaviour. A high-volume, low-precision scanner trains developers to ignore security output.
Q3. What is the difference between SAST and DAST in a DevSecOps pipeline, and why do you need both? Give a concrete example of a vulnerability that one finds but the other misses.
SAST is for web apps, DAST is for APIs. You use whichever matches your architecture.
SAST finds all vulnerabilities; DAST just confirms them. You only need SAST.
SAST analyses code without running it; DAST attacks a running application. SAST finds code-level patterns (SQLi in source code, hardcoded secrets) but has high false positives and misses runtime issues. DAST finds runtime issues (misconfigured headers, auth bypass flows requiring a live session) but cannot analyse code quality. Example: SAST finds a potential SQLi from a pattern match. DAST finds a missing CSRF token only discoverable by making actual cross-origin requests to a live app. Both are required for comprehensive coverage.
SAST runs in development, DAST runs in production. They are the same technology at different stages.
SAST (Static AST) reads your code looking for vulnerability patterns. It runs early (pre-commit or CI) and is fast. It finds: SQL injection code patterns, hardcoded secrets, dangerous function calls, insecure configurations. It misses: vulnerabilities that only manifest at runtime, authentication flows requiring a live session, response header misconfigurations, business logic flaws. DAST (Dynamic AST) sends HTTP requests to a running application. It finds: live authentication bypasses, missing security headers (X-Frame-Options, CSP), CSRF (by actually making cross-origin requests), and runtime injection (by observing actual server behaviour). It misses: code-level quality issues, things not triggered by its probe requests. Together: SAST gives you early, code-level coverage. DAST gives you runtime, end-to-end coverage. Complementary, not substitutable.

Model Answer — DevSecOps Programme for Fintech Startup

Gates and Tools (ordered by ROI and ease of implementation):
1. Secrets scanning (Gitleaks pre-commit + TruffleHog CI): Highest ROI. One leaked AWS key can cost $50K+. Zero false positives on verified secrets. Zero developer friction. Start here.
2. SCA (pip-audit + npm audit): Free tools, instant setup, catches Log4Shell-class CVEs automatically. Daily scheduled scan catches newly published CVEs. Minor developer friction only when a vulnerable dep has a fix available.
3. SAST (Semgrep free tier): Start with p/python and p/django rules. Run in warn-only mode for 2 weeks to baseline FP rate before blocking. Fintech-specific: add custom rules for PCI-DSS requirements (no card data in logs, encrypted storage).
4. IaC scanning (Checkov): Free, zero setup, catches open S3 buckets and unencrypted RDS — both PCI-DSS failures. Run on every Terraform PR.
5. Container scanning (Trivy): Free, fast, catches CVEs in base images and OS packages. Run post-build before push to registry.
6. DAST (OWASP ZAP): Deploy to staging, run ZAP API scan. Requires more setup but catches runtime auth issues and misconfigured headers.
7. SBOM generation (Syft): Generate on every merge to main. Critical for PCI-DSS audit trail and zero-day response speed.

Rollout Plan:
Month 1 (foundation, no developer friction): Install Gitleaks pre-commit across all 40 repos via a central .pre-commit-config.yaml in a shared config repo. Enable TruffleHog in GitHub Actions on all repos. Enable GitHub Secret Scanning (free, instant). Enable Dependabot on all repos. Enable pip-audit and npm audit in CI in warn mode. Deliverable: baseline report of secrets and CVE debt. Most importantly: no blocking yet — just measuring.

Month 2 (enforce with tuning): Enable SCA blocking for CRITICAL with available fix. Enable Semgrep in warn mode on all repos and spend 2 weeks categorising FPs. For PCI-DSS repos: enable Checkov blocking for S3 and encryption rules. Run Trivy on all container builds. Deliverable: all PRs now show security warnings. No blocking except secrets and critical CVEs. Track: secrets exposure rate (should drop to near zero in Month 1), false positive rate per tool.

Month 3 (mature and automate): Enable Semgrep blocking for CRITICAL/HIGH rules with confirmed low FP rates. Add DAST to staging deployment pipeline. Write 3 custom Semgrep rules for fintech-specific patterns (PAN data in logs, unencrypted card fields). Generate SBOM on every build. Set up vulnerability remediation SLAs and tracking dashboard. Deliverable: full 7-gate pipeline active, metrics dashboard live.

Developer Friction Strategy:
(1) Introduce tools one at a time, not all at once. (2) Run every new tool in warn mode for 2 weeks before blocking — give developers time to see findings without pressure. (3) Make the fix path easier than the bypass path: IDE plugins (Semgrep VS Code extension) show findings inline before CI does. (4) Never block on a finding without providing: the exact file/line, what the vulnerability is, how to fix it, and a link to documentation. (5) Set up a #security-help Slack channel where developers can ask "is this a false positive?" and get a same-day answer. (6) Track and celebrate: publish monthly "PRs caught by security gate" as a positive metric, not a blame metric.

First 3 Metrics:
1. Secrets exposure rate (count/month): Direct measure of whether pre-commit and CI scanning are working. Should trend to zero within 4 weeks. Easy to explain to the CTO.
2. SCA critical vulnerability age (days open): Measures whether discovered CVEs are actually being fixed. PCI-DSS requires timely remediation. Set alert if any CRITICAL CVE is open for >7 days.
3. Gate pass rate on first attempt (% of PRs passing all enabled gates without changes): Measures whether the developer population is learning. Start at maybe 60%, should reach 90%+ within 3 months. Low rate triggers targeted training.

Month 3 Advanced Work:
With 2 months of data: identify which Semgrep rules have the best signal-to-noise ratio and write 3 custom rules for the fintech codebase. Add DAST with authenticated scanning of payment API endpoints. Implement OPA-based policy evaluation to centralise blocking logic across all tools. Run the first internal threat modelling session on the payment processing service. Begin planning the first external penetration test (now that you have a baseline and can compare findings). Brief the CTO on PCI-DSS compliance posture improvement.
