GraphQL Security

GraphQL is not just a different syntax for REST. It is a fundamentally different API paradigm with a completely different attack surface. One endpoint replaces hundreds of REST endpoints — and with that power comes unique vulnerabilities: introspection leaks the entire schema, unbounded queries collapse your database, batching bypasses rate limits, and per-resolver authorization is trivially forgotten. This lesson covers every major GraphQL attack from first principles to production hardening.

🟢 Beginner — GraphQL from the ground up
What GraphQL is and why its security model is different
Before you can secure GraphQL, you must understand it. REST has many endpoints. GraphQL has one — and that changes everything about how you think about security.

A REST API exposes many URLs: GET /users, POST /orders, GET /orders/{id}. GraphQL exposes one URL: POST /graphql. The client sends a query specifying exactly which data it wants, and the server returns exactly that. This flexibility is powerful for developers but creates security challenges that REST simply does not have.

⚠️
The single endpoint fallacy: Many developers assume "one endpoint is easier to secure than 200 REST endpoints." This is wrong. That one endpoint exposes your entire data model and every operation simultaneously. REST has natural compartmentalization — a bug in /orders doesn't affect /users. In GraphQL the entire graph is reachable through one surface, so a missing authorization check anywhere leaks everything connected to it.

Introspection Enabled in Production
GraphQL-specific • Schema disclosure • Enables all further attacks
HIGH
What introspection reveals

GraphQL has a built-in meta-query system. Any client can send one query to discover every type, field, mutation, enum, and description in your entire schema. This is enabled by default in every GraphQL library. In development it is invaluable. In production it hands attackers a complete roadmap of your entire data model — including fields like passwordHash, mutations like deleteAllUsers, and types like AdminPanel that you may not have intended to advertise.

The introspection query attackers send first
query IntrospectionQuery {
  __schema {
    types { name kind
      fields { name
        type { name kind ofType { name } }
        args { name type { name } }
      }
    }
    mutationType {
      fields { name description
        args { name description type { name kind } }
      }
    }
  }
}
# Attacker gets back: every Type, every field on every type,
# every Mutation and its arguments, field descriptions (often
# contain internal notes like "INTERNAL USE ONLY — not for clients")
Fix — disable in production, allow in development
# Apollo Server (Node.js)
const server = new ApolloServer({
  typeDefs, resolvers,
  introspection: process.env.NODE_ENV !== 'production',
  playground: process.env.NODE_ENV !== 'production',
});

# Strawberry (Python) — via extension
from strawberry.extensions import SchemaExtension
from graphql import GraphQLError

class DisableIntrospection(SchemaExtension):
    def on_executing_start(self):
        query = self.execution_context.query or ""
        if "__schema" in query or "__type" in query:
            raise GraphQLError("Introspection disabled")

schema = strawberry.Schema(
    query=Query, mutation=Mutation,
    extensions=[DisableIntrospection] if IS_PRODUCTION else []
)

# Graphene-Django — via middleware
GRAPHENE = {
    "MIDDLEWARE": ["graphene_django.debug.DjangoDebugMiddleware"],
    "INTROSPECTION": not DEBUG,   # False in production
}

BOLA — Missing Resolver-Level Authorization
OWASP API1 • Most critical GraphQL flaw • Per-field auth required
CRITICAL
Why BOLA is uniquely dangerous in GraphQL

In REST you protect an endpoint once: add @permission_classes([IsOwner]) to GET /orders/{id} and every call to that endpoint is protected. In GraphQL you must protect every resolver for every field individually. If you protect the top-level user query but forget the orders field on the User type, an attacker reaches orders through the user query with no ownership check.

# VULNERABLE: orders field resolver has no ownership check
@strawberry.type
class User:
    id: str
    email: str

    @strawberry.field
    def orders(self, info) -> list["Order"]:
        return Order.objects.filter(user_id=self.id)  # ← returns ANY user's orders

@strawberry.type
class Query:
    @strawberry.field
    def user(self, info, id: str) -> User:
        return User.objects.get(id=id)  # ← fetches any user, no ownership check

# Attack — Alice reads Bob's orders:
query {
  user(id: "bob-uuid") {
    email
    orders { id total items { name price } }
  }
}
# Response: Bob's full order history returned to Alice
Fixed — ownership check in every resolver that handles sensitive data
@strawberry.type
class Query:
    @strawberry.field
    def user(self, info, id: str) -> User:
        requester = info.context.request.user
        if str(id) != str(requester.id) and not requester.is_staff:
            raise PermissionError("Not authorized")
        return User.objects.get(id=id)

@strawberry.type
class User:
    id: str
    email: str

    @strawberry.field
    def orders(self, info) -> list["Order"]:
        requester = info.context.request.user
        # self is the User object — only show orders if self == requester
        if str(self.id) != str(requester.id) and not requester.is_staff:
            raise PermissionError("Not authorized to view these orders")
        return Order.objects.filter(user_id=self.id)

Unbounded Query Depth — Denial of Service
GraphQL-specific DoS • One query crashes the server • OWASP API4
HIGH
The exponential query problem

GraphQL allows querying nested relations indefinitely. If your schema has deep or circular relations (User has Orders, Orders have User, User has Friends who have Orders...), one query can trigger an exponential number of database calls. This is not a bug in your resolver — it is an architectural property of GraphQL that must be explicitly constrained.

# Attack query — exponential DB load from one HTTP request
query {
  user(id: "1") {           # 1 DB call
    friends {              # 100 DB calls (user has 100 friends)
      friends {            # 10,000 DB calls
        friends {          # 1,000,000 DB calls
          friends {        # 100,000,000 DB calls → server OOM
            name email
          }
        }
      }
    }
  }
}

# Even without circular refs, wide queries are expensive:
query {
  allUsers {               # 10,000 users
    orders {               # 10,000 x 50 = 500,000 queries
      lineItems {          # 500,000 x 10 = 5,000,000 queries
        product { reviews { author { name } } }
      }
    }
  }
}
Fix — depth limit, complexity limit, and DataLoader
# Strawberry — depth and token limits via extensions
from strawberry.extensions import QueryDepthLimiter, MaxTokensLimiter

schema = strawberry.Schema(
    query=Query,
    extensions=[
        QueryDepthLimiter(max_depth=7),         # reject queries deeper than 7 levels
        MaxTokensLimiter(max_token_count=1000),  # reject huge query documents
    ]
)

# Apollo Server — depth limiting
const depthLimit = require('graphql-depth-limit')
const server = new ApolloServer({
  typeDefs, resolvers,
  validationRules: [depthLimit(7)],
})

# DataLoader — batch N+1 queries into one
# Instead of 10,000 separate "SELECT * FROM orders WHERE user_id=?" queries,
# DataLoader batches them: "SELECT * FROM orders WHERE user_id IN (?,...,?)"
from strawberry.dataloader import DataLoader

async def batch_load_orders(user_ids: list[str]) -> list:
    all_orders = await sync_to_async(list)(Order.objects.filter(user_id__in=user_ids))
    lookup = {uid: [] for uid in user_ids}
    for o in all_orders: lookup[str(o.user_id)].append(o)
    return [lookup[uid] for uid in user_ids]

orders_loader = DataLoader(load_fn=batch_load_orders)

Batching Attacks — Rate Limit Bypass
GraphQL-specific • Credential stuffing • 100 attempts in 1 HTTP request
HIGH
Two batching mechanisms attackers exploit

GraphQL supports query aliasing (multiple operations in one query using different names) and array batching (sending an array of operations in one HTTP request). Your rate limiter sees one HTTP request. But your server executes hundreds of operations. Classic credential stuffing protection fails entirely.

Attack 1 — alias-based credential stuffing
# Rate limit: 5 login attempts per minute per IP
# With aliases, 100 attempts = 1 HTTP request → 1 rate limit count
mutation {
  a1: login(email: "victim@test.com", password: "password123") { token }
  a2: login(email: "victim@test.com", password: "qwerty")       { token }
  a3: login(email: "victim@test.com", password: "letmein")      { token }
  # ... 97 more password attempts
}
# Server executes all 100 login attempts
# Rate limiter increments by 1, not 100
Attack 2 — array batch enumeration
# POST /graphql with array body — one HTTP request, 1000 operations
[
  { "query": "query { user(id: \"1\") { email } }" },
  { "query": "query { user(id: \"2\") { email } }" },
  // ... 998 more
]
# Enumerates 1000 users while rate limiter records 1 request
Fix — disable batching, rate limit per-resolver
# Apollo Server — disable array batching
const server = new ApolloServer({
  typeDefs, resolvers,
  allowBatchedHttpRequests: false,
})

# Limit aliases per query — custom Strawberry extension
from strawberry.extensions import SchemaExtension
from graphql import GraphQLError

class LimitOperationAliases(SchemaExtension):
    MAX_ALIASES = 5
    def on_executing_start(self):
        selections = self.execution_context.operation.selection_set.selections
        if len(selections) > self.MAX_ALIASES:
            raise GraphQLError(f"Max {self.MAX_ALIASES} operations per request")

# Also: rate limit by email/user in the resolver itself, not HTTP layer
@strawberry.mutation
def login(self, info, email: str, password: str) -> AuthPayload:
    key = f"login:{email}"
    if cache.get(key, 0) >= 5:
        raise GraphQLError("Too many login attempts")
    cache.incr(key, timeout=60)
    return authenticate(email, password)

Injection via GraphQL Arguments
SQLi & NoSQL Injection • Type system doesn't sanitize values • OWASP API3
CRITICAL
The type system myth

A common misconception: "GraphQL's type system prevents injection." It does not. The type system validates the shape of the query (is this a String? is this an Int?) but it does not sanitize the value. A String argument containing a SQL injection payload is still a valid String. If your resolver passes that value to a raw SQL query or MongoDB filter, you have injection.

# VULNERABLE: GraphQL argument passed to raw SQL
@strawberry.field
def search_products(self, info, name: str) -> list[Product]:
    sql = f"SELECT * FROM products WHERE name LIKE '%{name}%'"
    return db.execute(sql).fetchall()  # ← SQLi via GraphQL argument

# Attack query:
query {
  searchProducts(name: "' UNION SELECT username,password_hash,null FROM users--") {
    name
  }
}
# Returns: all usernames and password hashes in the "name" field
NoSQL injection in MongoDB-backed GraphQL
# VULNERABLE: raw MongoDB filter from GraphQL argument
@strawberry.field
def find_user(self, info, filter: JSON) -> User:
    return db.users.find_one(filter)  # ← attacker controls entire filter object

# Attack:
query {
  findUser(filter: { password: { $gt: "" } }) {
    email password
  }
}
# $gt:"" matches ANY non-empty password → returns first user in collection

# FIXED: use ORM (handles escaping automatically)
@strawberry.field
def search_products_fixed(self, info, name: str) -> list[Product]:
    return list(Product.objects.filter(name__icontains=name))  # ORM parameterizes

# FIXED: sanitize MongoDB operator keys from user input
def sanitize_mongo_filter(f: dict) -> dict:
    return {k: v for k, v in f.items() if not k.startswith('$')}

Hidden Admin Mutations — Broken Function Level Authorization
OWASP API5 • Introspection reveals admin mutations • No role check on resolvers
HIGH
The hidden mutation problem

GraphQL schemas commonly contain admin mutations that developers intended as "internal-only" but never actually protected with authorization. After running introspection, an attacker sees makeUserAdmin, exportAllData, or deleteAccount in the schema. If the resolver has no role check, any authenticated user can call them.

# Introspection reveals these mutations to any authenticated user:
type Mutation {
  updateProfile(input: ProfileInput): User
  makeUserAdmin(userId: ID!): User      # ← no auth check on resolver
  exportAllUserData: ExportJob           # ← no auth check
  deleteAccount(userId: ID!): Boolean   # ← no auth check
}

# Attacker calls immediately after reading introspection:
mutation {
  makeUserAdmin(userId: "attacker-uuid") { id role }
}
# If no role check → attacker is now admin
Fix — separate schema or permissions on every admin resolver
# Best practice: separate admin schema at /graphql/admin
# Admin mutations NEVER appear in the public /graphql schema
# /graphql/admin requires: IsAuthenticated + IsAdminUser + VPN network policy

# If single schema: permission class on every admin mutation
from strawberry.permission import BasePermission

class IsAdmin(BasePermission):
    message = "Admin role required"
    def has_permission(self, source, info, **kwargs) -> bool:
        return info.context.request.user.is_staff

@strawberry.type
class Mutation:
    @strawberry.mutation
    def update_profile(self, info, input: ProfileInput) -> User: ...

    @strawberry.mutation(permission_classes=[IsAdmin])
    def make_user_admin(self, info, user_id: str) -> User:
        user = User.objects.get(id=user_id)
        user.is_staff = True; user.save(); return user
HIGHOWASP API5Separate admin schema
CSRF via GraphQL Mutations
CWE-352 • Cookie-authenticated APIs • Often forgotten because it "feels like an API"
HIGH
Why GraphQL mutations are vulnerable to CSRF

CSRF affects any state-changing request that uses cookie-based authentication — including GraphQL mutations. When a victim visits an attacker's page, the attacker's JavaScript can POST to your GraphQL endpoint and the victim's browser will automatically include their session cookie. The mutation executes as the victim.

<!-- attacker.com — victim visits while logged into targetapp.com -->
<script>
  fetch('https://targetapp.com/graphql', {
    method: 'POST',
    credentials: 'include',    // ← sends victim's session cookie
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      query: 'mutation { updateEmail(email: "attacker@evil.com") { id } }'
    })
  });
</script>
// Victim's email is now changed to attacker-controlled address
// Next password reset goes to attacker → full account takeover
Fix options
# Option 1 (best): Use Bearer token auth instead of cookies
# Authorization: Bearer TOKEN is never sent automatically by browsers
# Cross-origin JS cannot read/set the Authorization header without CORS approval

# Option 2: SameSite=Strict on session cookie
# Django setting:
SESSION_COOKIE_SAMESITE = 'Strict'  # never sent in cross-origin requests
CSRF_COOKIE_SAMESITE    = 'Strict'

# Option 3: Enforce Content-Type: application/json
# Simple HTML forms cannot send application/json (they use text/plain or multipart)
# This blocks naive CSRF attacks but not fetch-based ones
class JsonOnlyGraphQLView(GraphQLView):
    def dispatch(self, request, *args, **kwargs):
        ct = request.META.get('CONTENT_TYPE', '')
        if request.method == 'POST' and 'application/json' not in ct:
            return HttpResponseBadRequest("Content-Type must be application/json")
        return super().dispatch(request, *args, **kwargs)
HIGHUse Bearer authSameSite=StrictCWE-352
Field Suggestions — Schema Reconstruction Without Introspection
Information leakage • Bypasses disabled introspection • Tool: Clairvoyance
MEDIUM
The "Did you mean?" bypass

GraphQL engines return helpful spelling suggestions in error messages: "Cannot query field 'emailAdress'. Did you mean 'emailAddress'?". Even with introspection fully disabled, an attacker can reconstruct your schema by guessing field names and reading these suggestions. The tool Clairvoyance automates this completely.

# Introspection disabled — but field suggestions still reveal the schema
query { user(id: "1") { passwordhash } }

# Response:
{
  "errors": [{
    "message": "Cannot query field 'passwordhash'. Did you mean 'passwordHash'?"
  }]
}
# Attacker now knows the exact field name is 'passwordHash'

# Clairvoyance automates this reconstruction:
$ python3 -m clairvoyance \
    https://api.target.com/graphql \
    -H "Authorization: Bearer TOKEN" \
    -w /usr/share/wordlists/graphql-fields.txt \
    -o recovered-schema.json
# Reconstructs full schema by iterating suggestions
# Works even when introspection is disabled

# Fix: disable field suggestions
# Apollo Server:
const server = new ApolloServer({
  typeDefs, resolvers,
  hideSchemaDetailsFromClientErrors: true,  // removes "Did you mean...?" messages
})
MEDIUMDisable field suggestions in prodTool: Clairvoyance
Subscription Authorization Bypass
WebSocket • Auth at connection only • Real-time data leak
HIGH
Two-phase authorization for subscriptions

GraphQL subscriptions open a persistent WebSocket that pushes events over time. Many implementations check authorization only at connection time — not on each event push. If permissions are revoked after subscription, the user continues receiving data. Worse: if there is no ownership check on the subscription argument, any user can subscribe to any other user's event stream.

# VULNERABLE: ownership check missing on subscription argument
@strawberry.subscription
async def order_updates(self, info, order_id: str):
    async for update in order_event_stream(order_id):
        yield update  # ← any user gets any order's events

# Attack: subscribe to another user's order events
subscription {
  orderUpdates(orderId: "victim-order-uuid") { status totalAmount }
}
# Attacker receives real-time payment and shipping updates for victim's order

# FIXED: check ownership at setup AND filter per event
@strawberry.subscription
async def order_updates_fixed(self, info, order_id: str):
    requester = info.context.request.user
    order = await sync_to_async(Order.objects.get)(id=order_id)
    if str(order.user_id) != str(requester.id) and not requester.is_staff:
        raise PermissionError("Not your order")
    async for update in order_event_stream(order_id):
        # Re-verify on each event: permissions may have changed
        fresh_user = await sync_to_async(get_user)(requester.id)
        if fresh_user.is_active:
            yield update
HIGHCheck ownership at setupRe-check per event

InQL is a Burp Suite extension built specifically for GraphQL. It sends the introspection query automatically, parses the schema, and generates a template query for every type and field. You get a complete, organised attack surface map inside Burp in seconds. Install from BApp Store → search "InQL".

# InQL workflow

# 2. InQL runs introspection, builds schema tree in sidebar
# 3. Click Query → user → InQL generates template:
query {
  user(id: "") {

    orders { id total }
  }

# 4. Send to Repeater, change id to another user's UUID → test BOLA
# 5. Browse Mutations tab → find makeUserAdmin, exportData, etc.

Clairvoyance reconstructs a GraphQL schema even when introspection is disabled, by exploiting field suggestions in error messages. It uses a wordlist to guess field names, reading "Did you mean...?" responses to confirm each one. Essential when the target has disabled introspection.

$ pip install clairvoyance

$ python3 -m clairvoyance \
    https://api.target.com/graphql \
    -H "Authorization: Bearer TOKEN" \
    -w /usr/share/wordlists/graphql-fields.txt \
    -o recovered-schema.json

# How it works internally:
# 1. Sends: query { unknownField } → gets suggestion "Did you mean 'user'?"
# 2. Confirms 'user' exists, queries user { unknownField }
# 3. Gets suggestions for nested fields → builds tree
# 4. Continues until full schema reconstructed
#
# Effective against: APIs with introspection disabled but suggestions enabled
# Fix: disable BOTH introspection AND field suggestions in production

# graphql/security_extensions.py — custom extensions
import os
from strawberry.extensions import SchemaExtension
from graphql import GraphQLError

class DisableIntrospection(SchemaExtension):
    def on_executing_start(self):
        q = self.execution_context.query or ""
        if "__schema" in q or "__type" in q:
            raise GraphQLError("Introspection is disabled")

class LimitAliases(SchemaExtension):
    MAX = 5
    def on_executing_start(self):
        n = len(self.execution_context.operation.selection_set.selections)
        if n > self.MAX:
            raise GraphQLError(f"Max {self.MAX} aliases/operations per request")

class MaskProductionErrors(SchemaExtension):
    # Hide stack traces and field suggestions in production
    def on_executing_end(self):
        if os.getenv("ENVIRONMENT") == "production":
            result = self.execution_context.result
            if result and result.errors:
                for err in result.errors:
                    if "Did you mean" in str(err.message):
                        err.message = "Unknown field"

Knowledge Check
GraphQL security interview questions
These questions appear in AppSec engineer interviews at companies with GraphQL APIs.
Q1. A developer argues that "GraphQL's strong type system prevents SQL injection because all inputs are validated against the schema." Is this correct? Explain your answer.
Correct — the type system validates all inputs, so injection is not possible
Partially correct — it prevents integer injection but not string injection
Incorrect. GraphQL's type system validates the SHAPE of input (is this a String? is this an Int?) but does NOT sanitize the VALUE. A String argument containing SQL injection payload — such as a single quote followed by OR 1=1 — is a perfectly valid String that passes type validation. If the resolver passes that value to a raw SQL query without parameterization, injection is fully exploitable. The fix is the same as REST: use an ORM, or parameterized queries.
Incorrect in theory, but GraphQL resolvers always use ORMs so it's not a practical concern
This is one of the most common GraphQL security misconceptions. The type system is a syntactic validator, not a semantic sanitizer. It ensures that if a field is typed as Int, you cannot pass a string there. But it says nothing about the content of a String. An attacker can pass a valid GraphQL String that contains SQL metacharacters, SSTI payloads, path traversal sequences, or MongoDB operators. Protection from injection requires the same patterns as always: use ORM methods that parameterize automatically, never concatenate user input into query strings.
Q2. Your team disabled GraphQL introspection in production two months ago. A security researcher reports they were still able to reconstruct your full schema. How is this possible and what additional control should you have implemented?
Not possible — if introspection is disabled, the schema cannot be discovered
The researcher found an old version of the API with introspection still enabled
Field suggestions were still enabled. When a field name is slightly misspelled, the GraphQL engine responds with "Did you mean fieldName?". A tool called Clairvoyance automates guessing field names and reading these suggestions to reconstruct the full schema without introspection. The fix: disable both introspection AND field suggestions in production. Apollo: hideSchemaDetailsFromClientErrors: true. Strawberry: custom extension that strips "Did you mean" from error messages.
The researcher guessed the endpoint URL and then guessed all field names manually
Introspection and field suggestions are two independent schema disclosure mechanisms. Disabling introspection is necessary but not sufficient. Field suggestions (the "Did you mean...?" error messages) provide the same information incrementally. Clairvoyance iterates through a wordlist of common field names, confirms each hit from the error message, then probes nested types. It can reconstruct a full schema in minutes. The complete fix requires disabling both. In Apollo Server: hideSchemaDetailsFromClientErrors: true. In Strawberry: a custom extension that rewrites error messages containing "Did you mean" to a generic "Unknown field" message.
Q3. You are testing a GraphQL API that has a login mutation. The API uses per-request rate limiting: 5 requests per minute per IP. How would you conduct a credential stuffing attack that bypasses this rate limit, and what is the correct fix?
Use rotating proxies to change your IP address for each attempt
Use a slow timing attack to stay under the 5/minute threshold
Use GraphQL query aliases: send a single HTTP request containing 100 aliased login mutations. The rate limiter counts 1 request; the server executes 100 login attempts. The correct fix has two parts: (1) limit the number of aliases per query at the schema level, and (2) implement per-resolver rate limiting by email/account, not just by HTTP request count. Account-level limiting is more important because it cannot be bypassed by any batching technique.
Send the mutations as an array in the request body to trigger batching
The alias-based batch attack is the most effective: one HTTP request contains dozens of aliased mutations, each with a different password. The HTTP rate limiter increments by 1. The resolver executes each alias independently. Array batching also works if the server allows it. The fixes: (1) Alias limit: detect the number of operations in the query document and reject if above a threshold (e.g., 5). (2) Per-resolver rate limiting by the target account (email address), not by HTTP request count. An attacker can rotate aliases and change IPs, but they cannot change which email they are targeting. Rate limiting per email is the only control that actually works for credential stuffing on GraphQL.
Q4. What is the difference between authorization for a REST endpoint and authorization for a GraphQL resolver, and why does the GraphQL approach require more discipline to implement correctly?
There is no difference — both require authentication middleware at the request level
GraphQL is simpler because there is only one endpoint to protect
REST: add one middleware or decorator to the endpoint function and every call is protected. GraphQL: every field in the schema has its own resolver function and each resolver must independently verify authorization. Protecting the top-level query resolver does not protect nested field resolvers. A missing check on one field resolver exposes everything reachable through that field to anyone who can reach the parent. This requires per-field permission classes or centralized authorization utilities that developers must consciously apply to every resolver.
GraphQL has built-in authorization via the @auth directive which REST lacks
The key insight is that GraphQL's type system connects data in a graph. Protecting a node in the graph does not protect nodes reachable from it. Example: you add IsAuthenticated to the user query. That protects the query itself. But the orders field on the User type has its own resolver, and if that resolver lacks an ownership check, any authenticated user can call user(id: "anyone") to reach their orders. REST has natural compartmentalization: a permission check on GET /orders/{id} protects that endpoint only, and a separate check on GET /users/{id} protects that one. GraphQL requires discipline to apply checks at every level of the type graph, which is why automated permission classes (like Strawberry's BasePermission applied per-field) are important for consistency.

Model Answer — Vulnerabilities Found:

Vulnerability 1 — BOLA on user() resolver (CRITICAL, OWASP API1):
Attack: Any authenticated user calls query { user(id: "victim-uuid") { email passwordHash isAdmin posts { ... } } } and gets full victim data including passwordHash. No ownership check exists.
Fix: Add ownership check: if str(id) != str(info.context.request.user.id) and not requester.is_staff: raise PermissionError("Not authorized"). Also: never expose passwordHash in the User type — remove it entirely from the schema (see Vuln 4).

Vulnerability 2 — SQL Injection in searchPosts() (CRITICAL, CWE-89):
Attack: query { searchPosts(keyword: "' UNION SELECT email,password_hash,null FROM users--") { content } } — returns all email/password pairs in the content field. GraphQL String type validation does not prevent this because the type system validates shape, not value.
Fix: Replace raw SQL with ORM: return list(Post.objects.filter(content__icontains=keyword)). The ORM parameterizes automatically.

Vulnerability 3 — BOLA on updateUser() (CRITICAL, OWASP API1):
Attack: Any user can PATCH any other user's profile by supplying a different id. No ownership check exists. Combined with Vulnerability 4 (mass assignment), this allows privilege escalation on any account.
Fix: Check str(id) == str(request.user.id) or request.user.is_staff before updating.

Vulnerability 4 — Mass Assignment via UserInput (HIGH, OWASP API3):
Attack: mutation { updateUser(id: "my-uuid", input: { isAdmin: true, passwordHash: "attacker_hash" }) { isAdmin } } — UserInput accepts isAdmin and passwordHash as writable fields. Any user can make themselves admin or set an arbitrary password hash.
Fix: Remove isAdmin and passwordHash from UserInput entirely. Create a restricted input type: input UpdateProfileInput { name: String, bio: String } — privileged fields are not writable through the API.

Vulnerability 5 — BFLA on deleteUser() and exportAllData() (HIGH, OWASP API5):
Attack: Any authenticated user can call mutation { deleteUser(userId: "victim-uuid") } to delete any account, or exportAllData to get all user data. No role check on either resolver.
Fix: Add IsAdmin permission class to both resolvers. Better: move deleteUser and exportAllData to a separate admin schema at /graphql/admin behind VPN, so they never appear in the public schema at all.

Vulnerability 6 — DoS via friends circular relation (HIGH, OWASP API4):
Attack: query { user(id:"1") { friends { friends { friends { friends { name } } } } } } — exponential DB calls, server OOM. The User.friends field creates a circular relation with no depth limit.
Fix: Add QueryDepthLimiter(max_depth=7) extension to the schema. Also use DataLoader to batch friend queries.

Vulnerability 7 — Unbounded allUsers() list (HIGH, OWASP API4):
Attack: query { allUsers(limit: 999999) { email passwordHash } } dumps entire user database. The limit parameter has no server-enforced maximum.
Fix: Enforce maximum: limit = min(limit, 100). Use cursor-based pagination with a UserConnection type instead of a plain list.

Vulnerability 8 — passwordHash exposed in User type (HIGH, OWASP API3):
Attack: Even if BOLA were fixed on the user() resolver, passwordHash is in the schema. If any other resolver returns a User object (e.g., admin endpoints, friend list), the hash is automatically accessible through it.
Fix: Remove passwordHash from the User type entirely. Create a UserPublic type with only safe fields (id, name, bio, avatar). Internal types that include sensitive fields should never be returned from public resolvers.

Production hardening config:
Extensions: QueryDepthLimiter(max_depth=7), MaxTokensLimiter(max_token_count=1000), LimitAliases(MAX=5), DisableIntrospection (production only), MaskProductionErrors (removes field suggestions from error messages).
Schema changes: Remove passwordHash from User type. Replace UserInput with UpdateProfileInput (name, bio only). Move deleteUser and exportAllData to admin schema. Add cursor pagination to allUsers.
Settings: SESSION_COOKIE_SAMESITE=Strict, SESSION_COOKIE_HTTPONLY=True, SESSION_COOKIE_SECURE=True. Require Content-Type: application/json on all GraphQL requests. Run GraphQL Cop in CI/CD and fail build on HIGH findings.
