Web Application
Firewall

A Web Application Firewall inspects HTTP/HTTPS traffic between clients and your application, blocking requests that match attack patterns before they reach application code. A WAF is not a substitute for secure code — SQL injection that would succeed at the database layer will eventually bypass any WAF rule. But as a defence-in-depth layer, a well-tuned WAF blocks the vast majority of automated attacks, buys time when a zero-day is disclosed, and provides crucial visibility into attack traffic. This lesson covers WAF mechanics, deployment models, the OWASP Core Rule Set, tuning to near-zero false positives, and the limits every AppSec engineer must know.

🟢 Beginner — How WAFs Work
Inspection, detection models, and deployment
A WAF sits between your clients and your application, inspecting every HTTP request and response. Understanding how it makes blocking decisions is essential for both configuring it and understanding its limits.
⚠️
The WAF is not a cure: A WAF is defence-in-depth layer 1, not a replacement for secure code. A skilled attacker given enough time will bypass any WAF rule set. The WAF's job is to stop commodity attacks, automated scanners, and known exploit patterns at scale, and to slow down targeted attackers enough for detection. If your code has a SQL injection vulnerability, fixing the code is the right answer. Adding a WAF rule is a temporary compensating control — virtual patching — not a solution.
Positive vs negative security models
The two fundamental detection approaches and when to use each
▼
Negative security (blocklist)

Block known-bad patterns. Allow everything else. Rules block SQLi, XSS, path traversal, command injection patterns. Easy to start; hard to be comprehensive. An attacker who finds a payload variant not in the ruleset bypasses it.

Positive security (allowlist)

Allow known-good traffic. Block everything else. Define exactly what parameters each endpoint accepts, what format they take, what ranges are valid. Highly effective but expensive to maintain. Any new API endpoint requires rule updates.

🟡 Intermediate — OWASP CRS & Cloud WAFs
The Core Rule Set and major WAF platforms
The OWASP Core Rule Set (CRS) is the industry-standard WAF rule set. Understanding it is essential whether you use ModSecurity, AWS WAF, Cloudflare, or any other platform.
OWASP Core Rule Set — structure and paranoia levels
How the CRS is organised and how to choose the right paranoia level
▼

The OWASP CRS is a set of generic attack detection rules for ModSecurity (and compatible engines) covering the OWASP Top 10 and more. It uses an anomaly scoring approach: each triggered rule adds to a transaction score, and requests are blocked when the cumulative score exceeds a threshold (default: 5). Paranoia level controls how aggressively rules trigger.

Paranoia levelRules activeFalse positive rateBest for
PL1 (default)Core rules only — high-confidence, low false-positive rulesLowStarting point for all deployments
PL2Adds more rules for better detection; more PHP/SQL-specific patternsMediumAfter tuning PL1 for 2+ weeks
PL3Adds rules that generate more false positives; catches evasion techniquesHighHigh-security environments with dedicated tuning
PL4Very aggressive; blocks nearly everything unusualVery highExtremely restricted applications only
ModSecurity + OWASP CRS (Nginx)
# /etc/nginx/conf.d/waf.conf
server {
    listen 443 ssl;
    server_name api.myapp.com;

    # Enable ModSecurity
    modsecurity on;
    modsecurity_rules_file /etc/nginx/modsec/main.conf;
}

# /etc/nginx/modsec/main.conf
Include /etc/nginx/modsec/modsecurity.conf
Include /usr/local/coreruleset/crs-setup.conf
Include /usr/local/coreruleset/rules/*.conf

# /usr/local/coreruleset/crs-setup.conf (key settings)
SecRuleEngine On                          # DetectionOnly for initial tuning
SecRequestBodyAccess On
SecResponseBodyAccess On
SecResponseBodyMimeType text/plain text/html application/json

# Anomaly scoring thresholds
SecAction \
  "id:900110,phase:1,nolog,pass,t:none,\
  setvar:tx.inbound_anomaly_score_threshold=5,\  # block at score 5
  setvar:tx.outbound_anomaly_score_threshold=4"

# Paranoia level
SecAction \
  "id:900000,phase:1,nolog,pass,t:none,\
  setvar:tx.paranoia_level=1"                    # start at PL1

# Disable specific rule for legitimate traffic
SecRuleRemoveById 920300   # Remove "Missing Accept Header" if your API clients don't send it

AWS WAF integrates natively with ALB, API Gateway, CloudFront, and AppSync. It uses Managed Rule Groups (including the AWS-managed OWASP equivalent and third-party rules from Fortinet, F5) or custom rules in Web ACLs. Pricing: per Web ACL + per rule + per request.

AWS WAF Web ACL (Terraform)
resource "aws_wafv2_web_acl" "api" {
  name  = "api-waf"
  scope = "REGIONAL"    # CLOUDFRONT for global

  default_action { allow {} }

  # Rule 1: AWS Managed OWASP Core Rule Set
  rule {
    name     = "AWSManagedRulesCommonRuleSet"
    priority = 1
    override_action { none {} }
    statement {
      managed_rule_group_statement {
        name        = "AWSManagedRulesCommonRuleSet"
        vendor_name = "AWS"
        # Override individual rules to Count (not Block) during tuning
        rule_action_override {
          name          = "SizeRestrictions_BODY"
          action_to_use { count {} }  # tune before blocking
        }
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "CommonRuleSet"
      sampled_requests_enabled   = true
    }
  }

  # Rule 2: AWS Managed SQL injection rule set
  rule {
    name     = "AWSManagedRulesSQLiRuleSet"
    priority = 2
    override_action { none {} }
    statement {
      managed_rule_group_statement {
        name        = "AWSManagedRulesSQLiRuleSet"
        vendor_name = "AWS"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "SQLiRuleSet"
      sampled_requests_enabled   = true
    }
  }

  # Rule 3: Rate limiting (per IP)
  rule {
    name     = "RateLimitPerIP"
    priority = 10
    action { block {} }
    statement {
      rate_based_statement {
        limit              = 2000   # per 5 minutes per IP
        aggregate_key_type = "IP"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "RateLimit"
      sampled_requests_enabled   = true
    }
  }
}

# Associate with ALB
resource "aws_wafv2_web_acl_association" "api" {
  resource_arn = aws_lb.api.arn
  web_acl_arn  = aws_wafv2_web_acl.api.arn
}

Cloudflare WAF sits at the CDN edge, meaning attack traffic is absorbed at Cloudflare's network before reaching your origin. It includes managed rules (OWASP equivalent), custom rules, rate limiting, bot management, and DDoS protection. The primary advantage over a self-managed WAF: Cloudflare sees attack patterns from across all its customers and updates rules automatically.

Cloudflare WAF (Terraform)
resource "cloudflare_ruleset" "waf" {
  zone_id = var.zone_id
  name    = "API WAF"
  kind    = "zone"
  phase   = "http_request_firewall_managed"

  rules {
    action = "execute"
    action_parameters {
      id = "efb7b8c949ac4650a09736fc376e9aee"  # Cloudflare OWASP CRS
      overrides {
        # Disable noisy rule during tuning
        rules {
          id     = "6179ae15870a4bb7b2d480d4843b323c"
          status = "disabled"
        }
        categories {
          category = "paranoia-level-2"
          status   = "disabled"    # only PL1 initially
        }
      }
    }
    expression  = "true"
    description = "OWASP CRS"
    enabled     = true
  }
}

# Custom rule: block SQL injection with known bypasses
resource "cloudflare_ruleset" "custom" {
  zone_id = var.zone_id
  kind    = "zone"
  phase   = "http_request_firewall_custom"

  rules {
    action      = "block"
    expression  = "(http.request.uri.query contains \"UNION SELECT\" or http.request.uri.query contains \"1=1\")"
    description = "Basic SQLi patterns"
    enabled     = true
  }

  # Rate limit login endpoint specifically
  rules {
    action = "block"
    ratelimit {
      characteristics     = ["cf.unique_visitor_id"]
      period              = 60
      requests_per_period = 5
      mitigation_timeout  = 600
    }
    expression  = "(http.request.uri.path eq \"/api/auth/login\")"
    description = "Login rate limit"
    enabled     = true
  }
}

ModSecurity (now Coraza) is the open-source WAF engine that runs as an Nginx/Apache module or as a standalone proxy. It uses the OWASP CRS. Free but requires operational expertise. Best for: Kubernetes ingress WAF, on-premises deployments, or anywhere cloud WAF isn't available.

ModSecurity custom rules — virtual patching
# Virtual patch: block exploitation of a known CVE before the fix is deployed
# CVE-2024-XXXX: path traversal in /api/files endpoint
# The regex blocks /../ patterns in the files path specifically

SecRule REQUEST_URI "@rx ^/api/files/.*\.\./.*" \
    "id:9000001,\
    phase:1,\
    deny,\
    status:400,\
    log,\
    msg:'Virtual patch: path traversal CVE-2024-XXXX',\
    tag:'CVE-2024-XXXX'"

# Custom rule: block user-agent strings from known scanners
SecRule REQUEST_HEADERS:User-Agent "@pmFromFile /etc/nginx/modsec/bad-bots.txt" \
    "id:9000002,\
    phase:1,\
    deny,\
    status:403,\
    log,\
    msg:'Known scanner blocked'"

# Custom rule: only allow known Content-Type values for API
SecRule REQUEST_METHOD "!@streq GET" \
    "id:9000003,\
    phase:1,\
    chain,\
    msg:'Invalid content-type'"
SecRule REQUEST_HEADERS:Content-Type "!@rx ^(application/json|multipart/form-data)" \
    "deny,\
    status:415"

# Exception: whitelist legitimate traffic that triggers a rule
SecRule REQUEST_URI "@beginsWith /api/search" \
    "id:9000010,\
    phase:1,\
    pass,\
    nolog,\
    ctl:ruleRemoveById=942100,\   # disable SQLi rule for search endpoint
    ctl:ruleRemoveById=942200"    # (search legitimately contains SQL keywords)
🔴 Advanced — Tuning & WAF Bypasses
Making the WAF trustworthy and understanding its limits
A WAF that blocks legitimate traffic destroys developer trust and gets disabled. A WAF with known bypass patterns is theatre. Both tuning and bypass awareness are essential operational skills.
Systematic tuning process — from noisy to trustworthy
The step-by-step process to reach near-zero false positives before enabling blocking
▼
WAF tuning workflow
# Phase 1: Deploy in detection-only mode and collect data (2 weeks)
SecRuleEngine DetectionOnly    # log everything, block nothing

# Phase 2: Analyse ModSecurity logs to find top-hit rules
$ cat /var/log/nginx/modsec_audit.log | \
    python3 -c "
import sys, json, collections
rule_hits = collections.Counter()
for line in sys.stdin:
    if 'id' in line:
        for part in line.split(','):
            if '\"id\"' in part:
                rule_hits[part.strip()] += 1
for rule, count in rule_hits.most_common(20):
    print(f'{count:5d} {rule}')
"

# Top-hit example output:
#  2847  "id":"920300"   Accept header missing  ← API clients don't send Accept
#  1204  "id":"932100"   Remote file inclusion   ← file paths in JSON params
#   891  "id":"942100"   SQL injection           ← search endpoint uses SQL keywords

# Phase 3: For each top rule, determine: false positive or true positive?
# Review 10 sample requests per rule. Classification:
# - Legitimate traffic: add exception
# - Real attack: confirm rule is correct, no exception needed
# - Noisy rule on benign pattern: tune score down or disable

# Phase 4: Add exceptions for confirmed false positives
# Method A: Disable rule globally (use sparingly)
SecRuleRemoveById 920300

# Method B: Disable rule for specific endpoint + condition (preferred)
SecRule REQUEST_URI "@beginsWith /api/search" \
    "id:90001,phase:1,pass,nolog,\
    ctl:ruleRemoveById=942100"

# Method C: Lower anomaly score for a specific rule
SecRuleUpdateActionById 932100 "setvar:tx.anomaly_score_pl1=+1"  # was +5

# Phase 5: Enable blocking at high threshold first
setvar:tx.inbound_anomaly_score_threshold=20   # week 1: very permissive
setvar:tx.inbound_anomaly_score_threshold=10   # week 2: tighten
setvar:tx.inbound_anomaly_score_threshold=5    # week 3: CRS default

# Monitor alert rate (should be <0.01% of legitimate requests)
$ grep "Access denied" /var/log/nginx/error.log | wc -l
Common WAF bypass techniques — why WAF is not the last line of defence
Every AppSec engineer needs to know these; they explain why WAF alone is never sufficient
▼
WAF bypass techniques
# 1. ENCODING bypasses — WAF decodes once, app decodes twice
# Double URL encoding:
/api?id=1' OR 1=1--               # WAF blocks: obvious SQLi
/api?id=1%2527%2520OR%25201%253D1  # WAF misses: double URL-encoded
# HTML entity encoding in JSON:
{"name": "<script>"}  # WAF sees entities; browser renders XSS

# 2. CASE / COMMENT obfuscation in SQL
SELECT * FROM users WHERE id='1' UNION SELECT...
SeLeCt * FrOm users WhErE id='1' uNiOn sElEcT...
SELECT/*!*/1,/*!*/2,/*!*/3 FROM users           # MySQL inline comments
SEL/*comment*/ECT * FR/**/OM users              # split keyword with comment

# 3. HTTP parameter pollution
# WAF inspects first value; app uses last value (or vice versa)
GET /search?q=hello&q=1' OR '1'='1

# 4. Content-Type confusion
# WAF only inspects JSON; app also processes form-encoded body
Content-Type: application/json
{"username": "admin'--"}
# Attacker sends:
Content-Type: application/x-www-form-urlencoded
username=admin'--
# If WAF only inspects JSON and app accepts both: bypass

# 5. Large body fragmentation
# WAF has a body inspection limit (e.g., 128KB)
# Attacker puts payload after 128KB of padding: WAF stops inspecting

# 6. JSON/GraphQL attacks that look legitimate
# WAF has no context for your API's schema
# {"userId": "1 OR 1=1"} — looks like normal JSON to WAF
# App uses userId in raw SQL — injected

# CONCLUSION: Fix the vulnerability. Use the WAF as a layer, not the last line.
Virtual patching — WAF as emergency compensating control
How to use WAF rules to buy time when you cannot deploy a code fix immediately
▼

Virtual patching is using a WAF rule to block exploitation of a known vulnerability while the real code fix is being developed and deployed. It is a temporary compensating control, not a permanent solution. Always track virtual patches as technical debt with a target date for replacement by a proper fix.

Virtual patching workflow
# Scenario: Critical SQLi found in /api/products?sort= parameter
# Code fix takes 3 days to test and deploy
# WAF virtual patch blocks exploitation immediately

# Step 1: Understand the vulnerability
# Vulnerable: GET /api/products?sort=name' UNION SELECT password FROM users--
# The sort parameter accepts ORDER BY clause directly (never do this)

# Step 2: Write the minimal WAF rule
# Block SQL keywords specifically in the sort parameter
SecRule ARGS:sort "@rx (?i)(union|select|insert|update|delete|drop|--|;)" \
    "id:9001001,\
    phase:2,\
    deny,\
    status:400,\
    log,\
    auditlog,\
    msg:'Virtual patch: SQLi in sort param (CVE ticket: PROD-4521)',\
    tag:'VIRTUAL_PATCH'"

# Step 3: Test the rule in detection-only first
# Step 4: Deploy and monitor for false positives
# Step 5: Track in ticket system: remove when code fix deployed
# Step 6: Verify rule removed after code fix: never accumulate virtual patches

# AWS WAF virtual patch:
rule {
  name     = "VirtualPatch-PROD4521"
  priority = 1      # high priority, check first
  action { block {} }
  statement {
    byte_match_statement {
      field_to_match { query_string {} }
      positional_constraint = "CONTAINS"
      search_string         = "union"
      text_transformations {
        priority = 0
        type     = "LOWERCASE"
      }
    }
  }
}

Knowledge Check
WAF interview questions
Q1. A security engineer proposes: "If we deploy a WAF, we don't need to fix the SQL injection in our code — the WAF will block it." Why is this wrong, and what is the correct role of the WAF?
Correct — a well-configured WAF blocks all SQL injection attacks
Wrong. WAFs can be bypassed using encoding, obfuscation, comment injection, parameter pollution, and other techniques. A skilled attacker given time will bypass WAF rules for a known vulnerability. The WAF blocks commodity attacks and automated scanners but is not a substitute for parameterised queries. The correct role: WAF as defence-in-depth layer 1 and as a virtual patch while the code fix is developed. The code fix is the actual solution.
Wrong only because WAFs are expensive to maintain
Correct, but only for cloud WAFs — not self-hosted ones
The WAF provides broad protection against known attack patterns but is not a substitute for secure code for three reasons: (1) Bypass techniques exist for every WAF rule — encoding, obfuscation, comment injection, HTTP parameter pollution. A determined attacker will find a bypass. (2) Second-order attacks: a malicious payload that is stored and later executed bypasses WAF inspection at storage time. (3) Business logic attacks look like legitimate requests. The correct model: WAF is a valuable defence-in-depth control and an excellent virtual patching tool while code fixes are in progress, but the underlying vulnerability must still be fixed. "WAF blocks it" should trigger a ticket, not close one.
Q2. You deploy the OWASP CRS at Paranoia Level 1 and immediately see hundreds of 403 responses on legitimate traffic. What went wrong and what is the correct process?
The CRS is too aggressive and should be replaced with a custom rule set
The WAF was deployed in blocking mode without a detection-only tuning period. The correct process: deploy in DetectionOnly (log but don't block), collect 2 weeks of logs, identify which rules fire most on legitimate traffic, add targeted exceptions for confirmed false positives, then enable blocking starting at a high anomaly score threshold (20) and gradually lowering it to the default (5) over 2-3 weeks while monitoring false positive rates.
PL1 is too aggressive; start at PL0 which has no rules
The CRS must be disabled for API endpoints since it only works for web apps
The classic mistake is enabling blocking without a baseline tuning period. Every application generates unique traffic patterns that the CRS may flag as suspicious: search boxes with natural language that resembles SQL, file paths in API parameters, base64-encoded data, legitimate scanner agents, etc. The CRS has no knowledge of your specific application. The tuning process: (1) DetectionOnly for 2 weeks. (2) Analyse logs for most-triggered rules. (3) For each: legitimate traffic or real attack? (4) Add exceptions for legitimate patterns. (5) Enable blocking at threshold=20. (6) Tighten to 10, then 5 over weeks while monitoring error rates. The goal: <0.01% of legitimate requests blocked before reaching default threshold.
Capstone Challenge — WAF Design for a Healthcare API

Design the WAF configuration for a HIPAA-regulated API

You are securing a REST API that handles patient health records. The API uses JWT auth, accepts JSON bodies up to 10MB for medical imaging uploads, and has a text-search endpoint that legitimately includes SQL-like keywords in queries (e.g., "patients with elevated creatinine AND BUN levels"). Design the WAF configuration addressing: deployment model, rule sets, specific exceptions needed, and rate limiting.

Known traffic patterns: Medical imaging uploads up to 10MB JSON payloads. Search endpoint at /api/search regularly includes clinical terms like "elevated", "AND", "OR", "SELECT" (as English words). Admin users at /api/admin/* access from a specific IP range (10.20.0.0/16). API clients do not send the Accept header. Roughly 5,000 requests per minute at peak.

Model Answer — WAF Configuration for Healthcare API

Deployment model: AWS WAF on the ALB (HIPAA requires that PHI traffic be inspectable — cloud edge at a CDN is acceptable but requires HIPAA BAA with Cloudflare/AWS; ALB-level WAF keeps data within your AWS environment). For the admin subnet: use a separate WAF rule that allows /api/admin/* only from 10.20.0.0/16 IP range, blocking all other sources regardless of authentication. Deploy initially in Count mode (AWS) or DetectionOnly (ModSec), not blocking, for 2 weeks.

Rule sets: AWS Managed Rules Common Rule Set (the OWASP equivalent) and AWS Managed SQLi Rule Set both in Count mode for the first 2 weeks, then blocking. Add the AWS Managed Known Bad Inputs Rule Set (blocks Log4Shell, Spring4Shell class patterns). Custom rule: Content-Type must be application/json for all non-upload endpoints; multipart/form-data only for /api/imaging/upload.

Exceptions required (with justification):
1. /api/search endpoint: disable SQLi rules 942100, 942200, 942260 for this endpoint only. Clinical search legitimately includes AND, OR, SELECT, UNION as English medical terminology. Exception scoped to this path only, not globally. Document: "Clinical search terms trigger SQL rules. Search uses parameterised full-text search; SQLi not possible at application layer. Reviewed by AppSec on [date]."
2. Disable rule 920300 (Missing Accept header) globally: API clients are medical devices and don't send Accept headers. This is a design constraint, not an attack signal.
3. Increase body size limit to 12MB for /api/imaging/upload: default CRS body limit is 128KB which would block all imaging uploads. Scope the exception to the upload endpoint only.
4. IP allowlist for /api/admin/*: custom rule ALLOW only if source IP is in 10.20.0.0/16, BLOCK otherwise. This is tighter than any CRS rule.

Rate limiting: Global: 2000 requests per 5 minutes per IP. /api/auth/login: 5 per minute per IP (credential stuffing protection). /api/search: 60 per minute per authenticated user (expensive full-text search — prevent DoS). /api/imaging/upload: 10 per minute per user (large payload limit). Admin endpoints: no additional rate limit beyond IP allowlist (admin users need unrestricted access from their subnet).

Rollout plan: Week 1-2: Count/DetectionOnly mode, all rules. Generate daily report of top-5 rule hits on legitimate traffic. Week 3: Add documented exceptions for search, Accept header, and body size. Switch SQLi and Common rules to blocking. Monitoring target: less than 0.1% legitimate requests blocked. Week 4: Tighten to default thresholds. Enable admin IP restriction. Brief developers on virtual patching process for any future vulnerabilities. For HIPAA: all WAF logs must be retained for 6 years (CloudWatch → S3 with lifecycle policy).
