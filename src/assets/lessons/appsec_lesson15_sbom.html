Software Bill
of Materials

An SBOM is a formal, machine-readable inventory of every component in a piece of software — every library, dependency, version, and licence. When Log4Shell hit in December 2021, organisations that had SBOMs knew within hours which of their systems were exposed. Organisations without them spent days or weeks manually inventorying their software. Executive Order 14028 (US, 2021) mandated SBOMs for federal software procurement, triggering industry-wide adoption. This lesson covers what SBOMs are, the two major formats, every tool for generating and consuming them, VEX attestations, and a complete pipeline that makes SBOMs a living artefact rather than a one-time snapshot.

🟢 Beginner — What SBOMs Are and Why They Exist
The ingredient list for software
A Software Bill of Materials is exactly what its name suggests: a list of every ingredient in your software product. The food industry analogy is deliberate — you cannot make informed decisions about what you consume if you do not know what is in it.

Every modern application is composed largely of open source components. Without an SBOM, the question "do we use log4j anywhere?" requires manually inspecting every repository, every container image, and every deployed artefact. With an SBOM, it is a single query: grep "log4j" sbom.json or a structured database lookup across your entire fleet. The SBOM is the inventory that makes all downstream security work tractable at scale.

⚠️
Log4Shell — the SBOM case study: CVE-2021-44228 was disclosed on 9 December 2021. CVSS 10.0. Every organisation running Java anywhere needed to know, immediately, whether they used log4j and in which versions. Organisations with SBOMs queried their inventory and had a definitive answer within hours. Organisations without them spent days manually grepping repositories and asking teams to self-report — and many missed instances that were buried 4–5 hops deep in transitive dependencies. CISA and NSA both published guidance explicitly citing this incident as justification for mandatory SBOM generation.

When to use each, what each excels at, and the key structural differences

Practical guidance

If your primary use case is security (CVE scanning, incident response, supply chain security): use CycloneDX. Its security-oriented design, native VEX support, and better tooling support in the security ecosystem make it the better choice. If your primary use case is licence compliance or you are delivering software to a customer with specific SPDX requirements: use SPDX. In practice many teams generate both. Syft and cdxgen both support both formats.

🟢 Beginner — Format Deep Dive
What SBOM files actually look like
Understanding the structure of both formats is essential for consuming and producing SBOMs programmatically.
CycloneDX JSON
SPDX JSON
Package URLs (PURL)

CycloneDX JSON is the most widely supported format in security tooling. Every component has a PURL for unambiguous identification, a hash for integrity verification, and structured licence information. The vulnerabilities section is native to CycloneDX and absent from SPDX.

SPDX JSON centres on the concept of packages and relationships. Its licence expression syntax (SPDXID references) is richer than CycloneDX for complex multi-licence situations. SPDX is an ISO standard (ISO/IEC 5962:2021), which matters for formal compliance.

Package URLs (PURLs) are the universal identifier used in both SPDX and CycloneDX. They provide an unambiguous, cross-ecosystem way to identify any package. A PURL encodes the package type, namespace, name, version, and optional qualifiers and subpath in a standard URL-like scheme.

# PURL syntax:
# pkg:type/namespace/name@version?qualifiers#subpath

# Python (PyPI)
pkg:pypi/django@4.2.3
pkg:pypi/requests@2.31.0

# Node.js (npm) — scoped package
pkg:npm/%40babel/core@7.22.0      # @ encoded as %40
pkg:npm/lodash@4.17.21

# Java (Maven) — namespace is groupId
pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1
pkg:maven/org.springframework/spring-core@6.0.11

# Go (Go modules) — namespace is module path
pkg:golang/github.com/gin-gonic/gin@v1.9.1

# Ruby (RubyGems)
pkg:gem/rails@7.0.8

# Docker/container image (with digest)
pkg:oci/python@sha256:abc123?repository_url=python&tag=3.12-slim

# Alpine APK (OS package)
pkg:apk/alpine/musl@1.2.4-r2?distro=alpine-3.18

# Debian package
pkg:deb/debian/curl@7.88.1-10+deb12u4?distro=bookworm

# PURLs enable cross-database lookups:
# NVD, OSV, GitHub Advisory, Snyk all accept PURLs as query identifiers
# One PURL works across all vulnerability databases
🟡 Intermediate — Generating SBOMs
Tools for producing SBOMs from every artefact type
An SBOM is only useful if it is accurate and comprehensive. Different tools have different coverage across ecosystems. Here is when to use each.
Syft — the Swiss Army knife of SBOM generation
Anchore's Syft generates SBOMs from container images, directories, and tarballs across 50+ ecosystems
▼

Syft is the most widely used open-source SBOM generator. It understands container image layers, filesystem layouts, language-specific package manifests (pip, npm, go.sum, Cargo.lock, Gemfile.lock, pom.xml), and OS package databases (dpkg, rpm, apk). It outputs CycloneDX, SPDX, and its own native format, in JSON, XML, or table form.

Syft — SBOM generation
# Install
$ curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh \
    | sh -s -- -b /usr/local/bin

# Generate from a container image (most comprehensive)
$ syft myapp:1.2.3 -o cyclonedx-json=sbom.cdx.json
# Scans: OS packages (apt/dpkg), Python (pip), Node.js (npm),
#  Go modules, Ruby gems, Java jars, Rust crates, .NET assemblies

# Generate from a container image — multiple output formats at once
$ syft myapp:1.2.3 \
    -o cyclonedx-json=sbom.cdx.json \
    -o spdx-json=sbom.spdx.json \
    -o table                          # human-readable to stdout

# Generate from a local directory (source code, not built image)
$ syft dir:./myapp -o cyclonedx-json=sbom-source.cdx.json

# Generate from a Docker image tarball (offline, no Docker daemon)
$ docker save myapp:1.2.3 -o myapp.tar
$ syft myapp.tar -o cyclonedx-json=sbom.cdx.json

# Scope: only application packages, not OS packages
$ syft myapp:1.2.3 --scope all-layers -o cyclonedx-json=sbom.cdx.json
# vs
$ syft myapp:1.2.3 --scope squashed -o cyclonedx-json=sbom.cdx.json

# GitHub Actions — generate SBOM as part of build pipeline
- name: Generate SBOM with Syft
  uses: anchore/sbom-action@v0
  with:
    image: myapp:${{ github.sha }}
    artifact-name: sbom-${{ github.sha }}.cdx.json
    format: cyclonedx-json
    output-file: sbom.cdx.json

# Attach SBOM as GitHub release asset
- name: Attach SBOM to release
  uses: softprops/action-gh-release@v1
  with:
    files: sbom.cdx.json

cdxgen — build-system-aware SBOM generation
OWASP's cdxgen understands build tools and produces more accurate SBOMs for complex Java, Node.js, and Python projects
▼

cdxgen (by OWASP) differs from Syft in a key way: it can invoke the actual build system to resolve dependencies, rather than just reading manifest files. For Java projects with Maven or Gradle, this means it resolves the full dependency graph as the build tool would, catching BOMs (Bill of Materials imports), dependency management sections, and optional dependencies. It also supports SBOM generation for Kubernetes manifests, Terraform, and GitHub Actions workflows.

cdxgen
# Install
$ npm install -g @cyclonedx/cdxgen

# Auto-detect project type and generate SBOM
$ cdxgen -o sbom.cdx.json

# Specify project type explicitly
$ cdxgen -t java -o sbom.cdx.json     # Maven/Gradle
$ cdxgen -t python -o sbom.cdx.json   # pip/Poetry/pipenv
$ cdxgen -t nodejs -o sbom.cdx.json   # npm/yarn/pnpm

# Generate with evidence (shows WHERE each dep was found)
$ cdxgen --evidence -o sbom.cdx.json

# Generate SBOM for a container image
$ cdxgen -t docker --image myapp:1.2.3 -o sbom.cdx.json

# Java with Maven — resolves via mvn dependency:tree
$ cdxgen -t maven -o sbom.cdx.json
# Much more accurate than reading pom.xml alone:
# handles BOMs, optional deps, version management sections

# Generate SBOM for Kubernetes YAML
$ cdxgen -t k8s -o k8s-sbom.cdx.json ./k8s/
# Finds all container images referenced in manifests

# Multi-language monorepo
$ cdxgen --multi-project -o sbom.cdx.json
SBOM quality — validating that your SBOM is actually useful
A low-quality SBOM gives false confidence. These are the quality signals to check.
▼
Quality dimensionHow to checkWhy it matters
PURL completenessjq '[.components[] | select(.purl == null)] | length' sbom.cdx.json should be 0Components without PURLs cannot be matched against vulnerability databases
Version completenessjq '[.components[] | select(.version == null or .version == "")] | length' sbom.cdx.json should be 0Unknown versions mean the CVE scanner must assume worst-case or skip the component
Dependency relationshipsjq '.dependencies | length' sbom.cdx.json should be > 0Without relationships, you cannot trace which direct dep introduced a transitive vulnerable component
Hash presencejq '[.components[] | select(.hashes == null or (.hashes | length) == 0)] | length' sbom.cdx.jsonHashes verify component integrity — ensures the component is exactly what it claims to be
Metadata completenessCheck .metadata.timestamp, .metadata.tools, .metadata.component are all presentTimestamp shows freshness; tools show provenance; component identifies what the SBOM describes
Licence datajq '[.components[] | select(.licenses == null or (.licenses | length) == 0)] | length' sbom.cdx.jsonMissing licence data means licence compliance checks are incomplete
SBOM quality validation script
import json, sys

sbom = json.load(open('sbom.cdx.json'))
components = sbom.get('components', [])
issues = []

missing_purl    = [c['name'] for c in components if not c.get('purl')]
missing_version = [c['name'] for c in components if not c.get('version')]
missing_license = [c['name'] for c in components if not c.get('licenses')]

if missing_purl:
    issues.append(f"  {len(missing_purl)} components missing PURL: {missing_purl[:3]}")
if missing_version:
    issues.append(f"  {len(missing_version)} components missing version")
if not sbom.get('metadata', {}).get('timestamp'):
    issues.append("  Missing metadata.timestamp")
if not sbom.get('dependencies'):
    issues.append("  No dependency relationships recorded")

if issues:
    print("SBOM quality issues:")
    for i in issues: print(i)
    sys.exit(1)
else:
    print(f"SBOM quality: PASS ({len(components)} components, all with PURL and version)")
SBOM attestation with cosign — proving the SBOM came from your pipeline
Attaching a signed SBOM to a container image so consumers can verify its authenticity
▼

Generating an SBOM and publishing it alongside your image is useful. But how does a consumer know the SBOM wasn't tampered with or fabricated by an attacker? Cosign attestations cryptographically bind the SBOM to the container image digest, signed with your pipeline's private key. The consumer verifies the signature with your public key before trusting the SBOM.

cosign — SBOM attestation
# 1. Generate SBOM after building the image
$ syft myapp:$SHA -o cyclonedx-json=sbom.cdx.json

# 2. Attach SBOM as a signed attestation on the image
$ cosign attest \
    --predicate sbom.cdx.json \
    --type cyclonedx \
    --key cosign.key \
    registry.io/myapp@$DIGEST
# Signs the SBOM and stores it in the OCI registry alongside the image
# The attestation is linked to the specific image digest (immutable)

# 3. Verify the attestation (consumer side)
$ cosign verify-attestation \
    --key cosign.pub \
    --type cyclonedx \
    registry.io/myapp@$DIGEST \
    | jq '.payload | @base64d | fromjson | .predicate.components | length'
# If signature verifies: prints component count
# If tampered or missing: cosign exits non-zero

# 4. Extract and use the SBOM (verified)
$ cosign verify-attestation \
    --key cosign.pub \
    --type cyclonedx \
    registry.io/myapp@$DIGEST \
    | jq -r '.payload | @base64d | fromjson | .predicate' \
    > verified-sbom.cdx.json

# Full GitHub Actions workflow:
- name: Generate SBOM
  run: syft myapp:${{ github.sha }} -o cyclonedx-json=sbom.cdx.json

- name: Attest SBOM to image
  run: |
    DIGEST=$(docker inspect --format='{{index .RepoDigests 0}}' \
             registry.io/myapp:${{ github.sha }} | cut -d@ -f2)
    cosign attest \
      --predicate sbom.cdx.json \
      --type cyclonedx \
      --key cosign.key \
      registry.io/myapp@$DIGEST
  env:
    COSIGN_PASSWORD: ${{ secrets.COSIGN_KEY_PASSWORD }}
🔴 Advanced — Consuming SBOMs
Scanning SBOMs for vulnerabilities and tracking drift
An SBOM by itself is an inventory. Its security value comes from feeding it into vulnerability scanners, diffing it between releases to detect unexpected changes, and querying it during incident response.
Grype — scanning an SBOM for vulnerabilities
Generate once, scan many times without re-pulling the image
▼

The generate-once, scan-many pattern is one of the most valuable SBOM use cases. You generate the SBOM once during CI as part of the build. You can then scan it with Grype at any future time — without re-pulling or re-building the image — to check whether newly published CVEs affect that particular version of your software. This is how you detect that a production image from 6 months ago is now vulnerable, without needing to rebuild it.

Grype — SBOM-based vulnerability scanning
# Install Grype
$ curl -sSfL https://raw.githubusercontent.com/anchore/grype/main/install.sh \
    | sh -s -- -b /usr/local/bin

# Scan an SBOM directly (no image pull needed)
$ grype sbom:./sbom.cdx.json

# Generate SBOM with Syft, then scan — this is the CI pattern
$ syft myapp:1.2.3 -o cyclonedx-json=sbom.cdx.json
$ grype sbom:./sbom.cdx.json --fail-on high --only-fixed

# JSON output for parsing and dashboarding
$ grype sbom:./sbom.cdx.json --output json > grype-report.json

# Parse: count HIGH and CRITICAL with available fix
import json, sys
data = json.load(open('grype-report.json'))
actionable = [
    m for m in data.get('matches', [])
    if m['vulnerability']['severity'] in ('High', 'Critical')
    and m['vulnerability'].get('fix', {}).get('state') == 'fixed'
]
if actionable:
    for m in actionable:
        v = m['vulnerability']
        a = m['artifact']
        print(f"  {v['id']} ({v['severity']}) in {a['name']}@{a['version']}")
        print(f"    Fix: {v['fix'].get('versions', [])}")
    sys.exit(1)

# .grype.yaml: persistent ignore rules
ignore:
  - vulnerability: CVE-2023-12345
    package:
      name: libssl
      version: 1.1.1n
    reason: "Not reachable in our build. Ticket SEC-234."
VEX — Vulnerability Exploitability eXchange
Communicating to downstream consumers whether a CVE in your SBOM actually affects them
▼

A VEX document is a statement from a software supplier about whether a specific CVE is exploitable in a specific version of their product. When you ship an SBOM and a consumer's scanner finds CVE-2023-XXXXX in a library you include, they cannot tell from the SBOM alone whether it affects them. Your VEX document says: "CVE-2023-XXXXX is in libX which we include, but the vulnerable function is never called in our product, so you are not affected." This stops the consumer from spending time chasing a phantom vulnerability.

CycloneDX VEX document (JSON)
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "version": 1,
  "metadata": {
    "timestamp": "2024-01-15T10:30:00Z",
    "component": {
      "name": "myapp", "version": "1.2.3"
    }
  },
  "vulnerabilities": [
    {
      "id": "CVE-2023-44271",
      "source": { "name": "NVD", "url": "https://nvd.nist.gov/vuln/detail/CVE-2023-44271" },
      "ratings": [{ "source": { "name": "NVD" }, "score": 7.5, "severity": "high" }],
      "affects": [
        { "ref": "pkg:pypi/Pillow@9.2.0" }
      ],
      "analysis": {
        "state": "not_affected",
        "justification": "protected_by_mitigating_control",
        "detail": "The vulnerability is in PIL.JpegImagePlugin._getmp(). Our application only processes PNG files via PIL.PngImagePlugin and never calls the JPEG plugin. Confirmed by static analysis. Ticket: SEC-456.",
        "responses": ["will_not_fix"]
      }
    },
    {
      "id": "CVE-2022-1471",
      "affects": [{ "ref": "pkg:pypi/PyYAML@5.4.1" }],
      "analysis": {
        "state": "not_affected",
        "justification": "code_not_reachable",
        "detail": "Application uses yaml.safe_load() exclusively. CVE-2022-1471 requires yaml.load() with FullLoader. The vulnerable code path is not reachable.",
        "responses": ["will_not_fix"]
      }
    }
  ]
}

# VEX analysis states:
# not_affected:  CVE exists in the package but does not affect this product
# affected:      Product IS affected and action should be taken
# fixed:         The CVE has been fixed in this version
# under_investigation: Still determining exploitability

# VEX justifications for not_affected:
# component_not_present:         Package is not in the deployed image
# vulnerable_code_not_present:   Vulnerable function excluded at build time
# vulnerable_code_not_in_execute_path: Code exists but is never called
# vulnerable_code_cannot_be_controlled_by_adversary: No user-controlled input
# inline_mitigations_already_exist: Compensating control in place
SBOM diffing — detecting unexpected dependency changes between releases
Comparing SBOMs between versions to surface supply chain surprises
▼

Diffing two SBOMs from consecutive releases tells you exactly what changed in your dependency tree: new packages added, packages removed, versions bumped, and packages whose version changed without an explicit update. This catches accidental transitive dependency upgrades, removed packages that may have been depended on, and unexpected new packages that might indicate a supply chain compromise.

SBOM diff with Syft
# Generate SBOMs for two versions
$ syft myapp:1.2.2 -o cyclonedx-json=sbom-old.cdx.json
$ syft myapp:1.2.3 -o cyclonedx-json=sbom-new.cdx.json

# Diff using syft
$ syft diff sbom-old.cdx.json sbom-new.cdx.json
  Added:
    pkg:pypi/opentelemetry-api@1.20.0       (new telemetry dependency)
    pkg:pypi/opentelemetry-sdk@1.20.0
  Removed:
    pkg:pypi/deprecated@1.2.14              (removed)
  Changed:
    pkg:pypi/requests@2.30.0 -> 2.31.0     (explicitly updated)
    pkg:pypi/urllib3@1.26.16 -> 2.0.4      (transitive upgrade via requests)
    pkg:deb/debian/libssl3@3.0.8 -> 3.0.9  (OS package update in base image)

# Python script: diff two CycloneDX SBOMs and flag unexpected additions
import json

def purl_set(sbom_path):
    data = json.load(open(sbom_path))
    return {c['purl']: c.get('version') for c in data.get('components', []) if c.get('purl')}

old = purl_set('sbom-old.cdx.json')
new = purl_set('sbom-new.cdx.json')

added   = {p: new[p] for p in new if p not in old}
removed = {p: old[p] for p in old if p not in new}
changed = {p: (old[p], new[p]) for p in new if p in old and new[p] != old[p]}

print(f"Added: {len(added)}, Removed: {len(removed)}, Changed: {len(changed)}")
if added:
    print("NEW DEPENDENCIES (review these):")
    for p, v in added.items():
        print(f"  + {p}@{v}")
🔴 Advanced — Complete SBOM Pipeline
SBOM as a living artefact in your CI/CD pipeline
An SBOM generated once and never updated is a snapshot that drifts from reality. A living SBOM is generated on every build, stored, signed, versioned, and continuously rescanned against new CVEs.

Generate, sign, store, scan, diff, and continuously monitor — end-to-end

.github/workflows/sbom.yml
name: SBOM Pipeline

on:
  push: { branches: [main] }
  schedule:
    - cron: '0 3 * * *'    # daily rescan: new CVEs against existing SBOMs

jobs:
  sbom-generate-and-scan:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      security-events: write
      id-token: write          # required for keyless cosign signing

    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }  # need history for diff

      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .

      # ── Generate SBOM ────────────────────────────────────────────
      - name: Generate SBOM with Syft
        uses: anchore/sbom-action@v0
        with:
          image: myapp:${{ github.sha }}
          artifact-name: sbom.cdx.json
          format: cyclonedx-json
          output-file: sbom.cdx.json

      # ── Validate SBOM quality ────────────────────────────────────
      - name: Validate SBOM quality
        run: |
          python3 -c "
          import json, sys
          sbom = json.load(open('sbom.cdx.json'))
          comps = sbom.get('components', [])
          no_purl = [c['name'] for c in comps if not c.get('purl')]
          no_ver  = [c['name'] for c in comps if not c.get('version')]
          if no_purl: print(f'Missing PURL: {no_purl[:5]}'); sys.exit(1)
          if no_ver:  print(f'Missing version: {no_ver[:5]}'); sys.exit(1)
          print(f'Quality OK: {len(comps)} components, all with PURL+version')
          "

      # ── Scan SBOM for vulnerabilities (Grype) ────────────────────
      - name: Grype vulnerability scan
        id: grype
        run: |
          curl -sSfL https://raw.githubusercontent.com/anchore/grype/main/install.sh \
              | sh -s -- -b /usr/local/bin
          grype sbom:./sbom.cdx.json \
              --output sarif > grype.sarif
          grype sbom:./sbom.cdx.json \
              --output json \
              --only-fixed \
              --fail-on high > grype.json || echo "FINDINGS=true" >> $GITHUB_ENV

      - name: Upload SARIF to GitHub Security
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with: { sarif_file: grype.sarif }

      # ── Sign SBOM with cosign (keyless via OIDC) ─────────────────
      - name: Install cosign
        uses: sigstore/cosign-installer@v3

      - name: Push image and attest SBOM
        run: |
          docker push registry.io/myapp:${{ github.sha }}
          DIGEST=$(docker inspect --format='{{index .RepoDigests 0}}' \
                   registry.io/myapp:${{ github.sha }} | cut -d@ -f2)
          cosign attest \
            --predicate sbom.cdx.json \
            --type cyclonedx \
            registry.io/myapp@$DIGEST
          # Keyless signing: uses GitHub OIDC token, no key management needed
          # Signature stored in public Sigstore transparency log (Rekor)

      # ── Store SBOM for future rescanning ─────────────────────────
      - name: Store SBOM as release asset
        if: github.event_name == 'push'
        uses: softprops/action-gh-release@v1
        with:
          tag_name: sbom-${{ github.sha }}
          files: sbom.cdx.json
          name: SBOM for ${{ github.sha }}

      # ── Diff against previous SBOM ───────────────────────────────
      - name: Fetch previous SBOM for diff
        run: |
          PREV_TAG=$(git tag --sort=-creatordate | grep "^sbom-" | sed -n '2p')
          if [ -n "$PREV_TAG" ]; then
            gh release download "$PREV_TAG" --pattern "sbom.cdx.json" \
               --output sbom-prev.cdx.json
            python3 -c "
          import json
          def purls(f):
              d = json.load(open(f))
              return {c['purl']: c.get('version') for c in d.get('components',[]) if c.get('purl')}
          old = purls('sbom-prev.cdx.json')
          new = purls('sbom.cdx.json')
          added = [p for p in new if p not in old]
          if added:
              print(f'NEW DEPS ({len(added)}):')
              for p in added[:10]: print(f'  + {p}')
          print(f'Changed: {sum(1 for p in new if p in old and new[p]!=old[p])}')
            "
          fi
        env:
          GH_TOKEN: ${{ github.token }}

      - name: Fail if HIGH/CRITICAL fixable vulnerabilities
        if: env.FINDINGS == 'true'
        run: |
          echo "Grype found HIGH/CRITICAL fixable vulnerabilities. See Security tab."
          exit 1

Knowledge Check
SBOM interview questions
Questions that appear in AppSec, DevSecOps, and supply chain security interviews.
Q1. A customer asks you to provide an SBOM for your product. They are evaluating whether to use CycloneDX or SPDX format. What are the key differences, and which would you recommend for a security-focused use case?
They are identical formats — just different serialisations of the same data model
SPDX is the older standard (ISO 5962), focused primarily on licence compliance and provenance, governed by the Linux Foundation. CycloneDX is an OWASP project designed specifically for security use cases: it has native VEX support, better tooling support in security scanners (Grype, Trivy, Snyk all prefer CycloneDX), and a security-oriented data model. For a security-focused use case, recommend CycloneDX. If the customer needs ISO compliance or has specific SPDX tooling, generate both — Syft and cdxgen support both formats from a single scan.
SPDX is better for all use cases because it is an ISO standard
CycloneDX is only for container images, SPDX is for source code
The key differentiator is design philosophy. SPDX was originally designed for the open source licence compliance community and evolved to include security features. CycloneDX was designed from the start for security use cases: vulnerability tracking, VEX, attestation, and software supply chain integrity. The practical difference in 2024: if your customer is feeding SBOMs into a security scanner (Grype, Trivy, Dependency-Track), CycloneDX will work better. If they are doing formal licence review or have legal/compliance processes built around SPDX, use SPDX. Since generating both adds negligible overhead (one extra flag in Syft), many teams provide both.
Q2. Your SBOM scanner reports a CRITICAL CVE in a library included in your SBOM. You have determined the vulnerable function is never called in your product. What is the correct way to communicate this to your customers and downstream users of your SBOM?
Remove the library from the SBOM to prevent false alarms
Update the SBOM to change the library version to a patched version you are not actually using
Publish a VEX (Vulnerability Exploitability eXchange) document stating the CVE analysis state as "not_affected" with the justification "vulnerable_code_not_in_execute_path" and a detailed explanation. The SBOM remains accurate (the library is still included), but the VEX document tells consuming tools and human reviewers that exploitability has been assessed and the product is not affected. This avoids false alarms for customers while maintaining SBOM honesty.
Add a note field to the SBOM component entry explaining the vulnerability is not exploitable
This is exactly the problem VEX was designed to solve. Removing a component from an SBOM because it has a CVE is dishonest and breaks the fundamental trust guarantee of an SBOM: it should accurately represent what is in the software. Changing versions is straightforwardly falsifying the record. A VEX document is the correct mechanism: it is a separate, structured, machine-readable attestation from the supplier stating their analysis of exploitability. The SBOM stays accurate; the VEX adds context. Scanning tools like Grype and Dependency-Track understand VEX and will suppress the finding for consumers when a "not_affected" VEX is present. This is the industry-standard pattern for communicating exploitability analysis.
Q3. What is the difference between generating an SBOM from source code versus from a container image, and which is more comprehensive for security purposes?
Source code SBOM is always more comprehensive because it has access to all dependency files
They are equivalent — both capture the same dependency information
A container image SBOM is more comprehensive for production security. Source code scanning captures language-level dependencies (pip packages, npm packages) but misses OS-level packages, base image components, and anything installed at image build time outside of the package manager. The container image contains the final deployed artefact including the OS layer (libssl, openssl, libc), the language runtime (Python itself, Node.js itself), and all build artefacts. For incident response and CVE triage, you need to know about the full stack including OS CVEs. Generate both: source SBOM early in the pipeline for developer feedback, image SBOM at build time for production tracking.
Container image SBOMs cannot capture language-level dependencies, only OS packages
The container image is the unit of deployment, so its SBOM represents what actually runs in production. It includes everything the source SBOM has, plus the OS base image packages (openssl, glibc, curl, libssl etc.), the language runtime itself (Python 3.12 is a component with its own CVE history), and any packages installed via apt/apk during the Dockerfile build. Log4Shell is a perfect example: a source SBOM of a Java project would find log4j in pom.xml. But a container image SBOM would also find any vulnerable OS libraries that might be affected by other CVEs. The best practice is to generate both: source SBOM gives early feedback in the developer's PR; image SBOM is the production ground truth.

Model Answer — SBOM Programme for 30-Service Fintech

1. Format choice: CycloneDX JSON
CycloneDX is the right choice for this scenario for three reasons: (1) The primary use case is security monitoring and CVE triage, not licence compliance — CycloneDX's security-first design and native VEX support are directly relevant. (2) Dependency-Track (the tool that solves the 1-hour CVE query requirement) has first-class CycloneDX support. (3) The security tooling ecosystem (Grype, Trivy, Snyk) all prefer CycloneDX. However: provide both CycloneDX and SPDX to the bank customer. Adding SPDX output costs one extra flag in Syft and ensures compatibility with whatever tooling the customer uses internally. SPDX is also an ISO standard, which matters for formal compliance assessments.

2. Generation tools: Syft for containers, cdxgen for Java services
Syft for all containerised services: it scans every image layer (OS packages, Python packages, Node.js packages, Java JARs) and produces accurate CycloneDX output. For Java services specifically, supplement with cdxgen: cdxgen invokes Maven/Gradle to resolve the full dependency tree including BOMs and version management sections that Syft may miss when reading pom.xml statically. Run both on Java services and merge or prefer cdxgen's output for the language-level components. The combined approach costs little extra in CI time and gives significantly better coverage for Java.

3. Automation across 30 repos with minimal per-repo effort
The key is centralisation, not per-repo configuration. Use a reusable GitHub Actions workflow stored in a central .github repository (the organisation's shared workflows repo). Each of the 30 repositories adds a single jobs: section that calls this shared workflow: uses: mycompany/.github/.github/workflows/sbom-generation.yml@main. The shared workflow handles: Syft generation, quality validation, Grype scan, cosign attestation, and Dependency-Track upload. Per-repo configuration is zero or near-zero. New repos automatically get SBOM generation by inheriting the shared workflow. Half a sprint is realistic for this approach: one week to build and test the shared workflow, one week to add the call to all 30 repos (can be scripted with the GitHub API).

4. Storage and signing: OCI attestation + Dependency-Track
Primary storage: cosign attestations in the OCI registry, binding the SBOM to each image digest. This is tamper-evident, travels with the image, and is discoverable by any cosign-aware tool. Use keyless signing (GitHub OIDC) to avoid key management overhead across 30 repos. Secondary storage: all SBOMs uploaded to Dependency-Track (the centralised monitoring platform). This gives queryability across all 30 services simultaneously. Additionally: store SBOMs as GitHub Release assets tagged by image SHA, which provides an easily accessible archive for customer requests and audit trails.

5. The 1-hour CVE query: OWASP Dependency-Track with webhook alerts
Deploy Dependency-Track (self-hosted, open source, or Dependency-Track Cloud). Every build uploads its SBOM to DT. DT continuously rescans all ingested SBOMs against NVD, GitHub Advisory, OSV, and Sonatype OSS Index. Configure DT to: (1) Automatically rescan all projects when new vulnerabilities are published (DT does this by default via scheduled NVD sync). (2) Send Slack/PagerDuty webhook alerts when a CRITICAL CVE matches any project. (3) Set the NVD sync interval to every 4 hours (DT default) to ensure new CVEs are picked up promptly. Result: when a new Log4Shell-class CVE drops, DT rescans all 30 services within 4 hours and sends an alert listing exactly which services are affected, what versions, and what the fix versions are. For the CTO's 1-hour requirement, configure a manual rescan trigger that can be run immediately on announcement of a major CVE. This gives sub-hour response time for critical incidents while the scheduled sync handles routine monitoring.

6. Customer delivery: a living SBOM programme, not a one-time deliverable
Initial delivery to the bank: provide the current CycloneDX JSON SBOM for each of the 30 services, plus the corresponding SPDX JSON versions. Include the Dependency-Track URL where they can query the current vulnerability status of all components (set up a read-only API key for them if they want programmatic access). Maintenance going forward: SBOMs are automatically regenerated on every build. When a new release is deployed, the bank can pull the updated SBOM from the GitHub Release assets or directly from the OCI registry via cosign. For VEX: when a CVE is found in a component you include but you have assessed it as not exploitable, publish a VEX document alongside the SBOM. This prevents the bank's scanner from raising false alarms and demonstrates mature security practice. Monthly SBOM report: send a digest of all SBOM changes (new components, version bumps, newly resolved and newly introduced CVEs) to the bank's security team to demonstrate continuous management.
