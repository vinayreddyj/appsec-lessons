Container
Security

Containers changed how software is built and deployed — and they introduced an entirely new attack surface. A single misconfigured container can hand an attacker root on the host, access to all other containers, and lateral movement across your entire cluster. This lesson covers everything: how container isolation actually works and where it breaks, Dockerfile hardening, image scanning, runtime security, Kubernetes security contexts, network policies, and admission control — from first principles to production-ready configuration.

🟢 Beginner — Container Isolation Fundamentals
How containers isolate — and where that isolation fails
A container is not a virtual machine. It shares the host kernel. Understanding exactly what is and isn't isolated is the foundation of all container security.

A VM has its own kernel, its own hardware emulation, and a hypervisor enforcing isolation at the hardware level. A container shares the host's kernel — the same Linux kernel that runs all other containers on that host. The isolation comes from two Linux kernel features: namespaces (what a process can see) and cgroups (what resources it can use). If either of these is misconfigured or bypassed, the container escape lands you in the host kernel.

⚠️
The shared kernel reality: Every container on the same host shares one kernel. A vulnerability in that kernel — like Dirty COW (CVE-2016-5195) or runc vulnerabilities — affects every container on that host simultaneously. This is why base image updates matter: a vulnerable kernel module in a container's base image can be the attack vector for a host escape that compromises every container.

Container escape vectors — how attackers break out
The 5 most common container-to-host escape techniques in the wild
▼
🔴 Real breach — Tesla Kubernetes (2018)

Tesla's Kubernetes dashboard was exposed to the internet with no authentication. Attackers gained access to the dashboard, found AWS credentials stored in pod environment variables, and used those credentials to mine cryptocurrency on Tesla's AWS infrastructure. The root cause: privileged pod with host-mounted filesystem and no authentication on the K8s dashboard.

Escape 1 — Privileged container

# A privileged container has ALL Linux capabilities and can mount the host filesystem
# If you run this in a privileged container, you own the host:
$ docker run --privileged -it ubuntu /bin/bash

# Inside the privileged container:
$ fdisk -l                          # see host disks
$ mkdir /mnt/host && mount /dev/sda1 /mnt/host   # mount host root filesystem
$ cat /mnt/host/etc/shadow          # read host password hashes
$ chroot /mnt/host /bin/bash        # chroot to host → full host access
# Game over. This is why --privileged is almost always wrong.

Escape 2 — Sensitive hostPath volume mount

# Mounting host directories gives the container direct host filesystem access
# These mounts are effectively container escapes:
volumes: [{ name: host-root, hostPath: { path: / } }]          # ← full host FS
volumes: [{ name: docker-sock, hostPath: { path: /var/run/docker.sock } }]  # ← worse

# The Docker socket mount is the most dangerous:
# With access to docker.sock you can start a new privileged container
$ docker run --rm -it -v /:/mnt/host --privileged ubuntu chroot /mnt/host /bin/bash
# This gives you full root on the host from inside a container
# Any container with /var/run/docker.sock mounted = full host escape

Escape 3 — Kernel vulnerability exploitation (CVE-2019-5736 runc)

# CVE-2019-5736: attacker can overwrite runc binary from inside a container
# Any container, no special privileges needed. Affects Docker, Kubernetes.
# Attack path:
# 1. Attacker has code execution inside container
# 2. Exploits runc vulnerability to overwrite /usr/bin/runc on host
# 3. Next time a container starts: malicious runc runs as root on host
# Fix: update runc >= 1.0-rc7. This is why base image updates matter.

# Check runc version:
$ runc --version
runc version 1.1.12  # must be >= 1.0-rc7 (CVE-2019-5736 patched)

Escape 4 — Capability abuse

# Linux capabilities break root into granular privileges
# Some capabilities allow container escape even without --privileged

# CAP_SYS_ADMIN: allows mount, unshare, many kernel operations
securityContext: { capabilities: { add: ["SYS_ADMIN"] } }  # ← dangerous

# With CAP_SYS_ADMIN inside a container:
$ mount -t cgroup -o rdma cgroup /tmp/cgrp
$ echo 1 > /tmp/cgrp/x/notify_on_release
# ... (cgroups notify escape technique) → execute commands on host

# Other dangerous capabilities:
# CAP_NET_ADMIN:  configure host network interfaces, add iptables rules
# CAP_SYS_PTRACE: trace host processes outside the container
# CAP_SYS_MODULE: load/unload kernel modules → kernel rootkits

# Fix: drop ALL capabilities, add back only what's needed
securityContext:
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]   # only if app needs to bind port < 1024

Escape 5 — Metadata service SSRF (cloud environments)

# Inside any container on AWS EC2/EKS without IMDSv2 enforcement:
# curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
# Returns temporary AWS credentials for the node's IAM role
# The node role often has much broader permissions than the app needs

# Fix 1: Enforce IMDSv2 (requires token, blocks simple curl)
$ aws ec2 modify-instance-metadata-options \
    --instance-id i-1234567890abcdef0 \
    --http-tokens required \                 # IMDSv2 required
    --http-put-response-hop-limit 1          # prevents containers from reaching metadata

# Fix 2: Use IRSA to scope permissions to the pod, not the node
# Pod's IAM role = only the permissions that specific app needs
# Even if SSRF to metadata works, the credentials are pod-scoped
Privileged = host escapedocker.sock = full hostDrop ALL capsNever hostPath /
🟡 Intermediate — Dockerfile Hardening
Building secure container images
Most container vulnerabilities are introduced at build time. A secure Dockerfile is the foundation of everything that follows. These are the patterns that eliminate entire vulnerability classes before the container ever runs.
The secure Dockerfile — before and after, line by line
Every security control explained with the reason it matters
▼
Insecure Dockerfile
FROM python:latest
WORKDIR /app
COPY . /app
RUN pip install -r requirements.txt
EXPOSE 8000
CMD ["python", "app.py"]
Problems to fix

❌ latest tag: unpinned, image changes without warning
❌ Root user: app runs as root
❌ COPY . /app: copies secrets, .git, dev files
❌ Large image: includes compilers, build tools in runtime
❌ No healthcheck: orchestrator can't detect failures

Dockerfile — production-hardened
# ── Stage 1: Build stage ────────────────────────────────────────
FROM python:3.12-slim-bookworm AS builder
                      # slim: minimal Debian, no dev tools
                      # bookworm: pinned Debian release (reproducible)
                      # 3.12: pinned Python version (not 'latest')

WORKDIR /build

# Copy only requirements first (layer caching)
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt
# --no-cache-dir: don't store pip cache in image
# --user: installs to /root/.local, keeps system Python clean

# ── Stage 2: Runtime stage ──────────────────────────────────────
FROM python:3.12-slim-bookworm AS runtime
# Multi-stage: runtime image has NO build tools, NO pip, NO gcc
# Attacker who gets into the container cannot install tools easily

WORKDIR /app

# Copy installed packages from build stage only
COPY --from=builder /root/.local /root/.local

# Use explicit .dockerignore to prevent copying secrets and dev files
# .dockerignore should include: .git/, .env, *.key, *.pem, secrets/
COPY src/ ./src/
COPY manage.py .

# Create non-root user (never run as root)
RUN addgroup --system --gid 1001 appgroup \
 && adduser --system --uid 1001 --gid 1001 --no-create-home appuser

# Set file ownership before switching user
RUN chown -R appuser:appgroup /app

# Switch to non-root user
USER appuser

# Expose non-privileged port (no CAP_NET_BIND_SERVICE needed)
EXPOSE 8000

# Drop all Linux capabilities at runtime
# Done in Kubernetes security context, not Dockerfile (see later)

# Read-only filesystem (prevents writes to app directory)
# Done in Kubernetes security context: readOnlyRootFilesystem: true

# Healthcheck: orchestrator can route traffic away from sick instances
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8000/health || exit 1

CMD ["gunicorn", "myapp.wsgi:application",
     "--bind", "0.0.0.0:8000",
     "--workers", "2"]

Distroless — the production ideal for most apps

Dockerfile — distroless runtime
# Build stage: standard Python for pip install
FROM python:3.12-slim-bookworm AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --target=/app/packages -r requirements.txt
COPY src/ ./src/

# Runtime stage: distroless — no shell, no package manager
FROM gcr.io/distroless/python3-debian12:nonroot AS runtime
# :nonroot tag runs as UID 65532 (nonroot) by default
# No /bin/sh, no /bin/bash, no apt, no curl, no wget
# Attacker who gets code execution has no tools to work with

WORKDIR /app
COPY --from=builder /app/packages /app/packages
COPY --from=builder /app/src /app/src

ENV PYTHONPATH=/app/packages

CMD ["/app/src/main.py"]
# Note: CMD must use exec form (JSON array), not shell form
# because there IS no shell in distroless
⚠️
Alpine caveat: Alpine uses musl libc instead of glibc. Some Python packages have C extensions that don't work with musl or need compilation. Test Alpine compatibility before committing. If packages fail, use slim instead. The CVE advantage of Alpine is real but not worth a broken application.
🟡 Intermediate — Image Scanning
Scanning container images for vulnerabilities
Container image scanners check every layer of your image — OS packages, language libraries, and Dockerfile configuration — against CVE databases. Here are the tools and how to integrate them into CI/CD.
Trivy
Grype
Hadolint
Docker Scout

Trivy (by Aqua Security) is the most comprehensive free container scanner. It checks OS packages, language-specific packages (pip, npm, go modules), secrets in image layers, and Dockerfile/Kubernetes misconfigurations. SARIF output integrates with GitHub Security. Install: brew install trivy or use the Docker image.

# Scan a built image — full vulnerability report
$ trivy image myapp:latest

# Scan with severity filter (CI gate: fail on HIGH/CRITICAL only)
$ trivy image \
    --severity HIGH,CRITICAL \
    --exit-code 1 \                  # non-zero exit = CI failure
    --ignore-unfixed \               # skip CVEs with no available fix
    --format table \
    myapp:latest

# SARIF output for GitHub Security tab
$ trivy image \
    --format sarif \
    --output trivy-results.sarif \
    myapp:latest

# Scan image filesystem (faster than pulling, good for local builds)
$ trivy fs --scanners vuln,secret,misconfig ./

# Scan IaC configs alongside container
$ trivy config ./kubernetes/

# Full CI/CD integration:
# After docker build, before docker push:
- name: Trivy image scan
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: myapp:${{ github.sha }}
    severity: HIGH,CRITICAL
    exit-code: 1
    ignore-unfixed: true
    format: sarif
    output: trivy.sarif

- uses: github/codeql-action/upload-sarif@v3
  with: { sarif_file: trivy.sarif }
# Findings appear in GitHub Security → Code scanning alerts

Grype (by Anchore) is a fast, standalone vulnerability scanner optimised for CI/CD. It pairs with Syft for SBOM generation. Grype can scan SBOMs directly, so you generate the SBOM once and scan it multiple times without re-pulling the image. Good for offline/air-gapped environments.

# Install
$ curl -sSfL https://raw.githubusercontent.com/anchore/grype/main/install.sh | sh -s -- -b /usr/local/bin

# Scan an image
$ grype myapp:latest

# Scan only HIGH and CRITICAL, fail CI on findings
$ grype myapp:latest \
    --fail-on high \
    --only-fixed                      # skip CVEs with no fix

# Scan an SBOM (generate once with Syft, scan many times)
$ syft myapp:latest -o cyclonedx-json > sbom.json
$ grype sbom:./sbom.json --fail-on high

# Grype config file (.grype.yaml) for persistent ignore rules:
ignore:
  - vulnerability: CVE-2023-12345     # known false positive
    reason: "Not reachable in our build. Ticket SEC-1234."
  - package:
      name: libssl                    # ignore specific package
      version: 1.1.1f
      type: deb

Hadolint is a Dockerfile linter that checks for security anti-patterns, best practice violations, and shell script issues in RUN commands. It catches: pinned vs floating tags, root user usage, curl piped to shell, unnecessary privileges, and more. Fast and zero configuration needed.

# Install and run
$ brew install hadolint
$ hadolint Dockerfile

# Example findings Hadolint catches:
Dockerfile:1  DL3007  Using latest is best avoided if reproducible builds wanted
Dockerfile:5  DL3008  Pin versions in apt get install
Dockerfile:8  DL3025  Use JSON for CMD and ENTRYPOINT
Dockerfile:12 SC2086  Double quote variables to prevent word splitting
Dockerfile:15 DL3002  Last USER should not be root

# GitHub Actions integration
- name: Hadolint lint
  uses: hadolint/hadolint-action@v3.1.0
  with:
    dockerfile: Dockerfile
    failure-threshold: warning       # fail on warnings and above
    ignore: DL3008,DL3009           # ignore specific rules

# Ignore a rule for a specific line (inline):
RUN apt-get install -y curl  # hadolint ignore=DL3008

Docker Scout is Docker's built-in image analysis tool (available in Docker Desktop and CLI). It provides a policy-based view of image health: base image recency, vulnerability counts, and recommendations for base image upgrades. Excellent for developer workflow in Docker Desktop.

# Quickview: at-a-glance security status
$ docker scout quickview myapp:latest
  i  Image stored locally, pulling from hub...
  ✔ SBOM of image already cached, 281 packages indexed

  Your image  myapp:latest  |  3C  12H  8M  2L

  Base image  python:3.12-slim-bookworm
  ✔ Updated base image  python:3.12.3-slim-bookworm
    -3C -5H -2M

# Detailed CVE report
$ docker scout cves myapp:latest \
    --only-severity high,critical \
    --only-fixed

# Recommendations for base image upgrade
$ docker scout recommendations myapp:latest

# Integrate in GitHub Actions
- name: Docker Scout scan
  uses: docker/scout-action@v1
  with:
    command: cves,recommendations
    image: myapp:${{ github.sha }}
    only-severities: high,critical
    exit-code: true
🔴 Advanced — Kubernetes Security
Securing containers in Kubernetes
Running containers in Kubernetes adds an entirely new security surface: the pod spec, RBAC, network policies, and admission control. Each layer is a defence-in-depth opportunity or an attack surface if misconfigured.
Pod & container Security Context — the most important K8s security control
Every security restriction you can apply at the pod and container level
▼
Kubernetes — hardened pod spec
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  template:
    spec:
      # ── Pod-level security context ──────────────────────────────
      securityContext:
        runAsNonRoot: true              # enforce non-root at pod level
        runAsUser: 1001                 # specific UID (matches Dockerfile)
        runAsGroup: 1001
        fsGroup: 1001                   # files created have this GID
        seccompProfile:                 # restrict system calls
          type: RuntimeDefault          # use container runtime's default seccomp
        supplementalGroups: []          # no extra group memberships

      containers:
        - name: myapp
          image: myapp:1.2.3@sha256:abc123  # pin by digest, not tag

          # ── Container-level security context ──────────────────────
          securityContext:
            allowPrivilegeEscalation: false  # cannot gain more privileges
            readOnlyRootFilesystem: true     # filesystem is read-only
            privileged: false               # explicit (default false)
            capabilities:                   # Linux capabilities
              drop: ["ALL"]                 # drop EVERYTHING
              add: []                       # add back nothing (or NET_BIND_SERVICE)

          # ── Resource limits — prevent DoS via resource exhaustion ──
          resources:
            requests:                       # guaranteed minimum
              cpu: 100m
              memory: 128Mi
            limits:                         # hard maximum (OOM kill if exceeded)
              cpu: 500m
              memory: 512Mi

          # ── Writable temp directory (required if readOnlyRootFilesystem) ─
          volumeMounts:
            - name: tmp
              mountPath: /tmp

      volumes:
        - name: tmp
          emptyDir:                         # in-memory tmpfs, wiped on pod restart
            medium: Memory
            sizeLimit: 64Mi

      # ── No service account token unless needed ──────────────────
      automountServiceAccountToken: false  # opt-in, not opt-out

      # ── Host namespace isolation ─────────────────────────────────
      hostPID: false                       # explicit (default false)
      hostIPC: false
      hostNetwork: false

What each control prevents

ControlWhat it prevents
runAsNonRoot: trueRoot processes inside the container that map to root on the host (even with user namespace remapping disabled)
readOnlyRootFilesystem: trueAttacker cannot write scripts, drop payloads, or modify application files after container start
allowPrivilegeEscalation: falseBlocks setuid binaries and the PR_SET_DUMPABLE syscall from gaining elevated privileges
capabilities: drop: ALLRemoves all 38 Linux capabilities including SYS_ADMIN, NET_ADMIN, SYS_MODULE — the most common escape paths
seccompProfile: RuntimeDefaultBlocks ~300 dangerous syscalls. The default seccomp profile blocks ptrace, kexec_load, and many kernel exploit primitives
automountServiceAccountToken: falsePod cannot call the Kubernetes API. Attacker who compromises the pod cannot enumerate cluster resources.
Resource limitsContainer cannot consume all CPU/RAM, preventing DoS to other pods on the same node
Network Policies — default-deny micro-segmentation
Without network policies all pods in a cluster can talk to all other pods. This is the firewall between your microservices.
▼

By default, Kubernetes allows all pods to communicate with all other pods in the cluster. If an attacker compromises one pod, they can reach all others via the cluster network. Network Policies are Kubernetes-native firewall rules that restrict which pods can communicate. Implementing default-deny and then allowlisting the specific flows you need limits lateral movement dramatically.

Kubernetes NetworkPolicy
# Step 1: Default-deny all ingress and egress in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}                     # selects ALL pods in namespace
  policyTypes: [Ingress, Egress]
  # no ingress/egress rules = deny everything
---
# Step 2: Allow specific traffic that the app actually needs
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-myapp
  namespace: production
spec:
  podSelector:
    matchLabels: { app: myapp }
  policyTypes: [Ingress, Egress]

  ingress:
    # Allow ingress from the ingress controller (HTTPS traffic)
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: ingress-nginx }
          podSelector:
            matchLabels: { app.kubernetes.io/name: ingress-nginx }
      ports:
        - port: 8000
          protocol: TCP

  egress:
    # Allow egress to the database pod only
    - to:
        - podSelector:
            matchLabels: { app: postgres }
      ports:
        - port: 5432
          protocol: TCP

    # Allow DNS (without this, pods can't resolve hostnames)
    - to: []
      ports:
        - port: 53
          protocol: UDP
        - port: 53
          protocol: TCP
# Result: myapp can only receive from nginx and only send to postgres + DNS
# Compromised myapp cannot reach Redis, internal APIs, metadata service, or internet
Admission Control — enforcing security policy at deploy time
OPA/Gatekeeper and Pod Security Standards reject non-compliant workloads before they run
▼

Admission controllers are Kubernetes webhooks that intercept API requests before objects are persisted to etcd. An admission controller can reject a pod spec that requests privileged mode, a hostPath volume, or no resource limits — before the pod ever starts. OPA/Gatekeeper lets you write these policies as code in the Rego language.

OPA Gatekeeper — constraint templates
# Policy 1: Block privileged containers
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sPSPPrivilegedContainer
metadata:
  name: psp-privileged-container
spec:
  match:
    kinds: [{ apiGroups: [""], kinds: ["Pod"] }]
    namespaces: ["production", "staging"]
  parameters:
    allowedCapabilities: []
    allowPrivilegeEscalation: false

# Policy 2: Require non-root user
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sPSPAllowedUsers
metadata:
  name: psp-pods-allowed-user-ranges
spec:
  match:
    kinds: [{ apiGroups: [""], kinds: ["Pod"] }]
  parameters:
    runAsUser:
      rule: MustRunAsNonRoot         # reject any pod with runAsUser: 0

# Policy 3: Require resource limits
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredResources
metadata:
  name: require-resource-limits
spec:
  match:
    kinds: [{ apiGroups: ["apps"], kinds: ["Deployment"] }]
  parameters:
    limits: ["cpu", "memory"]
    requests: ["cpu", "memory"]

# What happens when a developer deploys a non-compliant pod:
$ kubectl apply -f insecure-pod.yaml
Error from server: admission webhook "validation.gatekeeper.sh" denied the request:
  [psp-privileged-container] Privileged container is not allowed: myapp
  [psp-pods-allowed-user-ranges] Container myapp must not run as root
  [require-resource-limits] Container myapp has no resource limits

Pod Security Standards (built-in alternative to OPA)

Kubernetes Pod Security Standards
# Kubernetes 1.25+ built-in: three levels of security policy
# Privileged: no restrictions (for system components)
# Baseline:   prevents the most dangerous misconfigurations
# Restricted: follows current pod security best practices

# Apply Restricted policy to a namespace (warn+enforce):
$ kubectl label namespace production \
    pod-security.kubernetes.io/enforce=restricted \      # reject non-compliant pods
    pod-security.kubernetes.io/warn=restricted \         # warn even if not blocking
    pod-security.kubernetes.io/audit=restricted          # audit log violations

# Restricted profile requirements (automatic, no YAML policy needed):
# - Must not run as root
# - Must drop ALL capabilities
# - No privileged containers
# - readOnlyRootFilesystem required
# - No hostPath volumes
# - seccompProfile must be set
# Violations are rejected at admission time before the pod runs
Falco — runtime threat detection for containers
Detect attacks happening inside running containers in real time
▼

Falco is a CNCF runtime security tool that monitors kernel system calls and Kubernetes audit logs. It detects suspicious behaviour inside running containers: a shell being spawned, a sensitive file being read, a network connection to an unexpected destination, or a new process being executed. Falco fires an alert but does not block — it is a detection and alerting tool, not a blocker (RASP handles blocking).

Falco — default rules examples
# Rule: Detect shell spawned inside a container
- rule: Terminal shell in container
  desc: A shell was opened inside a container
  condition: >
    spawned_process and container
    and shell_procs                  # process is /bin/sh, /bin/bash etc.
    and proc.tty != 0                # has a terminal (interactive)
  output: >
    Shell spawned in container (user=%user.name container=%container.name
    image=%container.image.repository shell=%proc.name)
  priority: WARNING
  tags: [container, shell]

# Rule: Detect write to /etc inside a container
- rule: Write below etc
  desc: Attempt to write to /etc directory
  condition: >
    open_write and container
    and fd.name startswith /etc
  output: Write to /etc in container (container=%container.name file=%fd.name)
  priority: ERROR

# Rule: Detect outbound connection to unexpected destination
- rule: Unexpected outbound connection
  desc: Container made outbound connection to unexpected port
  condition: >
    outbound and container
    and not fd.rport in (80, 443, 5432, 6379)  # not expected ports
  output: Unexpected outbound (container=%container.name dest=%fd.rip:%fd.rport)
  priority: NOTICE

# Install via Helm and connect to SIEM:
$ helm install falco falcosecurity/falco \
    --namespace falco --create-namespace \
    --set falco.grpc.enabled=true \
    --set falco.grpc_output.enabled=true \

Image signing & policy enforcement with Cosign and Kyverno
Ensure every image running in the cluster was built and signed by your CI/CD pipeline
▼

Image signing (with Sigstore/Cosign) creates a cryptographic attestation that an image was built by your pipeline. Kyverno or OPA/Gatekeeper can enforce that unsigned images are rejected at admission time. This prevents: an attacker pushing a malicious image to your registry and deploying it, supply chain attacks where a dependency image is compromised, and accidental deployment of non-production images to production.

Cosign + Kyverno — image signing policy
# 1. Generate signing key pair
$ cosign generate-key-pair
# Outputs: cosign.key (private, store in Vault), cosign.pub (public, check in to repo)

# 2. Sign image in CI/CD after build and scan
- name: Sign container image
  run: |
    cosign sign \
      --key cosign.key \
      --tlog-upload=false \           # don't upload to public transparency log
      registry.io/myapp:${{ github.sha }}
  env:
    COSIGN_PASSWORD: ${{ secrets.COSIGN_KEY_PASSWORD }}

# 3. Kyverno policy: reject unsigned images
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-signed-images
spec:
  validationFailureAction: Enforce    # reject at admission (not just audit)
  background: false
  rules:
    - name: check-image-signature
      match:
        any:
          - resources:
              kinds: [Pod]
              namespaces: [production, staging]
      verifyImages:
        - imageReferences: ["registry.io/*"]
          attestors:
            - entries:
                - keys:
                    publicKeys: |-    # your cosign.pub content
                      -----BEGIN PUBLIC KEY-----
                      MFkwEwYHKoZIzj0CAQY...
                      -----END PUBLIC KEY-----
# Any pod in production/staging must use a signed image
# Attempting to deploy unsigned/unscanned image: admission webhook rejects it
Knowledge Check
Container security interview questions
Questions you will face in DevSecOps, cloud security, and AppSec engineer interviews.
Q1. A developer argues: "Our app needs to run as root because it binds to port 80." Is this correct, and how should this actually be configured?
Correct — binding to ports below 1024 requires root privileges in Linux
Incorrect. There are three alternatives: (1) Run on port 8080 (or any port >1024) and let the Kubernetes Service or load balancer handle the external port 80 mapping. (2) Add only the NET_BIND_SERVICE capability to the container, which allows port <1024 binding without full root. (3) Set the sysctl net.ipv4.ip_unprivileged_port_start=80. Running as root for this reason is a design choice, not a requirement.
Correct for the host, but containers have their own network namespace so root isn't needed
Incorrect, but the only fix is to use a service mesh like Istio to handle ports
This is one of the most common justifications for running containers as root, and it is almost always unnecessary. In Kubernetes specifically, the application almost never needs to bind directly to port 80. The typical architecture: app binds to port 8080 (or any non-privileged port), a Kubernetes Service maps external 80/443 to internal 8080, and an ingress controller handles TLS termination. The app never sees port 80 at all. If you do need port <1024 binding: add only CAP_NET_BIND_SERVICE (not full root). The principle: never add more privilege than the minimum required for the specific operation.
Q2. You find this in a Kubernetes deployment: volumes: [{ name: docker-sock, hostPath: { path: /var/run/docker.sock } }]. What is the security impact and what should replace it?
Minor issue — the socket is only useful for Docker management, not general host access
Moderate risk — should be replaced with a read-only mount
Critical — full container escape to host root. With docker.sock access, run: docker run --rm -it -v /:/mnt/host --privileged ubuntu chroot /mnt/host. This mounts the entire host filesystem and chroots into it, giving complete root on the host. Legitimate use cases (CI/CD Docker-in-Docker) should use Kaniko, Buildah, or img instead — tools that build images without needing the Docker daemon socket.
High risk but only if the container is also running as root
The Docker socket is the Docker daemon's control API. Anything that can write to that socket can issue Docker API commands: create containers, start/stop containers, pull images, and most critically, start a new privileged container with the host filesystem mounted. This is a trivial container escape that requires zero exploits — just one Docker API call. Common legitimate use: CI/CD runners that need to build Docker images. The fix: use daemonless image builders. Kaniko runs as a non-root container and builds images using the Dockerfile without needing the Docker daemon. Buildah does the same. These tools are purpose-built for building images in Kubernetes without the docker.sock escape risk.
Q3. What is the security difference between a Kubernetes NetworkPolicy and a container securityContext? When do you need each?
They are the same thing — both restrict what a container can do
NetworkPolicy is for production, securityContext is for development
SecurityContext controls what a container process can do on the host (capabilities, user ID, filesystem writes, syscalls). NetworkPolicy controls what network traffic is allowed to/from a pod. You need both: securityContext prevents privilege escalation and host escape if a container is compromised. NetworkPolicy limits lateral movement after compromise — a compromised container can't reach other pods, the metadata service, or the internet if NetworkPolicy restricts it. Defence in depth: securityContext is the first line, NetworkPolicy limits blast radius.
NetworkPolicy is the more important control; securityContext is optional for small clusters
Think of these as two complementary defence layers. SecurityContext is host-level isolation: it prevents the container process from doing dangerous things (gaining root, writing to restricted paths, using dangerous syscalls). NetworkPolicy is network-level segmentation: it limits where a compromised container can talk to. Scenario: attacker exploits an RCE vulnerability in your web app container. SecurityContext (readOnlyRootFilesystem, dropped capabilities) means they can't install tools or escalate privileges. NetworkPolicy means even with code execution, they can't reach your database, Redis, internal APIs, or the AWS metadata service. They're stuck with just the compromised container's network identity. Both controls together dramatically limit the blast radius of any container compromise.

Model Answer — All Issues Found

Dockerfile Issues:

1. FROM python:latest — Unpinned tag. New Python release changes the image without warning. Attacker can poison a tag update to introduce malicious code. Fix: FROM python:3.12-slim-bookworm (pinned version and variant).

2. COPY . /app — Copies everything including .env files, .git history, SSH keys, and development secrets. Use a .dockerignore to exclude secrets/ .env .git *.key *.pem, then COPY only what the app needs: COPY src/ requirements.txt manage.py.

3. RUN apt-get install -y curl — Adding curl to the runtime image gives attackers a tool to exfiltrate data and download payloads. If needed for healthcheck, use a purpose-built binary or Python's urllib. Never leave debugging tools in runtime images.

4. EXPOSE 80 + no USER directive — App runs as root. No USER directive means UID 0. Fix: add adduser and USER instructions before CMD. Bind to port 8000 (non-privileged). Let the Kubernetes Service handle external port 80 mapping.

5. No multi-stage build — Runtime image includes pip, build tools, and compilers. Attackers can use pip to install tools or gcc to compile exploits. Fix: use multi-stage build with builder stage for pip install, distroless or slim for runtime.

Deployment Issues:

6. privileged: true — Container escape to host root. Attacker with any code execution inside the container can mount host disks and chroot to full host. Fix: privileged: false (default). Drop ALL capabilities.

7. DB_PASSWORD in env.value — Secret hardcoded in the deployment YAML. Stored in etcd in plaintext. Visible to anyone with kubectl get deployment access. Fix: use secretKeyRef pointing to a K8s Secret (ideally synced from AWS Secrets Manager via ESO). Even better: use RDS IAM authentication to eliminate the password entirely.

8. /var/run/docker.sock hostPath — Full container escape. One Docker API call: docker run --rm -it -v /:/mnt/host --privileged ubuntu chroot /mnt/host gives complete root on the host. Fix: remove entirely. If CI/CD needs image building, use Kaniko or Buildah instead of Docker-in-Docker.

9. hostPath: / — Mounts the entire host filesystem at /host. Attacker can read /etc/shadow, SSH keys, any secret file. Fix: remove entirely. Never mount host root. Use PersistentVolumeClaims for storage needs.

10. automountServiceAccountToken: true (default) — Pod has a Kubernetes API token mounted at /var/run/secrets. Attacker can use it to enumerate cluster resources, read other secrets, create privileged pods. Fix: automountServiceAccountToken: false. Only enable with a minimal-privilege ServiceAccount if the app actually needs K8s API access.

11. hostNetwork: true — Pod uses host network namespace. Can bind to any host port, sniff all host network traffic, bypass NetworkPolicy. Fix: hostNetwork: false (default).

12. hostPID: true — Pod can see all host processes. Can send signals to host daemons, read /proc of host processes (leaking memory contents), and kill critical host services. Fix: hostPID: false (default).

13. image: registry.io/api:latest — Floating tag. Image changes without notice. Pin by digest: registry.io/api:1.2.3@sha256:abc123 to guarantee exactly what runs. Implement image signing with Cosign and Kyverno to reject unsigned images.

14. No securityContext at container level — Missing: allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities drop ALL, seccompProfile RuntimeDefault. Fix: add all four to securityContext.

15. No resource limits — Container can consume all CPU and memory on the node, causing DoS for all other pods. Fix: add resources.limits.cpu and resources.limits.memory with appropriate values.
