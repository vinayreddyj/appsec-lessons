Runtime Application
Self-Protection

Runtime Application Self-Protection (RASP) embeds security instrumentation directly inside the application runtime. Unlike a WAF, which sits outside the application and inspects HTTP traffic, RASP executes inside the application process and can see the actual function calls, database queries, and file operations that an attack triggers. RASP can block attacks that bypass WAF rules, detect second-order injection, and provide context that no external perimeter tool can match. This final lesson closes the curriculum: RASP is the innermost defence layer, the last line of defence before the vulnerability is exploited.

🟢 Beginner — How RASP Works
Security from inside the application process
RASP instruments the runtime — hooking database drivers, file system calls, deserialization functions, and other sensitive operations — to detect and block attacks at the moment they attempt to execute, not at the perimeter.
💡
Why inside the process? A WAF inspects the HTTP request and sees: GET /search?q=1'%20UNION%20SELECT. It applies a pattern match and may or may not block it. RASP sees what actually executes: the database driver is about to run SELECT * FROM products WHERE name='' UNION SELECT password FROM users--. RASP has full context: the exact SQL that would be sent, the call stack that produced it, and whether this was a parameterised call or a string concatenation. No bypass technique changes what RASP observes — it intercepts at the point of execution, after all transformations.

Python RASP — monkey-patching DB driver
import functools, re, logging

def rasp_sql_hook(original_execute):
    @functools.wraps(original_execute)
    def hooked_execute(self, query, params=None, **kwargs):
        # Inspect the query BEFORE it is sent to the database
        if params is None:
            # Unparameterised query: high risk — inspect for injection
            if detect_sqli(query):
                logging.critical(f"RASP: SQL injection blocked: {query[:200]}")
                raise SecurityException("SQL injection detected and blocked")
        # Parameterised: safe to execute (params are not interpreted as SQL)
        return original_execute(self, query, params, **kwargs)
    return hooked_execute

def detect_sqli(query: str) -> bool:
    # RASP has context: this IS the query going to the DB
    # No encoding bypass possible: we see the decoded, final query string
    patterns = [
        rr"UNION\s+SELECT",
        rr"OR\s+['\d]+=\s*['\d]+",
        rr"--\s*$",
        rr";\s*(DROP|DELETE|INSERT|UPDATE)\s+",
    ]
    return any(re.search(p, query, re.IGNORECASE) for p in patterns)

# Install the hook (at application startup)
import psycopg2.extensions
psycopg2.extensions.cursor.execute = rasp_sql_hook(
    psycopg2.extensions.cursor.execute
)
# Now every db.execute() call in the entire application passes through RASP
# This cannot be bypassed by encoding: RASP sees the final, decoded query

A custom RASP built on Python monkey-patching is the clearest way to understand the concept. It is also practical for protecting specific high-risk operations in your codebase that commercial tools might not cover well. Here is a complete multi-hook RASP implementation covering SQL, command execution, file access, and deserialization.

Python RASP — complete multi-hook implementation
# rasp/hooks.py
import functools, os, re, subprocess, pickle, logging

RASP_MODE = os.getenv("RASP_MODE", "block")   # "block" or "detect"

class RASPViolation(Exception): pass

def _rasp_action(attack_type: str, detail: str):
    logging.critical(f"[RASP] {attack_type}: {detail[:200]}")
    if RASP_MODE == "block":
        raise RASPViolation(f"Blocked by RASP: {attack_type}")
    # detect mode: log only, allow execution

# Hook 1: Database query inspection
def install_sql_hook():
    try:
        import psycopg2.extensions as ext
        _orig = ext.cursor.execute
        @functools.wraps(_orig)
        def _hooked(self, query, params=None, **kw):
            if params is None and _is_sqli(str(query)):
                _rasp_action("SQL_INJECTION", query)
            return _orig(self, query, params, **kw)
        ext.cursor.execute = _hooked
    except ImportError: pass

def _is_sqli(query: str) -> bool:
    dangerous = [rr"UNION\s+SELECT", rr";\s*(DROP|DELETE|TRUNCATE)\b",
                 rr"\bOR\b.+?=.+?\bOR\b"]
    return any(re.search(p, query, re.I) for p in dangerous)

# Hook 2: Command execution
_orig_popen = subprocess.Popen.__init__

def _safe_popen(self, args, *a, shell=False, **kw):
    if shell and isinstance(args, str):
        _rasp_action("COMMAND_INJECTION", f"shell=True: {args}")
    _orig_popen(self, args, *a, shell=shell, **kw)

subprocess.Popen.__init__ = _safe_popen

# Hook 3: Deserialization of pickle
_orig_pickle_loads = pickle.loads

def _safe_pickle_loads(data, **kw):
    import traceback
    stack = "".join(traceback.format_stack()[:-1])
    _rasp_action("INSECURE_DESERIALIZATION", f"pickle.loads() called\n{stack}")
    return _orig_pickle_loads(data, **kw)

pickle.loads = _safe_pickle_loads

# Hook 4: File path traversal
_orig_open = open

def _safe_open(file, mode='r', *args, **kwargs):
    path = os.path.realpath(str(file))
    allowed_roots = ['/var/www/uploads', '/tmp/safe']
    if mode in ('w', 'a', 'wb') and not any(path.startswith(r) for r in allowed_roots):
        _rasp_action("PATH_TRAVERSAL", f"Write to: {path}")
    return _orig_open(file, mode, *args, **kwargs)

import builtins
builtins.open = _safe_open

# Install all hooks at application startup:
# if os.getenv("RASP_ENABLED") == "1": install_all_hooks()

Zero code changes needed: install the Python/Java/Node ddtrace package, set environment variables, and RASP is active. It protects against SQLi, CMDi, path traversal, SSRF, deserialization, and includes request blocking with a UI.

Contrast Security provides RASP for Java, .NET, Python, Node.js, and Ruby. It uses bytecode instrumentation (Java) and monkey-patching (Python) to hook at every relevant point. Contrast is unique in combining IAST (dev/test vulnerability finding) and RASP (production protection) in the same agent — the same code that finds vulnerabilities in testing blocks them in production.

Contrast Security — Java agent

OpenRASP is an open-source RASP from Baidu supporting Java, PHP, and Python. It uses a JavaScript-based rule engine (V8) that loads hook scripts for each protection point. Fully open-source, no licensing cost. Best for teams who want visibility into the implementation or need to write custom detection logic.

OpenRASP — Java
# Java: add to JVM startup
java -javaagent:/opt/openrasp/rasp.jar \
     -Dopenrasp.root=/opt/openrasp \
     -jar myapp.jar

# /opt/openrasp/conf/openrasp.yml
cloud:
  enable: false              # standalone mode (no cloud dashboard)

log:
  maxburst: 100
  appender: syslog           # send alerts to syslog/SIEM

plugin:
  timeout.millis: 100        # plugin execution timeout

# OpenRASP hooks and their default actions:
# sql.connection: detect/block SQLi
# command: detect/block command injection
# fileUpload: validate uploaded file types
# readFile / writeFile: path traversal detection
# ssrf: detect outbound SSRF requests
# deserialization: detect unsafe Java deserialization
# xxe: detect XML External Entity attacks

# Custom rule in JavaScript (OpenRASP's rule engine):
plugin.register('sql', function(params, context) {
    var query = params.query;
    // Block queries that appear to use UNION-based injection
    if (/UNION\s+SELECT/i.test(query)) {
        return new Result(BLOCK, "SQL injection detected");
    }
    return new Result(IGNORE);
});

# Set RASP_MODE=detect in production
# Run for 2 weeks. Collect all alerts.
# Review: are any legitimate operations being flagged?
#   - Internal admin scripts that run raw SQL
#   - Backup scripts that call subprocesses with shell=True
#   - PDF generation that writes to filesystem

# Phase 2: Create exceptions for legitimate operations
def is_trusted_caller() -> bool:
    import traceback
    stack = traceback.format_stack()
    trusted_frames = ['backup_script.py', 'admin_task.py']
    return any(tf in ''.join(stack) for tf in trusted_frames)

# Phase 3: Enable blocking for highest-confidence hooks first
# Start with: deserialization (pickle.loads in web path is always wrong)
# Then: SQL injection detection (if all DB calls are parameterised, very low FP)
# Then: path traversal (hook specific upload endpoints)
# Last: command injection (most likely to have legitimate shell calls)

# Phase 4: Monitor false positive rate over 4 weeks
# Target: 0 false positives per day (RASP has much less FP than WAF)
# Any FP: add to trusted caller list or fix the underlying code

# Phase 5: Enable all hooks in BLOCK mode
# RASP_MODE=block in production

Knowledge Check
RASP interview questions
Q1. A colleague argues that RASP is unnecessary if the application code is already secure. What is the correct counter-argument?
Correct — if the code is secure, RASP adds overhead with no benefit
RASP is defence-in-depth for vulnerabilities that: (1) are not yet known (zero-days), (2) exist in dependencies you cannot immediately patch, (3) were missed by code review and SAST, and (4) are second-order injection that reaches the DB months later. "Secure code" is an aspiration — the question is what happens when a vulnerability is discovered that your code review and SAST missed. RASP is the last line before exploitation. It also provides invaluable context during incident response: you know exactly which request triggered which operation.
RASP is only needed for legacy code, not for modern applications
RASP is required by all compliance frameworks so it must be deployed regardless
The "secure code doesn't need RASP" argument commits the same error as "we have a WAF so we don't need to fix the code" — it assumes a single control is sufficient. Three reasons RASP adds value even on "secure" code: (1) Zero-days: a new attack technique or a newly discovered vulnerability in a dependency may not be caught by existing controls. RASP's hook-based detection does not rely on knowing the attack pattern in advance — it blocks anomalous operations regardless of how they were triggered. (2) Defence-in-depth: the second-to-last layer catching what the previous layers missed. (3) Detection value: even if RASP doesn't block, it provides the call stack, request, and exact operation that was attempted — far richer incident response context than WAF logs.
Q2. How does RASP detect second-order SQL injection when a WAF cannot?
RASP scans the database storage for malicious payloads
In second-order injection: (1) the payload is stored safely (the INSERT looks clean — WAF sees nothing suspicious). (2) Later, a different request reads the stored value and uses it in a new SQL query without sanitisation. The WAF inspects HTTP requests; it sees the safe store request and the later benign-looking read request separately. It never sees the final unsafe query. RASP is hooked at the database driver: it inspects every query sent to the database, regardless of where the data came from. When the stored malicious value reaches the driver in an unsanitised query, RASP sees it and blocks the execution.
RASP uses machine learning to predict which stored values will be used dangerously
WAFs can also detect second-order injection with the right rule configuration
This is the key architectural advantage of RASP over perimeter controls for injection attacks. The WAF's inspection point is the HTTP boundary: it sees individual HTTP requests in isolation and has no memory of previous requests. Second-order injection involves two separate HTTP requests (store, then execute), with a potentially long gap between them. The WAF cannot correlate them. RASP's inspection point is the database driver: it sees every query at the moment it is about to execute, with the complete call stack showing what code path produced it. The stored malicious value, once read back and inserted into a SQL query without parameterisation, looks exactly like a first-order injection to the database driver — and RASP blocks it at that point. This is not a magic capability; it requires that the application's DB calls go through an ORM or driver that RASP has hooked.

Model Answer — Complete Defence Stack for Payment Platform

Layer 1 — Perimeter: Cloudflare WAF (or AWS WAF on ALB). OWASP CRS at PL1, tuned in detection mode for 2 weeks before blocking. Rate limiting: global 2000 req/5min, login endpoint 5/min. DDoS protection included with Cloudflare. This stops automated scanners, known CVE exploits, and credential stuffing with zero application changes.

Layer 2 — Build pipeline: (1) GitHub Actions: all Actions pinned by SHA. OIDC for AWS access (replace static credentials immediately — this is the highest-priority fix). (2) Semgrep SAST + custom rules for Django patterns. (3) pip-audit + npm audit in CI. (4) TruffleHog secrets scanning on every PR and scheduled daily. (5) Dependabot for dependency updates. (6) Checkov for IaC scanning. (7) Trivy for container scanning. (8) cosign image signing + Kyverno admission control. Generate SBOMs on every build. This alone covers most of the attack surface for 500 engineers making mistakes.

Layer 3 — Application code: Structured code review checklist for every security-relevant PR. Custom Semgrep rules for: missing @login_required, BOLA patterns (QuerySet.get() without user=), raw SQL, pickle.loads(). Django: parameterised queries, DRF explicit serialiser fields (no __all__), CSRF enforced, httpOnly SameSite cookies. Java payment service: OWASP Java Encoder, no string SQL, no Object deserialization from user input. The 500 engineer scale means education matters: security champions programme, coding guidelines, AppSec office hours.

Layer 4 — Runtime (RASP): Datadog ASM on all Django services (zero code change, integrates with existing Datadog APM). Deploy in detection mode first. Provides: SQLi protection that WAF bypasses can't defeat, deserialization blocking, SSRF detection, user event tracking (login anomalies). For the Java payment service: Contrast Security (the commercial tool choice — justification below).

Layer 5 — Infrastructure: K8s security contexts on all pods (runAsNonRoot, readOnlyRootFilesystem, drop ALL capabilities). Default-deny NetworkPolicy with explicit allowlists per service pair. Pod Security Standards: enforce=restricted on production namespace. IRSA for AWS access from pods. Separate K8s namespace for payment service with strictest policies. Falco for runtime threat detection.

Layer 6 — Data: PostgreSQL least-privilege: separate DB users per service (Django app user: SELECT/INSERT on its tables only; payment service: separate schema, separate user). Encryption at rest: AWS RDS with KMS. Card data: never stored in plaintext; tokenised via payment processor (Stripe handles raw card data, not the internal system — reduce PCI scope). Audit logging: immutable append-only audit table with user ID, action, timestamp on all payment operations.

Commercial tool choice: Contrast Security for the Java payment service. Justification: (1) PCI-DSS requires strong application security controls around card data processing — RASP on the payment service provides the strongest possible application-layer defence. (2) Contrast provides both IAST (finds vulnerabilities in dev/test, critical for a 500-engineer team) and RASP (blocks in production) in the same agent — one tool, two modes. (3) Java's JVM agent model means zero code changes, just a -javaagent flag. (4) Contrast's call stack + request context for every blocked attack gives the incident response detail PCI DSS audit trails need. Budget alternative: Datadog ASM covers Python services; OpenRASP is free for Java if commercial budget is not available.

Priority order: Week 1: Replace static AWS credentials with OIDC (highest blast-radius risk). Enable TruffleHog secrets scanning. Week 2-3: SAST with Semgrep on all repos (big team needs automated first line). Week 4: WAF in detection mode. Month 2: WAF blocking + SCA daily scans. Month 2-3: Container security contexts + NetworkPolicy on all services. Month 3: RASP in detection mode on Django + payment service. Month 4: RASP blocking, SBOM programme, Dependency-Track. Month 5-6: SLSA provenance, image signing, Kyverno admission control.
