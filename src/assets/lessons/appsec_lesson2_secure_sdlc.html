Secure SDLC
Implementation

The SDLC — Software Development Lifecycle — is the process every team uses to build software. A Secure SDLC means weaving security into every single phase, not bolting it on at the end. This lesson teaches you exactly what to do at each phase, what tools to use, and how to prove it to an interviewer or an auditor.

You will understand

What happens at each SDLC phase, why it matters for security, and what goes wrong when it's skipped

You will implement

Real CI/CD pipeline configs, pre-commit hooks, security gates, and policy-as-code patterns

You will defend

Answer "how does your team implement Secure SDLC?" confidently in any AppSec interview

The Core Problem
Why "security at the end" fails

Most teams used to build first and audit later. That model is broken — and understanding why is foundational to your career as an AppSec engineer.

The IBM Systems Science Institute found that fixing a bug found in production costs 100× more than fixing the same bug found in design. Not 2×. Not 10×. One hundred times more expensive in money, time, and reputation.

📊 Real Cost — The IBM Finding

A SQL injection vulnerability found during requirements/design review costs ~$80 to fix (developer time to redesign input handling). The same SQLi found after a production breach costs $80,000–$8M+ (incident response, legal, regulatory fines, public notification, customer loss, brand damage). The ratio is 1:100 to 1:100,000.

⚠️
Security bolt-on failure: When security is a final gate before release, developers get a pentest report 2 days before launch, scramble to "fix" issues superficially without understanding them, and ship insecure software anyway because the deadline doesn't move. This is the waterfall security model — and it fails every time.
💡
Secure SDLC as a career concept: As an AppSec engineer, your job is NOT to be the gatekeeper who blocks releases. Your job is to make security invisible to developers — to embed it so deeply in tooling and process that vulnerabilities are caught automatically before they ever reach you. This lesson teaches you how to do that.

Phase 1 — Requirements
Security requirements: writing abuse cases

Most teams write use cases ("user can log in"). An AppSec engineer also writes abuse cases — the security inverse of every feature.

A use case describes what the system should do. An abuse case describes what an attacker could do to exploit that feature. Writing both at the requirements phase is the earliest and cheapest form of threat identification.

Feature (Use Case)Abuse CaseSecurity Requirement Created
User can log in with email/passwordAttacker brute-forces passwords with 10,000 attempts/secondMax 5 failed attempts per 15 min per account + IP lockout
User can reset password via emailAttacker enumerates valid emails from "email not found" errorAlways return same message regardless of whether email exists
User can upload a profile photoAttacker uploads a PHP webshell disguised as a .jpgValidate MIME type server-side, not just extension. Re-encode image via Pillow to strip metadata and payloads.
Admin can search users by nameAttacker SQLi payload in search field dumps entire user tableAll DB queries must use parameterized statements. No string concatenation in queries.
App stores user credit card for repeat purchasesDB breach exposes all stored card numbersUse Stripe/Braintree tokenization — never store raw card numbers. PCI scope isolation.
API returns user profile dataAttacker increments user_id to harvest all profiles (IDOR)All resource endpoints must verify requesting user owns the resource before returning data.
ℹ️
Compliance requirements also live here: If you're building anything that processes payments → PCI-DSS requirements. Medical data → HIPAA. EU users → GDPR (right to erasure, data minimization, breach notification within 72 hours). These must be captured in requirements or you'll violate regulations you didn't know applied to you.
Phase 2 — Design
Threat modeling in the design phase

Threat modeling is "thinking like an attacker before you write code." We cover STRIDE in depth in Lesson 3, but here's the design-phase workflow.

At the design phase you draw a Data Flow Diagram (DFD) — showing every component, every data store, every external entity, and every boundary between trust levels. You then apply STRIDE to every arrow and box to ask "what could an attacker do here?"

DFD → STRIDE analysis for a login feature
┌─────────────────────────────────────────────────────────────────┐
│  TRUST BOUNDARY: Internet ↔ Application Server                  │
│                                                                  │
│  [Browser] ──POST /login──▶ [Auth Service] ──SQL──▶ [User DB]  │
│      │                           │                              │
│      │                     [Session Store]                      │
│      ▼                           │                              │
│  [Browser Cookie] ◀──token───────┘                             │
└─────────────────────────────────────────────────────────────────┘

STRIDE Analysis on this diagram:

Spoofing:       Can attacker fake the browser identity?
               → Risk: session token theft via XSS
               → Control: HttpOnly + Secure cookie flags

Tampering:      Can attacker modify POST /login data in transit?
               → Risk: MITM without TLS
               → Control: HTTPS enforced, HSTS header

Repudiation:    Can user deny performing an action?
               → Risk: no audit trail for login events
               → Control: immutable security event log with timestamps

Information:    Does the Auth Service leak sensitive data in errors?
               → Risk: "user not found" vs "wrong password" → user enumeration
               → Control: generic "invalid credentials" message always

Denial of Service: Can attacker flood POST /login?
               → Risk: CPU overload from bcrypt on 10k requests/sec
               → Control: rate limiting per IP + per account + CAPTCHA

Elevation:      Can user gain admin access?
               → Risk: role field in JWT not verified server-side
               → Control: role loaded from DB on every request, never from token
💡
Design-phase security controls are the cheapest: Adding "rate limit this endpoint" as a design decision takes 30 seconds. Adding it after a credential stuffing attack already happened takes 3 weeks (incident response + code change + deploy + post-mortem + customer notification).
Design Principles
The 5 core security design principles
Principle 1
Least Privilege
Every component, user, and service should have the minimum permissions needed to do its job — nothing more. A read-only API that only reads data should have a read-only DB user, not the same admin credentials as the migration runner. If that API is compromised, an attacker can read data but cannot drop tables or create admin users.
Example: AWS IAM policy with only "s3:GetObject" on a specific bucket prefix, not "s3:*" on "*"
Principle 2
Defense in Depth
Don't rely on a single security control. Layer them so that if one layer fails, the next catches it. WAF blocks the SQLi attempt → if it gets through, parameterized queries prevent execution → if that fails, read-only DB user limits damage → if that fails, DB monitoring alerts the SOC. The attacker must defeat every layer.
Layers: WAF → Input validation → Parameterized queries → Read-only DB user → DB audit logging → SIEM alert
Principle 3
Fail Secure (Fail Safe)
When something goes wrong, the system should default to the most secure state, not the most available one. If your authorization service is down, the answer is "deny all access" — not "allow all access so the app stays up." If a JWT expires or can't be verified, the user is logged out — not kept logged in.
Bad example: if auth_service_down: return True # allow everything to keep app running
Principle 4
Separation of Concerns
Security logic and business logic must be separated. Don't weave authorization checks into business logic — they get removed when "refactoring," forgotten when adding new code paths, and are impossible to audit. Use dedicated middleware, decorators, or a policy engine (OPA, Casbin) that enforces access control regardless of what the business logic does.
Pattern: Centralized auth middleware → policy engine → every request passes through it
Principle 5
Complete Mediation
Every single access to every single resource must be checked against the authorization policy — every time, not just on first access. Don't cache authorization decisions for performance without expiry. An admin user who is demoted to regular user must lose access immediately, not after their cached decision expires.
Critical for: API endpoints, file downloads, WebSocket connections, batch jobs, background workers
Phase 3 — Development
Secure coding: what developers must do

As an AppSec engineer, you set the rules developers follow. These are the non-negotiable secure coding standards you enforce.

Rule 1 — Input Validation: never trust user data
The #1 cause of injection, XSS, and buffer overflow
▼

Every piece of data that enters your application from outside — query parameters, POST bodies, HTTP headers, file uploads, WebSocket messages, even data read from a DB that was written by a user — must be validated before use. Validation happens server-side, always. Client-side validation is UX, not security.

Two types of validation

TypeWhat it doesWhen to use
Allowlist (Whitelist)Define exactly what IS allowed. Reject everything else.Always preferred. Use for fields with known valid formats: email, phone, amount, enum values.
Blocklist (Blacklist)Define what is NOT allowed. Allow everything else.Last resort only. Attackers find bypasses for every blocklist. Never use for security-critical fields.
Allowlist validation — the right way
import re
from pydantic import BaseModel, validator, conint
from decimal import Decimal

class TransferRequest(BaseModel):
    # Pydantic enforces types AND validates at parse time
    amount:     Decimal                              # must be valid decimal — no "drop table" here
    to_account: str
    currency:   str

    @validator('amount')
    def validate_amount(cls, v):
        if v <= 0:            # allowlist: must be positive
            raise ValueError('Amount must be positive')
        if v > 10_000:         # allowlist: business rule maximum
            raise ValueError('Exceeds single transfer limit')
        return v

    @validator('to_account')
    def validate_account(cls, v):
        if not re.match(r'^[A-Z]{2}\d{18}$', v):  # allowlist: IBAN format only
            raise ValueError('Invalid account format')
        return v

    @validator('currency')
    def validate_currency(cls, v):
        ALLOWED = {'USD', 'EUR', 'GBP', 'JPY'}
        if v.upper() not in ALLOWED:     # allowlist: explicit set
            raise ValueError(f'Currency must be one of {ALLOWED}')
        return v.upper()

Pydantic models enforce input validation at the boundary of your application. If data doesn't match the schema, it's rejected with a 422 before reaching any business logic. This is the "parse, don't validate" pattern — you either get a valid, typed object or you get an error. There is no invalid data inside your system.

Rule 2 — Output Encoding: prevent XSS
Data must be encoded for the context it's placed into
▼

Cross-Site Scripting (XSS) happens when user-supplied data is placed directly into HTML without encoding. The browser sees the data as code and executes it. The fix is context-specific output encoding — encoding the data differently depending on where it appears.

Output encoding contexts

ContextExample locationEncoding requiredRisk if skipped
HTML body<p>{user_input}</p>HTML entity encoding: < → &lt;Stored/reflected XSS
HTML attribute<input value="{input}">HTML attribute encoding (quote all values)Attribute injection XSS

Rule 3 — Pre-commit hooks: catch issues before they exist in git
The cheapest security gate: runs on the developer's machine before any code is pushed
▼

A pre-commit hook runs on the developer's machine before git commit succeeds. It's the earliest possible automated check. If a developer accidentally adds an API key, the hook catches it before it ever enters git history. Once a secret is in git history, it's compromised — even after deletion, it lives in every clone and fork.

.pre-commit-config.yaml — full setup
# Install: pip install pre-commit && pre-commit install

repos:
  # 1. Detect secrets BEFORE they enter git
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.4.0
    hooks:
      - id: detect-secrets
        args: ['--baseline', '.secrets.baseline']

  # 2. SAST: Bandit for Python security issues
  - repo: https://github.com/PyCQA/bandit
    rev: 1.7.5
    hooks:
      - id: bandit
        args: ['-r', '.', '-ll']  # fail on medium+ severity

  # 3. Catch common security mistakes
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: detect-private-key       # blocks PEM private keys
      - id: check-added-large-files  # no accidental data file commits
      - id: no-commit-to-branch      # can't commit directly to main
        args: ['--branch', 'main', '--branch', 'production']

  # 4. Dependency vulnerability check
  - repo: local
    hooks:
      - id: safety-check
        name: safety
        entry: safety check --full-report
        language: python
        pass_filenames: false
⚠️
Pre-commit is not enough alone: Developers can bypass local hooks with git commit --no-verify. Always run the same checks in CI as a server-side gate that cannot be bypassed. Pre-commit is for developer convenience and speed — CI is the enforcement layer.
Rule 4 — Secrets management: never hardcode credentials
The most common critical finding in every AppSec audit
▼

Hardcoded credentials are the #1 finding in nearly every security audit. They appear in source code, Dockerfiles, CI/CD configs, and shell scripts. The worst part: deleting a secret from git does not remove it from git history. Once committed, a secret must be treated as compromised and rotated immediately.

❌ These are ALL insecure
# In Python source
API_KEY = "sk-live-abc123xyz"
DB_PASS = "P@ssw0rd!"

# In Dockerfile
ENV DB_PASSWORD=secret123

# In docker-compose.yml
  environment:
    - STRIPE_KEY=sk_live_abc

# In .env committed to git
OPENAI_API_KEY=sk-abc123...
✅ The correct patterns
# Env var at runtime (dev/staging)
import os
API_KEY = os.environ['API_KEY']  # raises if missing — intentional

# HashiCorp Vault (production)
import hvac
client = hvac.Client(url=VAULT_ADDR, token=VAULT_TOKEN)
secret = client.secrets.kv.v2.read_secret(
    path='myapp/prod', mount_point='secret'
)
DB_PASS = secret['data']['data']['db_password']
ℹ️
What to do when a secret is leaked in git: (1) Immediately rotate/revoke the leaked credential — assume it's already been used. (2) Remove from git history with git filter-repo or BFG Repo Cleaner. (3) Force-push the cleaned history. (4) Notify all users of the repo to re-clone. (5) Audit access logs to see if the key was used maliciously. Treating a leaked secret as "probably fine" is how breaches happen.
Phase 4 — Testing
CI/CD security gates: the automated enforcement layer

Every commit to main must pass through a defined set of security checks. These are your security gates — if any gate fails, the pipeline fails and the code cannot be merged or deployed.

GitHub Actions — complete Secure SDLC pipeline
# .github/workflows/security.yml
name: Secure CI Pipeline
on:
  pull_request:
    branches: [main, production]
  push:
    branches: [main]

jobs:
  # ─────────────────────────────────────────
  # GATE 1: Secret Detection (runs first, fast)
  # ─────────────────────────────────────────
  secrets-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # full history — scan all commits, not just latest
      - name: TruffleHog secrets scan
        uses: trufflesecurity/trufflehog@main
        with:
          path: ./
          base: ${{ github.event.repository.default_branch }}
          extra_args: --only-verified  # only report confirmed live secrets

  # ─────────────────────────────────────────
  # GATE 2: SAST — Static analysis
  # ─────────────────────────────────────────
  sast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      - name: Bandit SAST (Python)
        run: |
          pip install bandit[toml]
          bandit -r src/ -c pyproject.toml \
            -f json -o bandit-report.json \
            --exit-zero  # collect results without failing here

      - name: Semgrep SAST (multi-language, OWASP rules)
        uses: semgrep/semgrep-action@v1
        with:
          config: p/owasp-top-ten p/python p/secrets  # OWASP rule packs
          auditOn: push

      - name: Fail on HIGH severity findings
        run: |
          HIGH=$(jq '[.results[] | select(.issue_severity == "HIGH")] | length' bandit-report.json)
          if [ "$HIGH" -gt "0" ]; then
            echo "FAIL: $HIGH high-severity issues found"; exit 1
          fi

  # ─────────────────────────────────────────
  # GATE 3: SCA — Dependency vulnerabilities
  # ─────────────────────────────────────────
  sca:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Safety check (Python deps)
        run: |
          pip install safety
          safety check --full-report --output json \
            --policy-file .safety-policy.yml  # your org's risk acceptance policy

      - name: Snyk Open Source scan
        uses: snyk/actions/python@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          args: --severity-threshold=high --fail-on=upgradable

  # ─────────────────────────────────────────
  # GATE 4: Container image scan (if Dockerfile present)
  # ─────────────────────────────────────────
  container-scan:
    runs-on: ubuntu-latest
    if: hashFiles('Dockerfile') != ''
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .
      - name: Trivy container scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: 'myapp:${{ github.sha }}'
          exit-code: '1'
          severity: 'CRITICAL,HIGH'  # fail on CRITICAL or HIGH CVEs in base image

  # ─────────────────────────────────────────
  # GATE 5: IaC scanning (Terraform/CloudFormation)
  # ─────────────────────────────────────────
  iac-scan:
    runs-on: ubuntu-latest
    if: hashFiles('**/*.tf') != ''
    steps:
      - uses: actions/checkout@v4
      - name: Checkov IaC security scan
        uses: bridgecrewio/checkov-action@master
        with:
          directory: infrastructure/
          framework: terraform
          soft_fail: false   # fail the pipeline on IaC misconfigs
          check: CKV_AWS_*      # all AWS security checks
📌
Gate philosophy — which severity blocks? Define this in your security policy upfront. A common model: CRITICAL findings always block. HIGH findings block in main/production branches, warn on feature branches. MEDIUM and LOW go into a backlog ticket. You need an exception/risk acceptance process for known false positives — otherwise developers start ignoring all findings.
Phase 5 — Deployment
Hardening, IaC security, and immutable infrastructure

You've passed all the code-level gates. Now the question is: is the environment you're deploying into secure?

Infrastructure-as-Code (IaC) security scanning
Your cloud config is code — it needs security review too
▼

Terraform, CloudFormation, Pulumi — these define your cloud infrastructure. A misconfigured S3 bucket in Terraform means a public data exposure. Checkov and tfsec scan IaC files for security misconfigurations before they're applied to real infrastructure.

Terraform — vulnerable vs hardened S3 bucket
# ❌ VULNERABLE: Public S3 bucket
resource "aws_s3_bucket" "data" {
  bucket = "my-company-data"
  acl    = "public-read"                  # Checkov: CKV_AWS_20 — PUBLIC!
}

# ✅ HARDENED: Private, encrypted, versioned S3 bucket
resource "aws_s3_bucket" "data" {
  bucket = "my-company-data"
}
resource "aws_s3_bucket_public_access_block" "data" {
  bucket                  = aws_s3_bucket.data.id
  block_public_acls       = true           # CKV_AWS_53
  block_public_policy     = true           # CKV_AWS_54
  ignore_public_acls      = true           # CKV_AWS_55
  restrict_public_buckets = true           # CKV_AWS_56
}
resource "aws_s3_bucket_server_side_encryption_configuration" "data" {
  bucket = aws_s3_bucket.data.id
  rule { apply_server_side_encryption_by_default { sse_algorithm = "AES256" } }
}
resource "aws_s3_bucket_versioning" "data" {
  bucket = aws_s3_bucket.data.id
  versioning_configuration { status = "Enabled" }
}
Immutable infrastructure: never SSH into production
If you can SSH in, an attacker can too — or worse, an insider can
▼

Immutable infrastructure means you never modify a running server. Instead, you build a new image, test it, and deploy it — then destroy the old server. No SSH access in production. No manual changes. No config drift. This eliminates an entire attack surface: no running SSH daemon means no SSH brute force, no key theft, no interactive attacker sessions.

vs

→

→
Deploy

→

Old containers terminated — no drift, no attack surface

The feedback loop — why Ops feeds back to Requirements: Every security incident in production is a Secure SDLC failure somewhere upstream. Your incident retrospective should trace the root cause back to the SDLC phase where it should have been caught and fix the process — not just the vulnerability.
Real-World Framework
Microsoft SDL vs OWASP SAMM: which model to use

Two major industry frameworks implement Secure SDLC. You'll encounter both — here's how they differ.

FrameworkFull NameOriginBest ForStructure
Microsoft SDL Security Development Lifecycle Microsoft, 2004 (after Windows XP hacking wave) Teams starting Secure SDLC from scratch. Prescriptive and actionable. 12 practices organized by SDLC phase. Each has required and recommended activities.
OWASP SAMM Software Assurance Maturity Model OWASP, open-source Measuring and improving existing security programs. Benchmarking. 5 business functions × 3 security practices × 3 maturity levels = measurable score (0–3).
💡
Interview answer: "Our team follows a Secure SDLC model based on OWASP SAMM for measuring maturity. We currently operate at Level 2 in Secure Build (SAST + SCA in CI) and Level 1 in Threat Assessment (threat modeling on new features). Our roadmap targets Level 3 in Secure Build by Q4." This demonstrates you understand not just what Secure SDLC is, but how to measure and improve it.
Knowledge Check
Test your Secure SDLC knowledge

Questions you will face in AppSec interviews

Q1. A developer commits an AWS access key to a public GitHub repo. It's discovered 3 hours later. List the correct incident response steps in order — and why "deleting the commit" is not enough.
Delete the file, push the commit, and notify GitHub Security
Run git rm, force push, add to .gitignore, rotate key within a week
Immediately revoke/rotate the key → clean git history with git filter-repo → force push → audit CloudTrail for usage → notify affected teams
Make the repo private, delete the commit, no rotation needed if caught fast
The key is: rotate first, always. Git history exists in every clone, fork, and GitHub's own cache. Even if you delete it, it was visible for 3 hours and may have been scraped by automated secret-hunting bots (they scan GitHub in real time). Rotation happens before any cleanup. Then use git filter-repo (not git rm) to rewrite history and force push. Then audit CloudTrail/access logs to see if the key was used during those 3 hours.
Q2. Your Semgrep SAST scan is generating 400 findings per week, but developers are ignoring them all. What is the process failure, and how do you fix it?
Replace Semgrep with a different SAST tool
The tool is not tuned — too many false positives = alert fatigue. Fix: create a baseline, suppress known false positives, focus only on HIGH/CRITICAL, and define a triage SLA so developers know what's expected
Make SAST results mandatory to fix before merge for all severity levels
Remove SAST from CI to reduce developer friction
Alert fatigue is the #1 reason security tooling fails. When everything is flagged, nothing is prioritized. The fix is signal-to-noise ratio: (1) Create a baseline scan of existing code so only new findings are surfaced, (2) Write a suppression policy for confirmed false positives, (3) Auto-fail only on HIGH/CRITICAL — everything else goes to a ticket backlog, (4) Define a sprint-level SLA: e.g., developers triage HIGH findings within 1 sprint. This is a people-and-process problem, not a tool problem.
Q3. At which Secure SDLC phase is it cheapest to fix a "broken access control" vulnerability, and why?
Testing phase — because DAST can detect it automatically
Development phase — because the developer who wrote the bug can fix it immediately
Requirements/Design phase — because the authorization model can be designed correctly from the start, avoiding hundreds of individual code fixes later
Operations phase — because you have real attack data to guide the fix
Broken access control is an architectural vulnerability. If you design a centralized authorization middleware in the design phase, every endpoint gets access control for free. If you skip this, every developer must remember to add an if user.owns(resource) check on every single endpoint — and some will forget. Fixing that in production means auditing 500 endpoints one by one. The IBM 100× cost ratio is exactly about this: design decisions cost minutes to make, production fixes cost weeks.
