Secrets
Management

Secrets — API keys, database passwords, TLS certificates, OAuth tokens, SSH keys — are the skeleton keys to your infrastructure. A single leaked secret can compromise an entire cloud environment in minutes. Effective secrets management means never hardcoding secrets, centralising them in a purpose-built vault, rotating them automatically, and auditing every access. This lesson covers every layer: why secrets leak, the full taxonomy of secrets, HashiCorp Vault in depth, AWS/GCP/Azure native solutions, Kubernetes secrets, and rotation automation.

🟢 Beginner — Understanding Secrets
What secrets are and why they always leak
A secret is any credential that grants access to a system or resource. The history of cloud breaches is largely a history of leaked secrets. Understanding why they leak is the first step to preventing it.
⚠️
The scale of the problem: In 2023 GitGuardian detected over 10 million secrets exposed on GitHub — a 67% increase year-over-year. The average time from a secret being pushed to GitHub to it being discovered and exploited by automated bots is under 1 minute. In 2023 the Mercedes-Benz source code leak was caused by a single GitHub token left in a public repository. The fix costs nothing. The breach costs millions.

The secrets anti-pattern ladder — from worst to best
Where is your organisation on this ladder right now?

Anti-patterns (never do these)

❌ Hardcoded in source code

❌ In .env file committed to git

❌ Copied into Slack/email

❌ In CI/CD pipeline logs

❌ Shared across environments

❌ Never rotated, no expiry

Best practices (work towards these)

✅ Centralised secrets manager (Vault, AWS SM)

✅ Injected at runtime, never baked in

✅ Short-lived credentials (<1hr TTL)

✅ Automated rotation on schedule

✅ Per-service, per-environment isolation

✅ Full audit log of every access

The environment variable middle ground

Environment variables are better than hardcoding but not a complete solution. They are better because: secrets aren't in source code, different values per environment are easy, no code change to update a secret. They are worse than a vault because: no audit trail of who read the secret, no automatic rotation, all env vars visible to all processes in the container, printed by debugging tools like env or printenv.

# NEVER: hardcoded secret
DATABASE_URL = "postgresql://admin:SuperSecret123@db.myapp.com/prod"

# BETTER: environment variable (not in code, but no audit trail)
DATABASE_URL = os.environ["DATABASE_URL"]  # injected by deployment system

# BEST: fetched from secrets manager at runtime (full audit trail, rotation)
import boto3
secret = boto3.client('secretsmanager').get_secret_value(
    SecretId='myapp/prod/database'
)
DATABASE_URL = json.loads(secret['SecretString'])['url']
🟡 Intermediate — Secrets Managers in Depth
The four major secrets management platforms
A secrets manager is a centralised, audited, encrypted store for secrets that controls who can access what, logs every access, and supports automatic rotation. Each platform has different strengths. Know them all.
HashiCorp Vault
AWS Secrets Manager
GCP Secret Manager
Azure Key Vault

HashiCorp Vault is the most powerful and flexible secrets manager available. It is cloud-agnostic (runs anywhere), supports dynamic secrets (generates credentials on demand with TTL), has fine-grained policies (HCL), and provides multiple auth backends (LDAP, Kubernetes, AWS IAM, GitHub). The complexity cost is real: Vault requires operational expertise to deploy and maintain. But for multi-cloud or large organisations it is unmatched.

HashiCorp Vault
# 1. Enable the KV secrets engine (version 2)
$ vault secrets enable -path=secret kv-v2

# 2. Write a secret
$ vault kv put secret/myapp/prod/database \
    url="postgresql://admin:pass@db.myapp.com/prod" \
    max_connections=100

# 3. Read a secret
$ vault kv get -format=json secret/myapp/prod/database
{
  "data": {
    "data": { "url": "postgresql://admin:pass@..." },
    "metadata": { "version": 1, "created_time": "2024-01-15T..." }
  }
}

# 4. Write an access policy (policy.hcl)
# Grant myapp-prod read-only access to its own secrets
path "secret/data/myapp/prod/*" {
  capabilities = ["read"]          # read only, not write or delete
}
path "secret/metadata/myapp/prod/*" {
  capabilities = ["list"]           # list secret names but not values
}
# The myapp-dev policy would only get secret/data/myapp/dev/*
# Complete isolation between environments in one Vault cluster

$ vault policy write myapp-prod policy.hcl

# 5. Enable Kubernetes auth backend
$ vault auth enable kubernetes
$ vault write auth/kubernetes/config \
    kubernetes_host="https://kubernetes.default.svc:443" \
    kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt

# 6. Bind Kubernetes service account to Vault policy
$ vault write auth/kubernetes/role/myapp-prod \
    bound_service_account_names=myapp \
    bound_service_account_namespaces=production \
    policies=myapp-prod \
    ttl=1h                                 # token expires in 1 hour

# 7. Application retrieves secret using service account JWT
import hvac, os

client = hvac.Client(url="http://vault.vault.svc.cluster.local:8200")
client.auth.kubernetes.login(
    role="myapp-prod",
    jwt=open("/var/run/secrets/kubernetes.io/serviceaccount/token").read()
)
secret = client.secrets.kv.v2.read_secret_version(
    path="myapp/prod/database", mount_point="secret"
)
db_url = secret["data"]["data"]["url"]

AWS Secrets Manager is the natural choice for AWS-native infrastructure. It integrates directly with RDS, Redshift, and DocumentDB for automatic rotation. IAM policies control access. CloudTrail logs every API call. Cost: $0.40/secret/month + $0.05/10,000 API calls. For most teams on AWS, this is the right choice over self-hosted Vault.

AWS Secrets Manager
# 1. Store a secret via CLI
$ aws secretsmanager create-secret \
    --name "myapp/prod/database" \
    --description "Production database credentials" \
    --secret-string '{"username":"admin","password":"SuperSecret123","host":"db.prod.myapp.com"}' \
    --tags Key=Environment,Value=production Key=Service,Value=myapp

# 2. IAM policy: allow myapp-role to read only this specific secret
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "secretsmanager:GetSecretValue",
      "secretsmanager:DescribeSecret"
    ],
    "Resource": "arn:aws:secretsmanager:us-east-1:123456789:secret:myapp/prod/*"
    # Wildcard only for myapp/prod/. myapp/dev/* is separate → isolation
  }]
}

# 3. Python application — fetch secret at startup
import boto3, json

def get_secret(secret_name: str) -> dict:
    client = boto3.client('secretsmanager', region_name='us-east-1')
    response = client.get_secret_value(SecretId=secret_name)
    return json.loads(response['SecretString'])

# Cache the result in memory (don't call API on every request!)
# But re-fetch periodically to pick up rotated values
_secret_cache = {}
_cache_ttl = {}

def get_cached_secret(name: str, ttl_seconds: int = 300) -> dict:
    now = time.time()
    if name not in _secret_cache or now - _cache_ttl.get(name, 0) > ttl_seconds:
        _secret_cache[name] = get_secret(name)
        _cache_ttl[name] = now
    return _secret_cache[name]

# 4. Enable automatic rotation for RDS (Lambda rotator)
$ aws secretsmanager rotate-secret \
    --secret-id "myapp/prod/database" \
    --rotation-lambda-arn arn:aws:lambda:us-east-1:123:function:SecretsManagerRDSPostgreSQLRotationSingleUser \
    --rotation-rules AutomaticallyAfterDays=30

# AWS provides pre-built rotation Lambdas for: RDS, Redshift, DocumentDB,
# Elasticache. For custom services: implement the rotation Lambda yourself.

GCP Secret Manager is Google Cloud's fully managed secrets service. It uses Cloud IAM for access control, Cloud Audit Logs for every access event, and supports replication across regions. Integration with GKE via Workload Identity means pods can access secrets without any credential bootstrap problem. Cost: $0.06/active secret version/month.

GCP Secret Manager
# 1. Create a secret
$ gcloud secrets create myapp-prod-database \
    --replication-policy="automatic" \
    --labels=environment=production,service=myapp

# 2. Add a secret version (the actual value)
$ echo -n '{"url":"postgresql://...","password":"..."}' | \
    gcloud secrets versions add myapp-prod-database --data-file=-

# 3. Grant access to a GKE service account via Workload Identity
# First: create a Google Service Account (GSA)
$ gcloud iam service-accounts create myapp-prod \
    --project=my-project

# Grant GSA access to the secret
$ gcloud secrets add-iam-policy-binding myapp-prod-database \
    --member="serviceAccount:myapp-prod@my-project.iam.gserviceaccount.com" \
    --role="roles/secretmanager.secretAccessor"

# Bind GSA to Kubernetes Service Account (KSA)
$ gcloud iam service-accounts add-iam-policy-binding myapp-prod@my-project.iam.gserviceaccount.com \
    --role roles/iam.workloadIdentityUser \
    --member "serviceAccount:my-project.svc.id.goog[production/myapp]"

# Annotate KSA
$ kubectl annotate serviceaccount myapp \
    --namespace production \
    iam.gke.io/gcp-service-account=myapp-prod@my-project.iam.gserviceaccount.com

# 4. Python application — access secret (no key file needed!)
from google.cloud import secretmanager

def get_secret(project_id: str, secret_name: str) -> str:
    client = secretmanager.SecretManagerServiceClient()
    name = f"projects/{project_id}/secrets/{secret_name}/versions/latest"
    response = client.access_secret_version(request={"name": name})
    return response.payload.data.decode("UTF-8")
# Auth is automatic via Workload Identity — no credentials in the pod

Azure Key Vault stores secrets, keys, and certificates in one place. It integrates with Azure Active Directory for RBAC, supports HSM-protected keys, and works natively with Azure Kubernetes Service via the Secrets Store CSI driver. Cost: Standard tier $0.03/10,000 operations.

Azure Key Vault
# 1. Create Key Vault
$ az keyvault create \
    --name myapp-prod-vault \
    --resource-group myapp-rg \
    --location eastus \
    --enable-rbac-authorization true   # use RBAC not vault access policies

# 2. Store a secret
$ az keyvault secret set \
    --vault-name myapp-prod-vault \
    --name "database-url" \
    --value "postgresql://admin:pass@db.prod.myapp.com/prod"

# 3. Grant AKS pod identity access via Managed Identity
# Create user-assigned managed identity
$ az identity create -g myapp-rg -n myapp-prod-identity

# Grant Key Vault Secrets User role to the identity
$ az role assignment create \
    --role "Key Vault Secrets User" \
    --assignee $(az identity show -g myapp-rg -n myapp-prod-identity --query principalId -o tsv) \
    --scope $(az keyvault show -n myapp-prod-vault --query id -o tsv)

# 4. Python application — fetch secret using managed identity
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

credential = DefaultAzureCredential()  # uses managed identity automatically
client = SecretClient(
    vault_url="https://myapp-prod-vault.vault.azure.net/",

db_url = client.get_secret("database-url").value

🔴 Advanced — Dynamic Secrets & Automatic Rotation
From long-lived secrets to ephemeral credentials
The best secret is one that expires before it can be exploited. Dynamic secrets and automatic rotation make leaked credentials worthless. This section covers the patterns that eliminate long-lived credentials entirely.
💡
The goal: zero long-lived secrets. A database password valid for 30 days, if leaked, gives an attacker 30 days. A dynamic secret valid for 1 hour, if leaked, gives an attacker at most 1 hour — and the window closes automatically. The ideal architecture has no long-lived secrets at all: workload identity for cloud resources, dynamic secrets for databases, short-lived JWTs for service-to-service, and cert-manager for TLS. The fallback for things that can't be dynamic: automatic rotation on a short cycle.
Dynamic database credentials with Vault — a credential that barely exists
Vault generates a unique username/password for each request, valid for 1 hour, then auto-revokes it
▼

Vault's database secrets engine connects to your database and generates unique, short-lived credentials on demand. Each application instance gets its own username and password. When the TTL expires, Vault automatically drops the user from the database. There are no long-lived database passwords to rotate or protect.

HashiCorp Vault — dynamic DB secrets
# 1. Enable the database secrets engine
$ vault secrets enable database

# 2. Configure connection to PostgreSQL
$ vault write database/config/myapp-prod \
    plugin_name=postgresql-database-plugin \
    allowed_roles="myapp-readonly,myapp-readwrite" \
    connection_url="postgresql://vault-admin:{{username}}:{{password}}@db.prod.myapp.com:5432/myapp" \
    username="vault-admin" \
    password="vault-admin-password"   # vault-admin has CREATE ROLE privilege

# 3. Define a role (what SQL to run when creating credentials)
$ vault write database/roles/myapp-readwrite \
    db_name=myapp-prod \
    creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}'
      VALID UNTIL '{{expiration}}' IN ROLE app_readwrite;" \
    default_ttl="1h" \      # credential expires in 1 hour
    max_ttl="4h"            # can be renewed up to 4 hours total

# 4. Application requests a credential at startup
$ vault read database/creds/myapp-readwrite
{
  "username": "v-k8s-myapp-abc123-1705000000",   # unique per request
  "password": "A1B-xyz-9876abcd",               # random, not reusable
  "lease_id": "database/creds/myapp-readwrite/xyz",
  "lease_duration": 3600                           # expires in 1 hour
}

# Python application pattern:
import hvac, psycopg2

vault = hvac.Client(url="http://vault:8200", token=os.environ["VAULT_TOKEN"])
creds = vault.secrets.database.generate_credentials(name="myapp-readwrite")

conn = psycopg2.connect(
    host="db.prod.myapp.com",
    dbname="myapp",
    user=creds["data"]["username"],
    password=creds["data"]["password"]
)
# Vault auto-revokes this credential at TTL expiry
# No rotation code needed. No long-lived password to protect.
# If this credential leaks: attacker has <1 hour window. Vault closes it.
Automatic rotation — for secrets that can't be dynamic
AWS Secrets Manager rotation for RDS, and a custom rotation Lambda pattern
▼

Some secrets can't be made dynamic (OAuth client secrets, third-party API keys, TLS certificates). For these, automatic rotation on a schedule is the next best thing. AWS Secrets Manager provides built-in rotation for RDS databases. For anything else, you write a rotation Lambda that follows the four-step rotation pattern.

AWS Lambda — custom secret rotation
# The four-step rotation pattern (AWS standard)
# Vault uses the same pattern internally

import boto3, json, os

sm = boto3.client('secretsmanager')

def lambda_handler(event, context):
    secret_id = event['SecretId']
    token      = event['ClientRequestToken']
    step       = event['Step']

    if   step == 'createSecret':  create_secret(secret_id, token)
    elif step == 'setSecret':     set_secret(secret_id, token)
    elif step == 'testSecret':    test_secret(secret_id, token)
    elif step == 'finishSecret':  finish_secret(secret_id, token)

def create_secret(secret_id, token):
    # Step 1: Generate a new secret value and store as AWSPENDING version
    try:
        sm.get_secret_value(SecretId=secret_id, VersionStage="AWSPENDING")
        return  # already created this rotation cycle
    except sm.exceptions.ResourceNotFoundException:
        pass
    new_password = generate_secure_password(32)
    sm.put_secret_value(
        SecretId=secret_id,
        ClientRequestToken=token,
        SecretString=json.dumps({"password": new_password}),
        VersionStages=["AWSPENDING"]         # staged, not yet current
    )

def set_secret(secret_id, token):
    # Step 2: Apply the new secret to the actual service (e.g., update DB user)
    pending = json.loads(sm.get_secret_value(
        SecretId=secret_id, VersionStage="AWSPENDING")['SecretString'])
    update_third_party_api_key(pending['password'])   # call external API

def test_secret(secret_id, token):
    # Step 3: Verify the new secret actually works before promoting it
    pending = json.loads(sm.get_secret_value(
        SecretId=secret_id, VersionStage="AWSPENDING")['SecretString'])
    verify_connection_works(pending['password'])      # FAIL HERE if broken

def finish_secret(secret_id, token):
    # Step 4: Promote AWSPENDING to AWSCURRENT, demote old to AWSPREVIOUS
    metadata = sm.describe_secret(SecretId=secret_id)
    current_version = [
        v for v, stages in metadata['VersionIdsToStages'].items()
        if 'AWSCURRENT' in stages
    ][0]
    sm.update_secret_version_stage(
        SecretId=secret_id, VersionStage="AWSCURRENT",
        MoveToVersionId=token, RemoveFromVersionId=current_version
    )
# Application picks up the new value on next cache refresh (TTL ~300s)
🔴 Advanced — Kubernetes Secrets
Kubernetes secrets — why the default is insecure and how to fix it
Kubernetes Secrets are base64-encoded, not encrypted. By default they are stored in etcd in plaintext. Anyone with etcd access reads all secrets. Here is the correct architecture.
⚠️
Kubernetes Secret is not secret by default: kubectl get secret myapp-db -o yaml shows the "secret" base64-encoded. base64 -d decodes it to plaintext. Any user with kubectl access to the namespace reads the secret instantly. etcd stores it unencrypted unless you explicitly enable encryption at rest. Use External Secrets Operator or Vault Agent Injector to sync from a real secrets manager instead.
External Secrets Operator — sync from real secrets managers into K8s
The recommended pattern for Kubernetes: secrets live in AWS/GCP/Vault, ESO syncs them into K8s Secrets automatically
▼

External Secrets Operator (ESO) is a Kubernetes operator that reads secrets from external secrets managers (AWS Secrets Manager, GCP Secret Manager, Vault, etc.) and creates Kubernetes Secrets from them. Your applications use standard Kubernetes Secrets, but the source of truth is always the external secrets manager. ESO re-syncs on a schedule, so rotated secrets automatically appear in K8s.

Kubernetes / External Secrets Operator
# 1. Install ESO
$ helm repo add external-secrets https://charts.external-secrets.io
$ helm install external-secrets external-secrets/external-secrets \
    -n external-secrets --create-namespace

# 2. Create a SecretStore (connects ESO to AWS Secrets Manager)
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secretsmanager
  namespace: production
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        jwt:                              # use IRSA (no keys needed!)
          serviceAccountRef:
            name: external-secrets-sa

# 3. Create an ExternalSecret (which AWS secret to sync, and how)
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: myapp-database
  namespace: production
spec:
  refreshInterval: 5m              # re-sync every 5 minutes
  secretStoreRef:
    name: aws-secretsmanager
    kind: SecretStore
  target:
    name: myapp-database           # name of the K8s Secret created
    creationPolicy: Owner
  data:
    - secretKey: DATABASE_URL      # key in K8s Secret
      remoteRef:
        key: myapp/prod/database   # path in AWS Secrets Manager
        property: url              # field in the JSON secret
    - secretKey: DATABASE_PASSWORD
      remoteRef:
        key: myapp/prod/database
        property: password

# 4. Application pod uses the synced K8s Secret normally
spec:
  containers:
    - name: myapp
      env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: myapp-database   # the K8s Secret created by ESO
              key: DATABASE_URL
# When AWS Secrets Manager rotates the secret, ESO re-syncs within 5 minutes
# K8s Secret is updated, pod picks up new value on restart or via reloader
Vault Agent Sidecar Injector — secrets as files, not env vars
Inject secrets directly into the pod filesystem without ever creating a K8s Secret
▼

The Vault Agent Injector adds a sidecar container to your pod that authenticates to Vault using the pod's service account, fetches secrets, and writes them to a shared in-memory volume (tmpfs). Your application reads secrets from files rather than environment variables. When Vault rotates a secret, the agent writes the new value to the file automatically — no pod restart needed for some application frameworks.

Kubernetes — Vault Agent injection via annotations
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  template:
    metadata:
      annotations:
        # These annotations trigger the Vault Agent Injector webhook
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "myapp-prod"

        # Inject database secret as a file at /vault/secrets/database
        vault.hashicorp.com/agent-inject-secret-database: "secret/data/myapp/prod/database"
        vault.hashicorp.com/agent-inject-template-database: |
          {{- with secret "secret/data/myapp/prod/database" -}}
          DATABASE_URL={{ .Data.data.url }}
          DATABASE_PASSWORD={{ .Data.data.password }}
          {{- end }}

        # Agent template renders secret as a config file your app reads
        vault.hashicorp.com/secret-volume-path: "/vault/secrets"
    spec:
      serviceAccountName: myapp     # must match bound_service_account_names in Vault
      containers:
        - name: myapp
          image: myapp:latest
          # Application reads /vault/secrets/database (tmpfs file)
          # File is never in environment, never in etcd, never in K8s Secret
Enabling etcd encryption at rest for Kubernetes Secrets
If you must use native K8s Secrets, encrypt them in etcd with an envelope encryption key
▼
Kubernetes encryption config
# /etc/kubernetes/encryption-config.yaml (on control plane nodes)
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      # Use AWS KMS provider (recommended for EKS)
      - kms:
          name: aws-kms
          endpoint: unix:///var/run/kmsplugin/socket.sock
          cachesize: 1000
          timeout: 3s
      # Fallback: AES-CBC with a 32-byte key (less preferred)
      - aescbc:
          keys:
            - name: key1
              secret: <base64-encoded-32-byte-key>
      # Identity: plaintext (fallback for reading old unencrypted data)
      - identity: {}

🔴 Advanced — The Zero-Secrets Architecture
Eliminating secrets entirely with workload identity
The best secret is no secret. Workload identity allows cloud services to grant access to workloads based on their cryptographic identity rather than a shared credential. No key to rotate, no key to leak.
AWS IRSA — IAM Roles for Service Accounts
EKS pods access AWS services without any AWS credentials in the pod
▼

IRSA (IAM Roles for Service Accounts) lets Kubernetes pods assume an IAM role without any AWS Access Key or Secret Key in the pod. The pod's service account token is exchanged for temporary AWS credentials by the AWS STS service. The pod has full AWS SDK access with no credentials to manage, rotate, or protect.

# RDS IAM authentication — no database password ever
# The database password is replaced with a 15-minute token from AWS STS

import boto3, psycopg2

def get_rds_connection(host: str, dbname: str, user: str, region: str):
    # Generate token (valid 15 minutes, no password needed)
    token = boto3.client('rds', region_name=region).generate_db_auth_token(
        DBHostname=host, Port=5432, DBUsername=user
    )
    return psycopg2.connect(
        host=host, dbname=dbname, user=user,
        password=token,                       # the IAM token IS the password
        sslmode='require',
        sslrootcert='rds-ca-cert.pem'
    )
# No database password in code, config, environment, or Secrets Manager
# Token is valid 15 minutes, unique per request, non-reusable
Knowledge Check
Secrets management interview questions
These questions appear in DevSecOps, cloud security, and AppSec engineer interviews.
Q1. A developer argues: "We store all our secrets in environment variables, so we're fine. They're not in the code." What are the specific security gaps with this approach, and what should replace it?
Environment variables are a perfectly acceptable secrets management solution
Env vars are better than hardcoding but have real gaps: (1) No audit trail — you can't see who read the secret or when. (2) Visible to all processes in the container, including spawned subprocesses. (3) Printed by debugging tools like printenv, docker inspect, or crash dumps. (4) No automatic rotation. (5) Typically set by humans in CI/CD settings, creating another exposure surface. Replace with a secrets manager (AWS Secrets Manager, Vault) that provides audit logging, fine-grained access control, and automatic rotation.
The only problem with env vars is that they can be read by other processes, everything else is fine
Env vars are insecure only if they contain passwords. API keys and tokens are fine as env vars.
Environment variables are the minimum acceptable baseline — they avoid the worst anti-pattern (hardcoding) but solve very few of the actual secrets management problems. The full list of gaps: no audit trail of who accessed the secret, visible to all processes in the container via /proc/self/environ (readable if container is compromised), printed in many debugging contexts, no rotation support, typically set manually in CI/CD dashboards which is itself an exposure point, and they travel in process memory which can appear in crash dumps and heap dumps. A dedicated secrets manager addresses all of these: encrypted storage, per-request audit logging, IAM-based access control, automatic rotation, and API-based access that leaves no traces in the process environment.
Q2. Your team uses Kubernetes. A junior engineer creates a Secret with kubectl to store a database password. Why is this not a complete security solution, and what is the correct architecture?
Kubernetes Secrets are secure — they are encrypted at rest by default
Kubernetes Secrets are base64-encoded, not encrypted, by default. Anyone with kubectl access to the namespace reads the secret instantly with kubectl get secret -o yaml followed by base64 -d. etcd stores them in plaintext unless encryption at rest is explicitly configured. The correct architecture: store the real secret in AWS Secrets Manager or Vault, use External Secrets Operator to sync it into K8s as a Secret, enable etcd encryption at rest with KMS. Better yet: use IRSA or Vault dynamic secrets to eliminate the long-lived secret entirely.
K8s Secrets are fine if RBAC prevents developers from reading them
The only risk is that the secret is visible in the pod's environment variables
This is one of the most common Kubernetes security misconceptions. Base64 encoding is NOT encryption — it is reversible with one command. The raw etcd data is plaintext unless you explicitly configure an EncryptionConfiguration with a KMS provider. Even with encryption at rest: any user with kubectl get secret permission in that namespace reads the secret. The correct layered approach: (1) Enable etcd encryption at rest using KMS (stops etcd compromise from leaking secrets). (2) Use External Secrets Operator to keep the source of truth in a proper secrets manager, not etcd. (3) For AWS workloads: use IRSA so pods never need long-lived credentials at all. (4) Restrict kubectl permissions to secrets using RBAC (least privilege). Defence in depth: all four layers are needed, not just one.
Q3. What is the advantage of dynamic secrets (like Vault's database secrets engine) over rotating static secrets? Give a concrete attack scenario where dynamic secrets provide better protection.
Dynamic secrets are just a way to automate rotation. The security benefit is the same.
Dynamic secrets are only useful when you have many services needing the same database.
Dynamic secrets have TTLs of minutes to hours. Static secrets with 30-day rotation have a 30-day exposure window. Scenario: attacker compromises a container and exfiltrates its database credential. With static rotation (30-day cycle): attacker has 30 days of database access before the credential rotates. With dynamic secrets (1-hour TTL): the credential expires in under 1 hour automatically. Additionally, dynamic secrets are unique per lease — each pod gets a different username/password — so you can pinpoint exactly which pod's credential was used in an attack and revoke only that lease without affecting other pods.
Dynamic secrets are more expensive and only worth it for compliance purposes.
The key distinction is the exposure window. Static secrets with 30-day rotation: if leaked, an attacker has up to 30 days of access. Dynamic secrets with 1-hour TTL: if leaked, the attacker has at most 1 hour, and the window closes automatically without any incident response action. The additional benefit of uniqueness: every Vault lease generates a unique database username. If you see unexpected queries from username v-k8s-myapp-abc123-1705012345, you know exactly which pod's credential was compromised, when it was issued, and when it expires. You can immediately revoke just that lease with vault lease revoke, terminating the attacker's access without affecting any other service. This granular blast radius control is impossible with shared static credentials.

Model Answer

Secret 1 — Database password (hardcoded in settings.py):
Approach: Replace with RDS IAM authentication (zero-secret) or Vault dynamic secrets. If neither is immediately feasible: AWS Secrets Manager with 30-day rotation Lambda as the interim step.
Why RDS IAM auth is best: eliminates the password entirely. The boto3 RDS client generates a 15-minute token that is used as the password. Nothing to store, nothing to rotate, nothing to leak.
Config: Enable IAM authentication on the RDS instance. Create a DB user that authenticates via IAM. In the application: generate token via boto3.client('rds').generate_db_auth_token(). Connect using the token as the password. Ensure the pod's IAM role (via IRSA) has the rds-db:connect permission.

Secret 2 — Stripe API key in ConfigMap:
Approach: Two critical fixes needed. (1) ConfigMaps are not encrypted — move to AWS Secrets Manager immediately. (2) Never store secrets as GitHub Actions secrets that get written to ConfigMaps — this defeats the purpose of a secrets manager.
Why: ConfigMaps are plaintext in etcd. Any kubectl user can read them. GitHub Actions secrets are also visible to workflow logs and maintainers.
Config: Store in AWS Secrets Manager at path myapp/prod/stripe. Use External Secrets Operator to sync into a K8s Secret (not ConfigMap). Pod references the K8s Secret via secretKeyRef. Enable etcd encryption at rest. Set 90-day rotation reminder (Stripe supports key rotation via their dashboard).

Secret 3 — AWS S3 access (long-lived IAM keys from 2021):
Approach: Replace with IRSA immediately. This is the highest priority fix. AWS access keys from 2021 are a critical risk: they are long-lived, may have overly broad permissions, and if leaked give permanent access until manually revoked.
Why: IRSA gives the pod temporary credentials (15-minute TTL) scoped to exactly the permissions it needs (e.g., s3:GetObject and s3:PutObject on a specific bucket only). No Access Key ID or Secret Access Key exists anywhere.
Config: Create OIDC provider for EKS cluster. Create IAM role with S3 policy scoped to the specific bucket. Create K8s ServiceAccount annotated with the IAM role ARN. Assign ServiceAccount to the deployment. Remove AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY env vars. boto3 will use IRSA automatically.

Secret 4 — JWT signing key in K8s Secret without etcd encryption:
Approach: Two actions needed. (1) Enable etcd encryption at rest using AWS KMS immediately. (2) Move the source of truth to AWS Secrets Manager, synced via ESO.
Why: Without etcd encryption, anyone with etcd access (cluster admin, cloud provider support) reads the JWT signing key and can forge any user's session token, including admin tokens. This is a full application takeover vector.
Config: Enable EKS Secrets encryption: eksctl create cluster --encrypt-secrets-with-kms-key arn:aws:kms:... Or for existing cluster: enable via EKS console under Secrets encryption. Store DJANGO_SECRET_KEY in AWS Secrets Manager. Use ESO to sync to a K8s Secret. The K8s Secret is now encrypted in etcd by KMS. Re-encrypt existing secrets after enabling: kubectl get secrets --all-namespaces -o json pipe to kubectl replace.

Secret 5 — Shared bearer token across 8 microservices:
Approach: Replace with mTLS via a service mesh (Istio or Linkerd). This eliminates the shared secret entirely and provides cryptographically verified service identity.
Why: A single shared token is a catastrophic single point of failure. If any of the 8 services is compromised, the attacker can impersonate all services. There is no way to tell which service made a request. Revoking the token requires updating all 8 services simultaneously.
Config: Install Istio (istioctl install --set profile=production). Enable automatic sidecar injection on all service namespaces. Istio automatically issues SPIFFE X.509 certificates to each pod via SPIRE. Enable STRICT mTLS mode: PeerAuthentication policy with mtls.mode: STRICT. Services now authenticate each other with short-lived certificates (24-hour TTL, auto-rotated). No shared token. Each service has a unique cryptographic identity. If service A is compromised, only service A's certificate is revoked.
