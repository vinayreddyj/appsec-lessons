Security
Architecture

Security architecture is the discipline of designing systems so that they are secure by default — not patched into security later. The choices made at the architecture level determine what is possible and what is impossible for an attacker: you cannot inject authentication into a system that was never designed for it, and you cannot bolt defence-in-depth onto a flat network. This lesson covers the foundational principles, the architectural patterns that implement them, the major modern paradigms (Zero Trust, defence-in-depth, least privilege at system scale), and how to apply them when reviewing or designing real systems.

🟢 Beginner — The 8 Principles of Secure Design
The foundations every secure system is built on
These principles were first articulated by Jerome Saltzer and Michael Schroeder in 1975. They remain the most important security design guidance ever written. Every security architecture decision traces back to one or more of these.
01
Economy of Mechanism
Keep security mechanisms as simple as possible. Complex systems have complex failure modes. A complicated authorisation system has more places to introduce a bug than a simple one.
Simple RBAC beats complex ABAC unless ABAC is genuinely needed
02
Fail-Safe Defaults
Default to denial. Access requires explicit permission grants, not absence of denial. A misconfigured system should deny access, not grant it.
IAM: default deny all, allowlist specific actions
03
Complete Mediation
Every access to every resource must be checked against the access control policy. No caching of permission decisions that can become stale. No side doors.
Auth check on every API call, not just on login
04
Open Design
Security should not depend on secrecy of the mechanism. Assume attackers know how the system works. Only secrets should be secret (keys, passwords).
AES-256 is secure even though everyone knows how AES works
05
Separation of Privilege
Require more than one condition to grant access or perform a sensitive operation. No single key unlocks everything. Two-person integrity for critical actions.
MFA: password AND token both required
06
Least Privilege
Every component, user, and process should operate with the minimum permissions needed. Excess privilege is attack surface waiting to be exploited.
DB user with SELECT only, not full schema owner
07
Least Common Mechanism
Minimise shared mechanisms between users or components. Shared state is a potential covert channel; shared services are a single point of compromise.
Per-tenant databases vs shared schema with row-level security
08
Psychological Acceptability
Security mechanisms must not make the system harder to use than the insecure alternative. If security is too burdensome, users route around it.
SSO is more usable than 20 separate passwords; users adopt it
Defence-in-depth — why one control is never enough
The Swiss cheese model applied to security architecture
▼

Defence-in-depth (DiD) is the principle that security controls should be layered so that the failure of any single control does not result in a full compromise. James Reason's Swiss cheese model applies: each security layer has holes (vulnerabilities, misconfigurations, human error), but the holes in different layers don't align. An attacker must penetrate every layer simultaneously.

# Request to a financial API — defence-in-depth layers
#
# Layer 1: Network perimeter (WAF, DDoS protection)
#   Blocks: known bad IPs, XSS/SQLi in parameters, volumetric attacks
#   Bypassed by: unknown attack patterns, HTTPS payloads WAF can't inspect
#
# Layer 2: API Gateway (rate limiting, auth token validation)
#   Blocks: unauthenticated requests, brute force, expired tokens
#   Bypassed by: stolen valid tokens, token confusion attacks
#
# Layer 3: Application authentication & authorisation (RBAC)
#   Blocks: privilege escalation, BOLA, function-level access control
#   Bypassed by: logic errors in permission checks
#
# Layer 4: Input validation & parameterised queries
#   Blocks: SQL injection, command injection, XSS
#   Bypassed by: edge cases in validation logic
#
# Layer 5: Database access (least-privilege DB user)
#   Blocks: reading tables the app doesn't need, writing audit logs
#   Bypassed by: SQL injection that succeeds
#
# Layer 6: Data encryption at rest
#   Blocks: direct disk/backup access to read PII
#   Bypassed by: application-level access (already authenticated)
#
# Layer 7: Audit logging & anomaly detection (SIEM)
#   Detects: unusual data access patterns, failed auth spikes
#   Every layer's failure is still detected and alertable
#
# An attacker who bypasses Layer 2 still hits Layers 3-6
# Layer 7 fires on any successful bypass of the others
⚠️
Common DiD mistake: Treating the same control at different levels as "defence-in-depth." Two input validation checks in the same codebase is not DiD — they share the same failure mode (a bug in the validation logic). True DiD requires controls at different architectural layers that fail independently.

🟡 Intermediate — Security Architecture Patterns
The patterns that implement secure design principles
Architecture patterns are reusable solutions to recurring security design problems. Each pattern below encodes one or more of the foundational principles into a concrete, implementable design.
Zero Trust Architecture
Never trust, always verify • BeyondCorp • NIST SP 800-207
Modern Paradigm
What it is and why the old model failed

Traditional security assumed a trusted internal network. "Inside the firewall" meant trusted; "outside" meant untrusted. Zero Trust assumes there is no trusted network. Every request, from anywhere, must be authenticated, authorised, and verified, regardless of whether it originated inside or outside the corporate perimeter. The SolarWinds breach (2020) demonstrated exactly why: attackers inside the trusted network moved laterally for months because east-west traffic within the "trusted" perimeter was not inspected or controlled.

# Zero Trust pillars and what each requires in practice

# Pillar 1: Verify explicitly
# Every request must prove identity. "Inside the network" is NOT identity.
# Implementation: mTLS for service-to-service, JWT for user-to-service,
# SPIFFE/SPIRE for workload identity, MFA for all human access

# Pillar 2: Use least privileged access
# Access is granted just-in-time and just-enough, not permanently.
# Implementation: short-lived tokens (15min), dynamic secrets,
# IRSA for cloud resources, role binding by workload not by host

# Pillar 3: Assume breach
# Design assuming attackers are already in the network.
# Implementation: network segmentation so lateral movement is blocked,
# encryption of all east-west traffic, logging all internal API calls,
# blast radius minimisation via micro-segmentation

# BeyondCorp implementation (Google's Zero Trust):
# - Corporate laptop connects from home or coffee shop
# - Access proxy checks: device health, user identity, MFA, context
# - No VPN needed; access is granted per-application, not per-network
# - Device certificate + user identity = access decision
# - Lateral movement from compromised device is limited to that device's
#   approved application list, not the entire internal network

# Istio service mesh for Zero Trust service-to-service:
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: production
spec:
  mtls:
    mode: STRICT   # reject any non-mTLS traffic between services
# Every service gets a SPIFFE X.509 certificate from SPIRE
# Services verify each other's certificates on every request
# Compromised service A cannot masquerade as service B
Authentication Architecture — designing identity into the system
OAuth 2.0 / OIDC • JWT patterns • Service-to-service auth • MFA
Foundation
The authentication architecture decision tree

Authentication architecture decisions are among the highest-impact security choices made at design time. Getting them wrong is expensive to fix. The key decisions: what grants access (factor types), how identity is conveyed to services (token format and validation), and what happens when authentication is compromised (session revocation).

# User → Application authentication: OAuth 2.0 / OIDC
#
# PKCE flow (recommended for SPAs and mobile apps):
# 1. App generates code_verifier (random, 43-128 chars)
# 2. App sends code_challenge = SHA256(code_verifier) to auth server
# 3. User authenticates with IdP (SSO, MFA, etc.)
# 4. Auth server returns authorization_code
# 5. App exchanges code + code_verifier for tokens
# Prevents auth code interception attacks

# Token types and their security properties:
#
# Access token (JWT, short TTL: 15min)
# - Sent on every API request: Authorization: Bearer TOKEN
# - Stateless: API validates signature, no DB lookup
# - SHORT TTL: if stolen, attacker has <15 minutes
# - Validated: issuer, audience, expiry, signature
#
# Refresh token (opaque, long TTL: 7-30 days)
# - Stored securely (httpOnly cookie, not localStorage)
# - Used only to get new access tokens
# - Can be revoked server-side (DB lookup required)
# - Rotation: new refresh token issued on each use

# JWT validation checklist (every API that accepts JWTs):
import jwt from 'jsonwebtoken'

function validateToken(token, publicKey) {
  return jwt.verify(token, publicKey, {
    algorithms: ['RS256'],        // only RS256, never 'none' or HS256 with known key
    issuer: 'https://auth.myapp.com',   // reject tokens from other issuers
    audience: 'https://api.myapp.com',  // reject tokens meant for other services
    clockTolerance: 30                 // 30 seconds clock skew tolerance
  })
  // Never use: jwt.decode() (no signature verification!)
  // Never accept: algorithm: 'none'
  // Never use symmetric key (HS256) if key is shared with untrusted parties
}

# Service-to-service authentication patterns:
#
# Option A: mTLS (Mutual TLS) via service mesh
# - Best for Kubernetes: Istio/Linkerd auto-issues certs
# - Zero secrets to manage: certs rotate automatically
# - Cryptographic identity: impossible to spoof without cert
#
# Option B: JWT bearer token with short TTL
# - Service A generates signed JWT, presents to Service B
# - Service B validates: correct issuer, audience = "service-b", not expired
# - Good for: multi-cloud, heterogeneous infrastructure
#
# Option C: IRSA / Workload Identity (cloud-native)
# - No secrets: cloud IAM handles identity via OIDC
# - Best for: services calling cloud APIs (S3, Secrets Manager)
API Gateway Security Pattern
Central enforcement point • Rate limiting • Auth delegation • Traffic inspection
Infrastructure
The API gateway as a security chokepoint

An API gateway is the single entry point for all external API traffic. Centralising security enforcement here means: every downstream service can assume requests are authenticated, rate-limited, and logged. Each microservice does not need to re-implement these controls. The gateway pattern also enables consistent policy enforcement across all services as policies change.

# API Gateway security responsibilities (Kong/AWS API Gateway/Nginx):
#
# ── Authentication & authorisation ──────────────────────────────
# Validate JWT/OAuth tokens before forwarding to services
# Services receive pre-validated, trusted headers
# X-Authenticated-User: user123 (set by gateway after validation)
# Services trust this header ONLY because it came from gateway
# (Internal traffic must be restricted to gateway source only)
#
# ── Rate limiting ────────────────────────────────────────────────
# Per-user: 100 requests/minute on authenticated endpoints
# Per-IP: 20 requests/minute on public endpoints (before auth)
# Per-endpoint: custom limits for sensitive operations (login: 5/min)
# Response: 429 Too Many Requests with Retry-After header
#
# ── TLS termination ──────────────────────────────────────────────
# HTTPS terminates at gateway. Services communicate over HTTP internally
# OR: re-encrypt for end-to-end (required for high-security environments)
#
# ── Request/response transformation ─────────────────────────────
# Strip internal headers before forwarding to services
# Add correlation IDs for request tracing
# Remove sensitive response headers (server version, internal paths)

# Kong Gateway security plugin configuration:
plugins:
  - name: jwt
    config:
      key_claim_name: kid
      claims_to_verify: [exp, iss]
      allowed_algorithms: [RS256]

  - name: rate-limiting
    config:
      minute: 100
      policy: redis         # distributed rate limit across gateway instances
      error_message: "Rate limit exceeded"

  - name: cors
    config:
      origins: ["https://app.mycompany.com"]
      methods: [GET, POST, PUT, DELETE]
      allowed_headers: [Authorization, Content-Type]
      credentials: true

# CRITICAL: Backend services must only accept traffic from the gateway
# Not from the internet. Enforce via network policy:
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-gateway-only
spec:
  podSelector: { matchLabels: { app: myservice } }
  ingress:
    - from:
        - podSelector: { matchLabels: { app: api-gateway } }
  # If bypassing the gateway is possible, all its security controls are bypassed too
Microservices Security Architecture
Service mesh • mTLS • SPIFFE/SPIRE • Sidecar pattern
Distributed
Security challenges unique to microservices

Microservices break a monolith into many small services that communicate over a network. This creates security challenges that don't exist in a monolith: every service-to-service call is a potential attack vector, network traffic between services is often unencrypted by default, and each service must independently enforce authorisation. The service mesh pattern solves this at the infrastructure layer rather than requiring every service to implement it.

# Security problem: Service A calls Service B over HTTP (unencrypted)
# Service B has no way to verify the caller is actually Service A
http://order-service:8080/api/orders  # ← plaintext, no mutual auth

# Solution: Istio service mesh with mTLS and AuthorizationPolicy

# 1. mTLS enforced cluster-wide
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata: { name: default, namespace: production }
spec:
  mtls: { mode: STRICT }  # reject any non-mTLS request

# 2. AuthorizationPolicy: service-to-service allow rules
# Order service can ONLY be called by gateway and payment service
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata: { name: order-service-policy, namespace: production }
spec:
  selector: { matchLabels: { app: order-service } }
  action: ALLOW
  rules:
    - from:
        - source:
            principals:            # SPIFFE identity of the caller
              - "cluster.local/ns/production/sa/api-gateway"
              - "cluster.local/ns/production/sa/payment-service"
      to:
        - operation: { methods: ["GET","POST"], paths: ["/api/orders*"] }
# User-service cannot call Order-service even inside the cluster
# Compromised user-service cannot reach order data

# 3. JWT end-user authentication validation at the service layer
apiVersion: security.istio.io/v1beta1
kind: RequestAuthentication
metadata: { name: jwt-validation, namespace: production }
spec:
  selector: { matchLabels: { app: order-service } }
  jwtRules:
    - issuer: "https://auth.myapp.com"
      jwksUri: "https://auth.myapp.com/.well-known/jwks.json"
      audiences: ["https://api.myapp.com"]
Encryption Architecture — data in transit and at rest
TLS 1.3 • Envelope encryption • Key management • Field-level encryption
Data Protection 
# ── Data in transit ─────────────────────────────────────────────
# Minimum: TLS 1.2. Recommended: TLS 1.3 everywhere.
# TLS 1.3 improvements over 1.2:
# - 1-RTT handshake (vs 2-RTT): 50% faster connection setup
# - Perfect Forward Secrecy mandatory (ECDHE only)
# - Eliminated weak cipher suites (RC4, DES, CBC with MAC-then-encrypt)
# - Encrypted handshake (certificate hidden from passive observers)

# Nginx TLS configuration (production-grade):
server {
    ssl_protocols TLSv1.3 TLSv1.2;        # drop 1.0 and 1.1
    ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;         # TLS 1.3: client chooses
    ssl_session_timeout 1d;
    ssl_session_cache shared:SSL:10m;
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload";
    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options DENY;
}

# ── Envelope encryption (data at rest) ──────────────────────────
# Data Encryption Key (DEK): encrypts the actual data. AES-256-GCM.
# Key Encryption Key (KEK): encrypts the DEK. Stored in KMS (AWS/GCP/Azure).
# The DEK is stored alongside the data, encrypted with the KEK.
# Rotating the KEK re-encrypts only the small DEK, not all the data.

# AWS envelope encryption:
import boto3, os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

kms = boto3.client('kms')

def encrypt_sensitive_field(plaintext: bytes, kms_key_id: str) -> dict:
    # 1. Generate a data key (DEK) via KMS
    response = kms.generate_data_key(
        KeyId=kms_key_id, KeySpec='AES_256'
    )
    plaintext_dek  = response['Plaintext']   # ephemeral, use then discard
    encrypted_dek  = response['CiphertextBlob']  # safe to store alongside data

    # 2. Encrypt the actual data with the DEK
    nonce = os.urandom(12)
    ciphertext = AESGCM(plaintext_dek).encrypt(nonce, plaintext, None)

    # 3. Store ciphertext + nonce + encrypted DEK together
    return {'ct': ciphertext, 'nonce': nonce, 'edek': encrypted_dek}

# ── Field-level encryption ───────────────────────────────────────
# Use when specific fields (SSN, card PAN, health data) need
# stricter access controls than the rest of the record.
# Only the application components that legitimately need the data
# have the key to decrypt those specific fields.
# The reporting database can see all other fields but not PII.

🟡 Intermediate — What Not to Do
Security architecture anti-patterns
These design choices appear repeatedly in systems that suffer significant breaches. Recognising them in architecture reviews is as important as knowing the correct patterns.
Perimeter Trust
Implicit Trust
Security Through Obscurity
Bolted-on Security
Shared Credentials

The problem: "We have a firewall, so everything inside is trusted." East-west traffic (between internal services) is treated as safe and not authenticated or encrypted. A single compromised service can reach every other service.

# Anti-pattern: flat internal network, services trust each other
service_a → http://service_b/internal/admin  # no auth, just "internal"
database  ← any service can connect          # no service account isolation
vault     ← shared token for all services    # any service reads any secret

# Real consequence: SolarWinds (2020)
# Attackers with a foothold moved laterally for months
# because east-west traffic was fully trusted inside the perimeter

# Fix: Zero Trust, mTLS, AuthorizationPolicy per service pair
service_a → mTLS + SPIFFE cert → service_b   # cryptographic identity
database  ← per-service credentials          # service_a reads only its tables
vault     ← per-service policy               # service_a reads only its secrets

The problem: Services trust request metadata without verification. "The gateway sets X-User-ID and services trust it." But if services are accessible without going through the gateway, or if an attacker can forge the header, the trust chain breaks.

# Anti-pattern: trusting headers without verification
def get_current_user(request):
    user_id = request.headers.get('X-User-ID')    # ← attacker controls this
    return User.objects.get(id=user_id)             # ← any user ID works

# Fix 1: Only accept requests from known gateway (network policy)
# Fix 2: Use signed JWT (gateway signs, service verifies signature)
def get_current_user_secure(request):
    token = request.headers.get('Authorization', '').removeprefix('Bearer ')
    payload = jwt.decode(token, PUBLIC_KEY, algorithms=['RS256'],
                        audience='https://api.myapp.com')
    return User.objects.get(id=payload['sub'])

The problem: "We don't publish the admin endpoint URL, so attackers won't find it." Hidden endpoints, obfuscated API keys in client-side JavaScript, and "secret" internal URLs are not security controls. Attackers enumerate, decompile, and search leaked source.

# Anti-pattern: relying on obscurity
GET /api/v1/internal_admin_xyz123/users  # "secret" endpoint
const API_KEY = "sk_live_abc123"         # hardcoded in JS bundle
                                         # will be found by: grep, jsbeautifier, Sourcemapper

# Real example: Firebase misconfigurations where API keys were in
# client JS but database rules were "no one would guess the path"

# Fix: design assuming the attacker knows the full URL and structure
POST /api/v1/admin/users                 # clearly named
Authorization: Bearer ADMIN_JWT          # authentication is the protection
                                         # not secrecy of the URL

The problem: Security added after the design is complete. Authentication added to an API that was designed without it. Encryption added to a database schema that stores data in a way that makes selective decryption impossible. Audit logging added to a system where the data model doesn't record which user performed which action.

# Anti-pattern: authentication bolted onto a system post-design
# Original design had no user concept at all:
GET /orders        → returns ALL orders from the DB
POST /orders       → creates order with no owner field

# After "bolting on" auth:
GET /orders        → now requires JWT... but still returns ALL orders
                   → "authenticated" but still has BOLA/data exposure
                   → orders table has no user_id column to filter by

# Fix: design the data model with ownership from the start
orders.user_id                  → every order belongs to a user
GET /orders → filter by JWT sub → user sees only their orders

# Security must be designed in, not added on top

The problem: Multiple services share the same database credentials, API key, or service account. When one service is compromised, all shared credentials must be rotated simultaneously — often requiring a coordinated production deployment across all consumers.

# Anti-pattern: shared credentials
DB_PASSWORD=shared_prod_password  # used by 8 different services
API_KEY=stripe_key_abc             # used by order-service AND reporting-service
VAULT_TOKEN=hvs.abc123             # same token for all services in the cluster

# Consequences:
# - Compromise of any service exposes all others
# - Rotation requires coordinated deployment of ALL consumers
# - Audit log says "db_user connected" — which service was it?

# Fix: per-service credentials
order_service: DB user order_svc_user (SELECT/INSERT on orders, order_items)
reporting:     DB user report_ro_user (SELECT only, on reporting views)
               Stripe key is READ-ONLY reporting key, not the payment key
               Vault: per-service policy, per-service token TTL=1h
🔴 Advanced — Architecture Review
How to conduct a security architecture review
A security architecture review (SAR) is a structured analysis of a system's design to identify security risks before the system is built or before changes go live. It is distinct from a penetration test: you are reviewing diagrams and design documents, not running exploits against a live system.
The security architecture review process
5 phases from intake to sign-off
▼
PhaseWhat you doOutputTypical duration
1. Scope & contextUnderstand what is being reviewed: new feature, new system, or existing system change. Identify the data sensitivity, regulatory context, and threat actors relevant to this system.Scope document, threat actor list, data classification1–2 hours
2. Architectural reviewReview data flow diagrams, architecture diagrams, and any existing threat models. Identify trust boundaries, entry points, data stores, and how components communicate.Annotated architecture diagram, trust boundary map2–4 hours
3. STRIDE analysisApply STRIDE to each component and data flow. For each: what spoofing attacks are possible? What tampering? What repudiation? What information disclosure? What denial of service? What privilege escalation?STRIDE matrix with findings per component2–4 hours

STRIDE applied at system level — worked example
Applying STRIDE to an e-commerce order processing system
▼

The system: a web frontend, an API gateway, an order service, a payment service, a notification service, and a PostgreSQL database. Users place orders; the order service calls the payment service; on success, the notification service sends email.

# STRIDE analysis per component and data flow
#
# ── Order Service ────────────────────────────────────────────────
# S Spoofing:
#   Risk: Any caller can claim to be the payment service in a callback
#   Mitigation: Validate callback via HMAC signature or mTLS from payment-svc
#
# T Tampering:
#   Risk: Order total could be modified in transit between frontend and API
#   Mitigation: Server-side total calculation, never trust client-submitted price
#
# R Repudiation:
#   Risk: User claims they never placed an order they actually placed
#   Mitigation: Audit log with user ID, timestamp, IP, order details, JWT claims
#
# I Information disclosure:
#   Risk: Order service returns all orders to any authenticated user (BOLA)
#   Mitigation: Filter by user_id = JWT sub on every query, not just GET /orders/{id}
#
# D Denial of service:
#   Risk: Expensive "get all orders with full details" query crushes DB
#   Mitigation: Pagination (max 50/page), query timeout, read replica for reports
#
# E Elevation of privilege:
#   Risk: Order service has schema owner DB privileges, injected SQL deletes tables
#   Mitigation: Dedicated app DB user with SELECT/INSERT on specific tables only
#
# ── Payment Service → External Payment Processor ─────────────────
# T Tampering:
#   Risk: Amount could be modified in the outbound API call
#   Mitigation: HMAC-sign the payment request; Stripe validates the signature
#

#   Risk: Payment service logs include full card details

Security vs usability vs performance — the real tradeoffs
How to make and communicate architecture decisions when security competes with other constraints
▼

Every security control has a cost: performance overhead, development complexity, operational burden, or user friction. The job of a security architect is not to maximise security at all costs, but to maximise security per unit of friction. Some tradeoffs are false (TLS 1.3 is both more secure AND faster than TLS 1.2). Most are real.

Knowledge Check
Security architecture interview questions
These questions appear in senior AppSec engineer, security architect, and staff engineer interviews.
Q1. A team proposes handling authorisation in a middleware that checks every request at the API layer. They argue this is "defence-in-depth" because they also validate permissions in the frontend. Is this correct? What is the flaw?
Correct — checking auth in both frontend and backend is a good example of defence-in-depth
Incorrect. This is not defence-in-depth because both controls share the same failure mode and the frontend check is trivially bypassed. Real defence-in-depth requires controls at different architectural layers that fail independently. True layered auth: API middleware validates JWT (layer 1), individual resolver/service checks object ownership (layer 2), database row-level security enforces at query time (layer 3). Frontend validation is not a security control — it is a UX optimisation.
Correct — any two controls counts as defence-in-depth
Incorrect because they should use a WAF instead of middleware
Defence-in-depth requires that controls fail independently — a bug in one should not cause all others to fail simultaneously. Frontend + API middleware using the same permission logic is not independent: if the permission model has a flaw, both checks are wrong in the same way. Additionally, client-side checks are trivially bypassed: an attacker sends a raw HTTP request and the frontend never runs. True security-in-depth for authorisation has independent layers: API gateway validates token structure, application middleware checks coarse-grained permissions (is this user authenticated?), individual resolver enforces object ownership (does this user own this order?), and database row-level security enforces at the data layer regardless of what the application does. These layers fail independently.
Q2. You are reviewing a new microservices architecture. Service A calls Service B using a shared API key that is stored in both services' environment variables. What security problems does this create, and what should replace it?
The API key should be in a secrets manager instead of an env var — that fixes the problem
Three problems: (1) Shared credential: if either Service A or B is compromised, the key is exposed and must be rotated simultaneously across both. Any audit trail says "api-key-abc" not "service-a called service-b". (2) Static long-lived key: no automatic rotation means it grows more valuable to attackers over time. (3) Shared secret is a covert channel: any service that knows the key can impersonate any other service that uses it. Replace with: mTLS via service mesh (SPIFFE identity per service, automatic rotation, no secret to share), or per-service JWT with short TTL issued by a central auth service, or IRSA/Workload Identity for cloud-native environments.
Only rotate the API key more frequently — monthly rotation fixes the problem
This is fine for internal service-to-service communication
This is the shared credentials anti-pattern. The fundamental problem is that a shared secret provides no individual identity: you know someone who knows the secret presented it, but not which specific service. This breaks audit trails, complicates incident response (which service leaked the key?), and means rotation must be coordinated across all consumers simultaneously. mTLS via service mesh is the cleanest solution: each service gets a unique X.509 certificate issued by SPIRE, signed by a SPIFFE trust domain. The certificate identity is specific to that service's workload. There is no shared secret: Service B sees "this request was made by the entity holding the certificate for service-a.production.svc". Certificates rotate automatically (24-hour TTL), so there is nothing to manage. Moving the key to a secrets manager is an improvement (better audit trail, rotation management) but does not solve the shared identity problem.
Q3. A startup argues: "We don't need Zero Trust because we're too small for nation-state attacks and we trust our employees." What is wrong with this reasoning, and what is the minimum Zero Trust investment that would make a meaningful difference?
The reasoning is correct — small companies don't need Zero Trust
Zero Trust is only about preventing insider threats, which may not apply
Wrong on two counts. First, most breaches are not nation-state attacks — they are opportunistic criminals exploiting misconfigurations and stolen credentials. Second, Zero Trust is not about distrust of employees; it is about designing systems that limit the blast radius when any credential, device, or endpoint is compromised — which happens to small companies through phishing, stolen laptops, and credential stuffing constantly. Minimum effective investment: (1) MFA on all admin access (stops 99% of credential-based attacks). (2) Default-deny network policies between services. (3) Per-service database credentials. (4) Short-lived tokens. These four controls deliver most of the Zero Trust blast-radius-limiting benefit at very low cost.
Zero Trust requires a service mesh which is too complex for small companies
Zero Trust is fundamentally about blast radius limitation: designing systems so that when something goes wrong (compromised credential, phished employee, misconfigured service), the damage is contained. Phishing, credential stuffing, and stolen laptops are not nation-state attacks — they are routine threats that hit every company at every scale. The minimum Zero Trust investment that changes the risk profile: MFA eliminates most credential-based attacks; network policies prevent a compromised service from reaching everything; per-service credentials mean one compromised service doesn't expose all data; short-lived tokens mean a stolen token expires quickly. None of these require a service mesh, complex infrastructure, or significant engineering investment. They are policy and configuration decisions.

A team is building a new healthcare patient portal. Apply a structured security architecture review and identify the security design issues. Then propose the correct design for each.

System description: A React SPA calls a Django REST API. The API stores patient records in PostgreSQL. The API calls an external lab results service via an API key. Model Answer — Healthcare Portal Security Architecture Review

Issue 1 — 7-day JWT TTL in localStorage (CRITICAL):
Problem: Two separate issues combined. (1) 7-day TTL: a stolen token gives an attacker a full week of access to patient health records. No amount of password security helps if the token persists after a credential compromise. (2) localStorage storage: accessible via JavaScript, which means any XSS vulnerability can exfiltrate the token. Healthcare data is PHI under HIPAA, making XSS-via-stolen-token a reportable breach.
Attack: XSS payload reads localStorage.getItem('access_token') and exfiltrates to attacker's server. Attacker uses token for 7 days to access any patient record the user could access.
Fix: Reduce TTL to 15 minutes. Store tokens in httpOnly, Secure, SameSite=Strict cookies. HttpOnly prevents JS access; SameSite=Strict prevents CSRF. Silent refresh in the background using a refresh token (also httpOnly cookie). For healthcare: enforce re-authentication before viewing sensitive records.

Issue 2 — PostgreSQL superuser connection (CRITICAL):
Problem: The application connects as the postgres superuser. Any SQL injection, logic error, or compromised application process can: read any table in any database, drop tables, create new superusers, execute arbitrary OS commands via pg_execute_server_program. Violates both least privilege and breach containment.
Attack: SQL injection in the patient search query executes as superuser: SELECT * FROM patients WHERE name='x'; DROP TABLE patients;-- or COPY (SELECT * FROM pg_shadow) TO '/tmp/hashes';
Fix: Create a dedicated application user: CREATE USER portal_app WITH PASSWORD '...'; GRANT SELECT, INSERT, UPDATE ON patients, records, appointments TO portal_app; The app can only touch the tables it legitimately needs. Also implement row-level security (RLS) so even if SQL injection occurs, the query runs as the portal_app role and RLS policies limit which rows are visible.

Issue 3 — Lab API key in ConfigMap (HIGH):
Problem: Kubernetes ConfigMaps are not encrypted and are world-readable to anyone with kubectl get configmap access in that namespace. The lab API key grants access to patient lab results at an external service. A Kubernetes namespace compromise, a misconfigured RBAC role, or any pod with exec access can trivially read it.
Fix: Move to a Kubernetes Secret (immediate step) and enable etcd encryption at rest with KMS. Better: use External Secrets Operator to sync from AWS Secrets Manager or Vault, with 90-day automatic rotation. The ESO syncs the key into a K8s Secret that is encrypted in etcd. Add audit logging for Secret access so you know when it is read.

Issue 4 — Admin routes with per-view is_staff check (HIGH):
Problem: Relying on every developer to remember to add the is_staff check to every admin view is error-prone. One forgotten check exposes the admin function to regular users. This is "bolted-on" security rather than structural. Also: the admin dashboard being at /api/admin/* means it shares the same authentication infrastructure as the patient API, so a patient-facing vulnerability (like a cookie theft) can give admin access.
Fix: Implement admin routes as a separate Django application (or separate service) with its own authentication middleware that enforces is_staff at the framework level, not at the individual view level. Admin traffic should require: staff flag AND separate admin session AND ideally MFA step-up re-authentication. Network policy should prevent patient-facing pods from reaching admin endpoints. Better: host the admin dashboard at a separate subdomain only accessible via VPN/corporate SSO.

Issue 5 — Celery worker and API share service account (MEDIUM-HIGH):
Problem: If the Celery worker is compromised (e.g., via a dependency vulnerability), the attacker inherits the API service account's permissions, which include reading patient records, calling the lab API, and all other API permissions. The notification worker has no legitimate need for patient record access but gets it through shared identity. Also: incident response cannot distinguish between "the API service did X" and "the Celery worker did X" in audit logs.
Fix: Create separate Kubernetes ServiceAccounts and IAM roles for the web API and the Celery worker. The Celery worker needs only: SendGrid API key (in its own Secret) and ability to read queued task data. It does not need access to patient records, the lab API key, or database write permissions beyond what tasks require. Principle of least common mechanism: separate service accounts, separate permissions.

Issue 6 — No NetworkPolicy (flat K8s network) (HIGH):
Problem: All pods can communicate with all other pods. A compromised patient-facing web pod can directly reach the database, the Celery worker's message broker, the admin service, and any other internal service. The flat network means lateral movement is trivial. This is the anti-pattern that made SolarWinds devastating.
Fix: Implement default-deny NetworkPolicy in the production namespace. Then allowlist only necessary flows: web-api → postgres:5432, web-api → redis:6379 (Celery queue), celery-worker → redis:6379, celery-worker → SendGrid (HTTPS egress), web-api → lab-service (HTTPS egress). Admin service gets its own namespace with its own network policies. Lateral movement from a compromised web pod is now blocked from reaching the database or other services.

Issue 7 — Audit logging without user IDs (HIGH for healthcare):
Problem: HIPAA requires audit controls that record who accessed which patient records and when. Logging timestamps and HTTP methods without user IDs is not a HIPAA-compliant audit trail. "GET /patients/12345/records at 14:32" is useless for an investigation: you cannot determine which user, whether they were authorised, or whether this was a breach. In healthcare this is not just a security gap; it is a compliance failure with regulatory penalties.
Fix: Log at minimum: user_id (from JWT sub claim), patient_id accessed, data type accessed (records, appointments, etc.), action (read/write/delete), timestamp, IP address, service name. For healthcare: implement a dedicated audit log table that is append-only (no UPDATE/DELETE permissions for the application user) and consider shipping logs to an immutable SIEM. The application user should have INSERT only on the audit_log table, not SELECT (prevents an attacker from covering their tracks).

Issue 8 — No ownership check on patient records (CRITICAL, BOLA):
Problem: This is a textbook Broken Object Level Authorization (OWASP API1). Any authenticated user can access any patient's records by changing the patient ID in the URL. In a healthcare context, this is a PHI breach on every request. A patient can access another patient's mental health records, HIV status, or prescriptions simply by incrementing the ID.
Fix: Every query that returns patient data must include a WHERE clause that ties the patient to the requesting user: SELECT * FROM records WHERE patient_id = %s AND patient_id IN (SELECT id FROM patients WHERE assigned_user_id = %s). For healthcare portals specifically: a patient can only view their own records. Clinicians can view assigned patients. Implement this as a database policy (row-level security) in addition to application-level checks so a SQL injection that bypasses application logic is still constrained by the database policy.
