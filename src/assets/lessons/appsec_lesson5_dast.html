DAST

DAST attacks your running application exactly like a real attacker would — sending crafted HTTP requests and observing responses — without ever looking at your source code. It finds what SAST misses: runtime vulnerabilities, authentication flaws, live server misconfigurations, and business logic issues. This lesson takes you from "what is DAST?" all the way to configuring authenticated scans, building CI/CD pipelines, and interpreting real findings from OWASP ZAP and Burp Suite.

🟢 Beginner — Level 1
What is DAST and how does it work?
DAST is the closest thing to having an automated pentester probing your application 24/7. Understanding what it does — and how it differs from SAST — is foundational.

SAST reads your source code. DAST interacts with your running application over HTTP — the same way a browser or an attacker would. It knows nothing about your code. It only knows what your server responds with. This means it tests the system as it actually behaves in production, catching runtime issues that code analysis can never see.

ℹ️
The DAST mindset: DAST doesn't read code — it reads responses. It sends a payload, watches what comes back, and infers from the response whether a vulnerability exists. A reflected XSS is found when the payload appears unescaped in the response body. A SQL error is found when the DB error message leaks into a 500 response. A header misconfiguration is found by inspecting the response headers of every page.

💡
Interview answer on SAST vs DAST: "SAST finds vulnerabilities in code before it runs — fast feedback for developers, but high false positives. DAST confirms exploitability against a live app — slower, lower false positives, finds runtime issues SAST misses. A mature security program uses both: SAST on every commit for fast feedback, DAST against staging before every release."
Black-box vs Grey-box DAST — know the difference
The mode determines how much the scanner knows before it starts
▼
ModeWhat the scanner knowsProsConsBest used for
Black-box Only the target URL. No credentials, no API spec, no source code. Tests exactly what an external unauthenticated attacker sees. Most realistic threat model. Misses all authenticated functionality. Scans only publicly accessible pages. Coverage is limited. Initial perimeter scan. External attacker simulation.
Grey-box Target URL + valid credentials (session token, username/password) + optionally an OpenAPI spec or sitemap Tests authenticated endpoints — where most vulnerabilities live. Much higher coverage. Faster scanning with OpenAPI spec. Requires maintaining test credentials. Risk of modifying production data if not using dedicated test environment. CI/CD pipeline scans. Pre-release testing. Most DAST in professional security programs.
White-box DAST Full source code access + running application. Often called IAST (Interactive) — covered in Lesson 7. Instruments the application from inside. Extremely accurate, no false positives. Requires agent installation. Performance overhead. More complex setup. High-value application security assurance programs.
⚠️
Never run DAST against production: DAST sends thousands of crafted HTTP requests including payloads like SQL injection strings, XSS payloads, and fuzzing inputs. Against production, this can corrupt data, trigger alert systems, crash the application, and generate fraudulent records. Always scan a dedicated staging/QA environment that mirrors production but has isolated databases.

🟢 Beginner — Level 2
How a DAST scan works — phase by phase
Every DAST tool follows the same fundamental workflow. Understanding each phase makes you a better scanner operator and helps you interpret results.
1
Target Configuration — what to scan and how
Before scanning starts
▼

You configure the scanner with: the target URL (e.g., https://staging.myapp.com), the scan scope (which paths to include/exclude), authentication credentials or a session token, and optionally an OpenAPI spec for API scanning. This phase is the most important — bad configuration leads to incomplete scans or wasted time scanning irrelevant endpoints.

Critical configuration decisions
Config itemWhy it mattersExample
Scope (include)Only test URLs that belong to your application. Without scope, scanner follows every external link.https://staging.myapp.com/.*
Scope (exclude)Exclude logout URLs (would terminate your session mid-scan), admin destructive actions, email-sending endpoints..*/logout.*, .*/send-email.*
AuthenticationWithout auth, scanner only tests public pages — misses 80% of attack surface.Session cookie, Bearer token, username+password for form auth
Max depth / threadsToo deep = too slow. Too many threads = crashes the app server.Max depth: 5. Threads: 10 for staging.
2
Spider / Crawl — discovering the attack surface
~10–30 minutes depending on app size
▼

The spider visits your application like a browser — following every link, form action, and JavaScript-discovered URL to build a map of the entire application. Every discovered URL, parameter, and form becomes a potential attack point for the active scan. Without thorough spidering, the active scan has nothing to attack.

Two types of spider
Spider typeHow it worksBest forLimitation
Traditional spiderFollows HTML links, form actions, and redirects. Fast.Server-rendered HTML apps (Django, Rails, Laravel)Misses JavaScript-rendered content (React, Vue, Angular SPAs)
AJAX spiderUses a headless browser (Selenium/Playwright) to render JavaScript and discover dynamically loaded routes.Modern SPAs, React/Vue/Angular apps, AJAX-heavy applicationsSlower — must execute JavaScript for every page
📌
For React/Vue/Angular apps: Always use the AJAX spider (also called DOM spider). A traditional spider on a SPA will find only the root / URL and miss every route. The AJAX spider renders the app, clicks through UI elements, and discovers dynamically loaded API calls — giving you the full attack surface.
3
Passive Scan — analyzing every response for immediate findings
Runs concurrently with spidering — zero additional requests
▼

As the spider fetches pages, the passive scanner analyzes every request and response it sees — without sending any additional requests. It's looking for issues that are immediately visible: missing security headers, insecure cookie flags, information disclosure in responses, mixed HTTP/HTTPS content, and weak TLS configurations. Because it sends zero extra requests, it cannot disrupt the application.

What passive scanning finds
Missing: Content-Security-Policy
No CSP header means XSS attacks have no mitigating layer beyond input validation
Missing: Strict-Transport-Security
No HSTS means browser will connect over HTTP if redirected by attacker (SSL stripping)
Set-Cookie: session=abc; Path=/
Missing HttpOnly (XSS can steal cookie) and Secure (sent over HTTP)
Server: Apache/2.4.29 (Ubuntu)
Server version disclosure — attacker knows exact version to look up CVEs for
X-Powered-By: PHP/7.2.0
Framework version disclosure — PHP 7.2.0 is EOL with known vulnerabilities
4
Active Scan — attacking every discovered parameter
The main event — sends thousands of crafted payloads
▼

The active scanner takes every URL, parameter, header, and form field discovered by the spider and attacks them with crafted payloads. For a URL with 3 parameters, it might send 1,000+ requests — each one probing for a different vulnerability type. The response to each request is analyzed for indicators of vulnerability (error messages, reflected payload, time delays, different status codes).

How active scanning works for each vulnerability type
VulnerabilityPayload exampleIndicator of success
SQL Injection (error-based)' OR '1'='1, ' --, '; DROP TABLE--SQL error message in response: "You have an error in your SQL syntax"
SQL Injection (blind, time-based)'; WAITFOR DELAY '0:0:5'-- (MSSQL)Response takes 5+ seconds longer than baseline — confirms SQLi without error output
Reflected XSS<script>alert(1)</script>, "><img src=x onerror=alert(1)>Payload appears unencoded in response body — browser would execute it
Path Traversal../../../etc/passwd, ....//....//etc/passwdResponse contains root:x:0:0 — contents of /etc/passwd
SSTI (Template Injection){{7*7}}, ${7*7}, #{7*7}Response contains 49 — template engine evaluated the expression
Open Redirect?next=https://evil.com, ?redirect=//evil.comResponse redirects to attacker's domain (Location header: https://evil.com)
Command Injection; sleep 5, | whoami, $(id)Time delay (for blind) or command output in response
5
Reporting — understanding DAST output
Triaging findings into real vs false positive
▼

DAST reports contain findings ranked by severity (Critical → High → Medium → Low → Informational). Each finding shows: the affected URL, the specific parameter, the payload that triggered it, the evidence in the response, and a remediation recommendation. Your job is to triage these findings — not every finding is a real vulnerability.

DAST finding triage checklist
Question to askWhat to check
Is the payload actually dangerous?Some scanners flag <b> being reflected as "XSS" even if HTML is properly escaped. Verify the payload actually executes in a browser.
Is the endpoint reachable by attackers?An internal-only endpoint accessible only from within the VPC is lower risk than a public endpoint.
Is authentication required?A finding on an unauthenticated endpoint is higher severity than the same finding behind authentication.
Can you reproduce it manually?Open Burp Suite, replay the exact request the scanner used. If it doesn't reproduce, it may be a false positive.
What is the real business impact?Missing X-Frame-Options on an app with no sensitive functionality is lower risk than the same on a banking portal.
🟡 Intermediate — OWASP ZAP
OWASP ZAP — the industry standard free DAST tool
OWASP ZAP (Zed Attack Proxy) is the most widely used DAST tool in the world. It's free, open-source, and maintained by OWASP. It can be used as a GUI tool for manual testing or run headlessly in CI/CD pipelines. Every AppSec engineer must know it deeply.

Installation
GUI Workflow
Authenticated Scan
CLI / Headless

ZAP operates as an intercepting proxy between your browser (or test scripts) and your target application. Every HTTP request passes through ZAP, which records it, passively analyzes it, and optionally attacks it. ZAP's architecture consists of:

ProxySits between browser and app. Records all traffic.Manual exploration, session capture, authenticated scan setup
SpiderAutomated crawler — finds all URLs and parametersAttack surface discovery before active scan
AJAX SpiderHeadless browser crawler for JavaScript-heavy appsSPA scanning (React/Vue/Angular)

Passive ScannerAnalyzes traffic without extra requestsHeader issues, cookie flags, info disclosure

The ZAP GUI is where you do manual exploration and set up authenticated scans before running automated scans. Here is the standard workflow:

# STEP 1: Configure your browser to use ZAP as proxy
# ZAP listens on: localhost:8080 (HTTP proxy)
# Set in browser: Settings → Network → Manual Proxy → localhost:8080
# Install ZAP's root CA certificate in your browser (Tools → Options → Network → Server Certificates)

# STEP 2: Browse your application
# With your browser proxied through ZAP, log in to the app and navigate through key features.
# ZAP records every request in the "Sites" tree.
# This builds the attack surface map before automated scanning.

# STEP 3: Set scan scope
# Right-click the target site in "Sites" tree → "Include in Context"
# This tells ZAP to only scan YOUR app's URLs, not CDNs or third parties

# STEP 4: Run Spider
# Right-click target → Spider → "Start Scan"
# ZAP discovers all additional URLs not found through manual browsing

# STEP 5: Run Active Scan
# Right-click target → Active Scan → "Start Scan"
# ZAP begins attacking every discovered parameter

# STEP 6: Review Alerts
# Bottom pane → "Alerts" tab
# Sorted by risk: Red (High) → Orange (Medium) → Yellow (Low) → Blue (Informational)

Authenticated scanning is the most critical configuration. Without it, you only scan public pages. There are three authentication methods in ZAP depending on your app's auth type:

# ── Method 1: Session Cookie (most common) ─────────────────────
# Step 1: Log in to your app manually via ZAP proxy
# Step 2: Find the session cookie in ZAP → Request → Response → Cookies
# Step 3: In ZAP: Sites → Right-click app → Context → Authentication
# Step 4: Set Authentication Method: "Script-based" or "Form-based"
# Step 5: Add session cookie as an HTTP Session Token

# ── Method 2: Bearer Token / JWT (API authentication) ──────────
# In ZAP: Right-click target → Context → Authorization
# Add Authorization header: Bearer eyJ... (your test user JWT)
# ZAP attaches this header to every request in the scan

# ── Method 3: Form-based auth (automated login) ─────────────────
# ZAP logs in on your behalf using credentials you provide
# Configure in: Context → Authentication → Form-based Authentication
Login URL:    https://staging.myapp.com/login
POST data:    username={%username%}&password={%password%}
Success:      Logged in as       # text that appears when login works
Failure:      Invalid credentials # text that appears on failed login

# ZAP monitors for the logout pattern and re-authenticates
# if it detects the session has expired during the scan

# ── Verification: confirm ZAP is authenticated ──────────────────
# Spider → check that authenticated URLs appear in Sites tree
# If /dashboard, /profile, /settings appear → auth is working
# If only /login, /register appear → auth failed, check config

# ZAP CLI / Docker — three built-in scan scripts

# ── 1. Baseline Scan: passive only, fast (2–5 min) ─────────────
$ docker run ghcr.io/zaproxy/zaproxy:stable zap-baseline.py \
    -t https://staging.myapp.com \
    -r baseline-report.html \
    -J baseline-report.json \
    -I                        # don't fail on warnings, only errors

# ── 2. Full Scan: spider + active scan (20–60+ min) ─────────────
$ docker run ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py \
    -t https://staging.myapp.com \
    -r full-report.html \
    -z "-config scanner.strength=HIGH" \  # increase scan strength
    -x full-report.xml

# ── 3. API Scan: OpenAPI-spec-driven (most thorough for APIs) ───
$ docker run -v $(pwd):/zap/wrk ghcr.io/zaproxy/zaproxy:stable zap-api-scan.py \
    -t /zap/wrk/openapi.json \  # your OpenAPI 3.0 spec file
    -f openapi \
    -r api-report.html

# ── Authenticated scan from CLI ──────────────────────────────────
$ docker run ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py \
    -t https://staging.myapp.com \
    -r report.html \
    -z "-config replacer.full_list(0).description=Auth \
        -config replacer.full_list(0).enabled=true \
        -config replacer.full_list(0).matchtype=REQ_HEADER \
        -config replacer.full_list(0).matchstr=Authorization \
        -config replacer.full_list(0).replacement='Bearer eyJ...'"
# This injects your Bearer token into every request ZAP makes
🟡 Intermediate — Burp Suite
Burp Suite — the professional pentest platform
Burp Suite is the tool of choice for professional security engineers and pentesters. The Community edition is free with limited features. Professional ($449/yr) adds the automated scanner, Intruder (for fuzzing), and extensions. Enterprise adds CI/CD integration.
ℹ️
ZAP vs Burp: ZAP is free, excellent for CI/CD automation, and good for systematic scanning. Burp Pro is the professional tool for manual security testing, pentesting, and more sophisticated attacks. In a mature security program, you use both: ZAP in the automated pipeline, Burp for manual pentest work and deep investigation of findings.
Burp Proxy — intercept and modify every HTTP request
The foundation of all Burp workflow — everything flows through the proxy
▼

Burp Proxy is an intercepting HTTP/HTTPS proxy. Every request your browser makes to the target goes through Burp first. You can inspect it, modify it, forward it, or drop it. This is how security engineers manually test for vulnerabilities — intercept a request, modify a parameter, see what the server does.

# Burp Proxy workflow for testing an IDOR vulnerability:

# 1. Configure browser to proxy through Burp: 127.0.0.1:8080
# 2. Navigate to your profile page: GET /api/user/1001
# 3. Burp intercepts the request — you see:
GET /api/user/1001 HTTP/1.1
Host: staging.myapp.com
Cookie: session=abc123
Authorization: Bearer eyJ...

# 4. Modify user ID in Burp: change 1001 → 1002
GET /api/user/1002 HTTP/1.1
Host: staging.myapp.com
Cookie: session=abc123

# 5. Forward modified request and observe response:
HTTP/1.1 200 OK                          # ← should be 403 Forbidden!
{"id": 1002, "email": "other@user.com", "address": "123 Main St"}
# CONFIRMED IDOR: user A can read user B's data
Burp Repeater — replay and modify requests manually
Your primary tool for confirming vulnerabilities and crafting exploits
▼

Repeater lets you resend any intercepted request with modifications and see the response instantly. It's your workbench for confirming vulnerabilities. When ZAP flags a potential SQL injection, you use Repeater to manually craft progressively more complex payloads to confirm the vulnerability and determine its full impact.

# Confirming SQL injection with Burp Repeater
# ZAP flagged: POST /search?q= as potential SQLi

# Test 1: Baseline — normal request
POST /search HTTP/1.1
Content-Type: application/json
{"q": "laptop"}
# Response: 200 OK, 12 results

# Test 2: Single quote — triggers error?
{"q": "'"}
# Response: 500 Internal Server Error
# Body: "You have an error in your SQL syntax near '''"
# → CONFIRMED: SQL injection, error-based

# Test 3: Authentication bypass
{"q": "' OR '1'='1' --"}
# Response: 200 OK, ALL 50,000 products returned
# → Authentication bypass confirmed. Attacker can dump entire catalog.

# Test 4: Union-based data extraction
{"q": "' UNION SELECT username, password, null FROM users --"}
# Response: 200 OK, results include:
# [{"name": "admin", "description": "$2b$12$hash..."}, ...]
# → Full database dump via SQLi confirmed
Burp Intruder — automated fuzzing with payload lists
Iterate through thousands of payloads against a specific parameter
▼

Intruder takes a request with marked injection points and iterates through a payload list, sending one request per payload. It's used for credential brute-forcing, IDOR enumeration, and fuzzing for injection vulnerabilities with large payload sets.

# Burp Intruder — enumerating IDOR across order IDs

# Base request (intercepted from Burp Proxy):
GET /api/orders/§1001§ HTTP/1.1   # § marks injection point
Cookie: session=user_a_token

# Payload type: Numbers
# Payload set: 1000 → 2000 (sequential)
# Intruder sends 1000 requests, one per order ID

# Analyze results by response length:
# ID 1001: 200 OK, length 342  ← your order
# ID 1002: 403 Forbidden, length 0
# ID 1003: 403 Forbidden, length 0
# ID 1004: 200 OK, length 387  ← ANOTHER USER's order! IDOR confirmed
# ID 1005: 200 OK, length 412  ← and another one...

# Filter by status code 200 → shows every IDOR-accessible order
# This is automated IDOR enumeration — finds all exposed records
💡
Intruder attack types: Sniper (one payload list, one position at a time), Battering Ram (same payload in all positions simultaneously), Pitchfork (parallel payload lists), Cluster Bomb (all combinations). For credential stuffing: Pitchfork with username list + password list. For IDOR: Sniper with sequential numbers.

ZAP Alert ID: 40018 · CWE-89 · URL: https://staging.myapp.com/api/products/search
CRITICAL
Evidence from ZAP Report
# Request ZAP sent:
POST /api/products/search HTTP/1.1
Host: staging.myapp.com
Content-Type: application/json

{"q": "' AND 1=2 UNION SELECT NULL,@@version,NULL--"}

# Response ZAP received:
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{
  "error": "near '--': syntax error",
  "query": "SELECT id, name, price FROM products WHERE name LIKE '%' AND 1=2 UNION SELECT NULL,@@version,NULL--%'"
}
# DB error leaked full SQL query in response → Error-based SQL injection confirmed
Your Triage

TRUE POSITIVE — CRITICAL. ZAP has not just detected a potential SQLi — it has confirmed it. The full SQL query is reflected in the error response, revealing the query structure. The attacker can now craft a UNION-based extraction to dump the entire database. This is a P0 finding — block deployment until fixed.

Fix
# Vulnerable (Flask + SQLAlchemy raw query):
def search_products(q):
    result = db.engine.execute(f"SELECT * FROM products WHERE name LIKE '%{q}%'")

# Fixed — SQLAlchemy ORM (parameterized by design):
def search_products_fixed(q):
    results = Product.query.filter(Product.name.ilike(f'%{q}%')).all()
    return results

# ALSO fix: never return SQL errors to client
app.config['PROPAGATE_EXCEPTIONS'] = False  # generic 500 error only

# ZAP concludes: no CSRF protection
Triage — Is This a Real CSRF Vulnerability?

This may be a FALSE POSITIVE — depending on your authentication mechanism. Here's the critical check:

Auth methodCSRF vulnerable?Reason
Bearer Token (Authorization header)NOT vulnerable to CSRFCSRF attacks cannot set custom request headers. An attacker's forged form submission from evil.com cannot include your Authorization header — the browser blocks it. Bearer token auth IS CSRF-safe.
Session Cookie (Cookie header)VULNERABLE to CSRFBrowsers automatically send cookies with cross-origin requests. An attacker's form on evil.com triggers POST to your app, and the browser attaches the victim's session cookie automatically.
Verdict

If the API uses Bearer tokens exclusively: FALSE POSITIVE — suppress with documentation: # nosec CSRF — API uses Bearer token auth; CSRF not applicable per OWASP CSRF Prevention Cheat Sheet

If the API accepts cookies for auth: TRUE POSITIVE — add SameSite=Strict to session cookie AND verify that state-changing requests require either a CSRF token or check the Origin/Referer header.

CONTEXT-DEPENDENTFP if Bearer-onlyTP if cookie authCWE-352
🔴 Advanced — CI/CD Integration
DAST in your CI/CD pipeline
Running DAST in CI is harder than SAST — DAST needs a live running application. Here is the full architecture and GitHub Actions configuration to make it work reliably.
📌
Architecture challenge: SAST scans source code — it can run without any infrastructure. DAST needs: a running application server, a running database, any external services your app calls (mocked or real), and a dedicated test environment with isolated data. This is why DAST is more complex to automate than SAST.
github-actions
# .github/workflows/dast.yml
name: DAST Security Scan

on:
  push: { branches: [main] }
  pull_request: { branches: [main] }

jobs:
  dast:
    runs-on: ubuntu-latest

    services:
      # ── Spin up the application + database ──────────────────────
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB: testdb
          POSTGRES_PASSWORD: testpass
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4

      # ── Build and start your application ───────────────────────
      - name: Set up Python
        uses: actions/setup-python@v5
        with: { python-version: '3.12' }

      - name: Install dependencies and start app
        run: |
          pip install -r requirements.txt
          python manage.py migrate --run-syncdb
          python manage.py loaddata test_fixtures.json  # load test data including test users
          python manage.py runserver 0.0.0.0:8000 &     # start app in background
          sleep 5                                        # wait for server to be ready
        env:
          DATABASE_URL: postgresql://postgres:testpass@localhost/testdb
          SECRET_KEY: ci-test-secret-key-not-for-production
          DEBUG: 'False'

      # ── Obtain authentication token for grey-box scan ───────────
      - name: Get auth token for ZAP
        id: auth
        run: |
          TOKEN=$(curl -s -X POST http://localhost:8000/api/auth/token/ \
            -H "Content-Type: application/json" \
            -d '{"username":"testuser","password":"testpass123"}' \
            | jq -r '.access')
          echo "token=$TOKEN" >> $GITHUB_OUTPUT

      # ── Run ZAP Baseline (passive) scan ─────────────────────────
      - name: ZAP Baseline Scan
        uses: zaproxy/action-baseline@v0.11.0
        with:
          target: 'http://localhost:8000'
          rules_file_name: '.zap/rules.tsv'     # custom rule overrides
          cmd_options: '-I'                      # don't fail on warnings

      # ── Run ZAP Full Scan (authenticated, active) ───────────────
      - name: ZAP Full Authenticated Scan
        uses: zaproxy/action-full-scan@v0.10.0
        with:
          target: 'http://localhost:8000'
          cmd_options: >-
            -z "-config replacer.full_list(0).enabled=true
               -config replacer.full_list(0).matchtype=REQ_HEADER
               -config replacer.full_list(0).matchstr=Authorization
               -config replacer.full_list(0).replacement='Bearer ${{ steps.auth.outputs.token }}'"

      # ── Enforce severity threshold ──────────────────────────────
      - name: Parse ZAP results and enforce gate
        run: |
          HIGHS=$(cat zap-report.json | jq '[.site[].alerts[] | select(.riskdesc | startswith("High"))] | length')
          CRITS=$(cat zap-report.json | jq '[.site[].alerts[] | select(.riskdesc | startswith("Critical"))] | length')
          echo "Critical: $CRITS  High: $HIGHS"
          if [ $((CRITS + HIGHS)) -gt 0 ]; then
            echo "::error::DAST gate failed — $CRITS critical, $HIGHS high findings"
            exit 1
          fi

      # ── Upload HTML report as artifact ──────────────────────────
      - name: Upload ZAP Report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: dast-report
          path: |
            zap-report.html
            zap-report.json
🔴 Advanced — API Security Scanning
DAST for APIs — OpenAPI-driven scanning
Modern applications are largely APIs. DAST scanning a REST API requires a different approach than scanning a web app — you need an API spec to tell the scanner what endpoints exist and what parameters they accept.
ℹ️
Why APIs need special handling: A traditional web spider discovers pages by following HTML links. REST APIs have no HTML links. Without an OpenAPI/Swagger spec, the scanner has no way to discover endpoints like POST /api/v2/payments or DELETE /api/users/{id}. The OpenAPI spec IS the attack surface map for API scanning.
# ZAP API Scan with OpenAPI spec — most thorough API DAST

# Your openapi.json / openapi.yaml specifies all endpoints:
# ZAP reads the spec, generates requests for every endpoint,
# and injects payloads into every parameter.

$ docker run -v $(pwd):/zap/wrk:rw ghcr.io/zaproxy/zaproxy:stable \
    zap-api-scan.py \
    -t /zap/wrk/openapi.json \         # OpenAPI 3.0 or Swagger 2.0 spec
    -f openapi \
    -r /zap/wrk/api-report.html \
    -J /zap/wrk/api-report.json \
    -z "-config scanner.strength=HIGH" \
    -H "Authorization: Bearer eyJ..."  # auth token for authenticated scan

# For GraphQL APIs — ZAP has a dedicated GraphQL scanner:
$ docker run ghcr.io/zaproxy/zaproxy:stable \
    zap-full-scan.py \
    -t https://staging.myapp.com/graphql \
    -z "-config graphql.endpoint=https://staging.myapp.com/graphql \
        -config graphql.schemaUrl=https://staging.myapp.com/graphql?sdl"
API-specific vulnerabilities DAST finds
Beyond standard web vulnerabilities — these are API-specific attack patterns
▼
VulnerabilityHow DAST tests itOWASP API Category
BOLA / IDOR Tests resource endpoints by replacing the object ID with other valid IDs (numeric increment, UUID fuzzing). Checks if different users' data is returned. API1 — Broken Object Level Authorization
Mass Assignment Sends extra fields in POST/PUT bodies beyond what the API spec accepts (e.g., adding "role":"admin" to a user update). Checks if the server accepts and processes them. API3 — Broken Object Property Level Auth
No Rate Limiting Sends the same request 100× in rapid succession. If all succeed with 200 OK → no rate limiting. Critical for auth endpoints. API4 — Unrestricted Resource Consumption
Excessive Data Exposure Analyzes API responses for fields not in the OpenAPI spec — password hashes, internal IDs, PII fields that should be filtered out. API3 — Broken Object Property Level Auth
Broken Function Level Auth Tests admin/privileged endpoints with a regular user token. If 200 OK → auth check missing at function level. API5 — Broken Function Level Authorization 
# Example: testing Mass Assignment with curl / Burp
# API spec says: PATCH /api/users/{id} accepts: {name, email}
# DAST tests: what happens if we send extra fields?

# Normal request (as per spec):
PATCH /api/users/42 HTTP/1.1
Authorization: Bearer user_token
{"name": "Alice", "email": "alice@example.com"}
# Response: 200 OK — expected

# Mass assignment attack (adding unauthorized field):
PATCH /api/users/42 HTTP/1.1
Authorization: Bearer user_token
{"name": "Alice", "email": "alice@example.com", "role": "admin", "is_staff": true}
# If Response: 200 OK → mass assignment vulnerability!
# User has escalated their own privileges to admin

# Fix: use explicit field allowlist in your serializer
class UserUpdateSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = ['name', 'email']  # ONLY these two — role, is_staff excluded
🔴 Advanced — Scan Policies & Tuning
Custom scan policies and false positive management
A default ZAP scan on a large app generates hundreds of findings, many of which are false positives. Tuning your scan policy reduces noise and makes findings actionable.
# ZAP custom rules file: .zap/rules.tsv
# Format: rule_id  PASS|WARN|FAIL  optional-description

# Syntax: tab-separated: AlertID   Action
# PASS = suppress finding (false positive, accepted risk)
# WARN = report but don't fail CI
# FAIL = fail CI pipeline (default for HIGH+)

10020	WARN	# X-Frame-Options — we use CSP frame-ancestors instead
10038	WARN	# CSP missing — we're still rolling out CSP
10202	PASS	# CSRF — API uses Bearer tokens only, CSRF not applicable
90022	PASS	# App error disclosure in test env only — not prod
10015	WARN	# Incomplete or no cache-control — acceptable for this app

# Key ZAP Alert IDs to know:
# 40018 = SQL Injection        40012 = XSS Reflected
# 40014 = XSS Persistent       10202 = CSRF
# 10038 = CSP missing          10020 = X-Frame-Options
# 40009 = Path Traversal       90022 = App Error Disclosure
# 10010 = Cookie no HttpOnly   10011 = Cookie Secure Flag Missing
⚠️
Every PASS suppression needs a documented business justification. In your .zap/rules.tsv, add a comment for every suppressed rule explaining why it's safe to suppress. "10202 PASS — API exclusively uses Bearer JWT tokens in Authorization header; CSRF not applicable per OWASP CSRF Cheat Sheet. Verified: no cookie-based auth." This is your audit trail for security reviews and compliance audits.
Knowledge Check
DAST interview questions
Questions you will face in AppSec engineer and security consultant interviews
Q1. ZAP flags a "SQL Injection" finding on your login endpoint. You check the request ZAP sent — it used a single quote as the payload. The response was a generic "Invalid credentials" message with no error details and a normal 200 status code. Is this a true positive?
Yes — any SQL injection payload causing a different response confirms SQLi
Yes — single quote always triggers SQLi
Likely false positive — a generic "Invalid credentials" 200 response to a single quote gives no evidence of SQLi. A true positive would show a DB error, a different status code, or different response length/timing. Verify manually with Burp Repeater using time-based payloads.
Definitely false positive — login endpoints are never vulnerable to SQLi
DAST confidence levels matter. ZAP sometimes flags potential SQLi when a response differs from baseline — but a generic "Invalid credentials" doesn't confirm injection. The evidence must show something injectable: a DB error, a significant response time difference with ; SLEEP(5)--, different result counts, or reflected SQL in the response. Use Burp Repeater to manually test: send ' AND SLEEP(5)-- and check if response takes 5+ seconds. That would confirm blind SQLi.
Q2. You need to run DAST in CI/CD but your app calls Stripe's payment API during checkout. What problems does this cause and how do you solve them?
No problem — DAST only tests your app, not Stripe
DAST will trigger real Stripe API calls during scanning, potentially creating real charges and fraudulent transactions. Solution: use Stripe's test mode with test API keys in the CI environment. Also mock/stub all third-party integrations in the test environment, or configure ZAP to exclude the checkout endpoint from active scanning.
Disable DAST scanning for the payment section entirely
Use production Stripe keys — DAST won't send enough requests to cause real charges
DAST active scanning sends hundreds of crafted requests to every discovered endpoint. For a checkout endpoint, this means hundreds of attempted payment transactions — creating fraudulent charges in Stripe if live keys are used. Solutions: (1) Use Stripe test mode (sk_test_... keys) in CI — test charges don't cost real money. (2) Stub the Stripe SDK in the test environment (replace with a mock that returns fake success). (3) Add .*/checkout.* and .*/payment.* to ZAP's active scan exclusions. Option 3 reduces coverage — prefer option 1 or 2.
Q3. What is the difference between a ZAP Baseline scan and a ZAP Full scan, and when would you use each in a CI/CD pipeline?
They are the same — Full scan just has more rules enabled
Baseline is for APIs, Full is for web applications
Baseline = passive scan only (no attack payloads sent, 2–5 min). Finds header misconfigs and info disclosure without disrupting the app. Full = spider + active scan (sends thousands of attack payloads, 20–60+ min). Finds SQLi, XSS, injection. Use Baseline on every PR (fast, safe). Use Full on merge to main or nightly (thorough but slow).
Baseline scans authenticated pages, Full scan is unauthenticated
The key distinction is active vs passive. Baseline uses only the passive scanner — it never sends attack payloads, so it's extremely fast and safe to run against any environment. Full scan runs the active scanner — it sends SQLi strings, XSS payloads, and path traversal sequences to every discovered parameter, which can disrupt app operation and is slow. Pipeline strategy: Baseline on every PR (2–5 min, blocks on header issues), Full on merge to main (20–60 min, blocks on HIGH+ active findings), API scan against OpenAPI spec on pre-release.
