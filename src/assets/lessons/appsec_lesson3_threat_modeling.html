🟢 Beginner — Level 1
What is threat modeling?
Start here if you've never done it before. This section explains the concept from scratch.

Imagine you are building a bank vault. Before you pour the concrete, you would ask: Who would try to break in? How would they do it? What are we protecting? What happens if they succeed? Threat modeling is exactly that — but for software systems, done before you write the first line of code.

💡
The simplest definition: Threat modeling is a structured process for identifying security problems in a system's design before building it. It answers: what could go wrong, and what should we do about it?
⚠️
Why "I'll just fix bugs after testing" doesn't work: Security flaws found in design cost $80 to fix. The same flaw found after a production breach costs $80,000–$8,000,000. You cannot bolt good security onto a poorly designed system. The architecture must be correct from the start — and threat modeling is how you make it correct.
The Framework
The 4 questions every threat model must answer
Q1
What are we building?
Draw a Data Flow Diagram (DFD). Show every component, every data store, every user, and every data flow between them. Without this diagram, your team is arguing about an imaginary system.
Q2
What can go wrong?
Apply a threat categorization framework (STRIDE, PASTA, LINDDUN) to every element in your diagram. For each element, ask: how could an attacker abuse this? What assumptions are we making that might be wrong?
Q3
What are we going to do about it?
For each threat identified, decide: mitigate (add a control), accept (document the risk and why), transfer (cyber insurance, third-party), or eliminate (remove the feature). Every threat needs a documented decision.
Q4
Did we do a good job?
Review the threat model. Are the threats plausible? Did we miss any? Are the controls actually implemented? Threat models must be living documents — updated when the system changes, not filed away and forgotten.
🟢 Beginner — Level 2
Assets, trust boundaries & the DFD
Three foundational concepts you must understand before applying any threat framework.
Assets — what are you protecting?
Without knowing your assets, you don't know what to defend
▼

An asset is anything of value that an attacker would want to steal, destroy, or manipulate. Before you can identify threats, you must list your assets — because every threat targets an asset.

Asset types

Asset TypeExamplesImpact if compromisedClassification
Data assetsUser PII, passwords, payment cards, medical records, API keysData breach, regulatory fines, identity theftConfidential / Restricted
System assetsWeb servers, databases, CI/CD pipeline, cloud credentialsService disruption, ransomware, data destructionCritical / High
Business assetsReputation, customer trust, IP, trade secrets, source codeLong-term business damage, competitive disadvantageConfidential
Process assetsDeployment pipeline, CI/CD, build process, authentication flowSupply chain attack, backdoor injectionCritical
ℹ️
Asset-first threat modeling: Always start by listing assets, then threats. "What could go wrong?" is unanswerable without knowing what you're protecting. "What could go wrong with user passwords?" is answerable. This simple shift makes threat modeling 10× more productive.
Trust boundaries — where attacks cross
Every security failure happens when data crosses a trust boundary without validation
▼

A trust boundary is a line on your diagram where data moves between two components that have different trust levels. The internet is untrusted. Your database is highly trusted. When data moves from the internet to your database — it crosses a trust boundary, and that crossing is where attacks happen.

Trust boundary examples

BoundaryLower Trust SideHigher Trust SideRequired Control
Internet → App ServerAny user on the internetYour application logicInput validation, WAF, rate limiting, TLS
App Server → DatabaseApplication code (could be compromised)Database with production dataParameterized queries, read-only user, network firewall
User → Admin functionAuthenticated regular userAdmin functionalityRole-based access control, MFA for privileged actions
Third-party API → Your appExternal service response (could be tampered with)Your data processingResponse validation, HMAC verification, allowlist
Container → Host OSContainer processHost kernel and filesystemNon-root user, seccomp, read-only filesystem, no --privileged
⚠️
The golden rule: Any data that crosses a trust boundary from lower to higher trust must be validated, sanitized, and authorized before use. SQL injection, XSS, command injection — all of them are caused by failing this rule. The attacker sends malicious data from their untrusted browser into your trusted database without validation at the boundary.
Data Flow Diagrams (DFD) — the foundation of threat modeling
You cannot threat model what you haven't drawn
▼

A Data Flow Diagram shows how data moves through your system. It has 4 elements: External Entities (users, third parties), Processes (code that does something), Data Stores (databases, caches, files), and Data Flows (arrows showing data movement). Trust boundaries are drawn as dashed lines around groups of components at the same trust level.

DFD notation

ShapeMeaningExampleIn threat modeling
RectangleExternal entity — outside your controlBrowser, mobile app, payment providerSource of untrusted input
Circle/OvalProcess — code that transforms dataAuth service, order processor, API handlerWhere logic vulnerabilities live
Two parallel linesData store — persisted dataPostgreSQL, Redis cache, S3 bucket, logsTarget asset for attackers
ArrowData flow — data in transitHTTP request, DB query, API callWhere interception/tampering happens
Dashed boxTrust boundary — privilege level changeInternet ↔ DMZ, DMZ ↔ internalWhere every crossing needs validation

Spoofing — "I am not who I claim to be"
Violates: Authentication. The attacker pretends to be a legitimate user, service, or system to gain unauthorized access.

What spoofing attacks look like

AttackHow it worksExample
Credential theftAttacker steals a valid user's session token or password and uses itPhishing email → user enters credentials → attacker logs in as them
Session fixationAttacker sets the victim's session ID before login, then uses the same ID afterApp sets session cookie before auth → attacker knows the cookie → logs in as victim
JWT forgeryAttacker crafts a JWT with forged claimsWeak secret → attacker brute forces HMAC key → signs arbitrary {"role":"admin"} token
DNS spoofingAttacker returns fake DNS responses to redirect traffic to their serverapi.bank.com resolves to attacker IP → all API calls go to attacker's server

Vulnerable code and the fix

# SPOOFING: JWT algorithm confusion attack
# Attacker changes alg from RS256 to HS256 and signs with the PUBLIC key

import jwt

def verify_token_vulnerable(token):
    # VULNERABLE: accepts ANY algorithm the token claims
    decoded = jwt.decode(token, PUBLIC_KEY, algorithms=None)
    # Attacker sets alg=HS256, signs with PUBLIC_KEY (which they have)
    # → Server verifies with PUBLIC_KEY using HMAC → accepts forged token!
    return decoded

# FIXED: algorithm is specified server-side and NEVER from the token
def verify_token_fixed(token):
    decoded = jwt.decode(
        token,
        PUBLIC_KEY,
        algorithms=["RS256"],   # ← hardcoded server-side, not from token
        options={"require": ["exp", "iat", "sub"]}  # ← required claims
    )
    return decoded

Controls for Spoofing threats

Strong authentication (MFA) Short-lived tokens with rotation Certificate pinning for service-to-service HTTPS with HSTS — prevent downgrade Algorithm pinning in JWT verification

# TAMPERING: parameter manipulation — price tampering
# Attacker modifies the price in the request body

@app.route('/checkout', methods=['POST'])
def checkout():
    item_id = request.json['item_id']
    price   = request.json['price']        # ← TAMPERED: attacker sends price=0.01
    charge_card(price)                        # charges $0.01 instead of $99.99

# FIXED: NEVER trust user-supplied price. Look it up server-side.
@app.route('/checkout', methods=['POST'])
def checkout_fixed():
    item_id = request.json['item_id']
    item  = Product.query.get_or_404(item_id)  # ← price from DB, not request
    price = item.price                          # ← attacker cannot influence this
    charge_card(price)
R
Repudiation — "I didn't do that, prove it"
Violates: Non-repudiation. The attacker (or malicious insider) performs an action and then claims they didn't. Without proper audit logs, you cannot prove otherwise.

Repudiation is the only STRIDE threat where the absence of a control creates the vulnerability. If you have no immutable audit log, you have a repudiation problem — even if no attacker ever exploits it. A malicious employee could transfer money, delete data, or leak PII and then deny it completely.

What good audit logging looks like

# BAD: No audit log — repudiation trivially possible
@app.route('/admin/delete-user', methods=['POST'])
def delete_user():
    user_id = request.json['user_id']
    User.query.filter_by(id=user_id).delete()   # ← no record of who did this, when
    db.session.commit()
    return 'deleted'

# GOOD: Immutable audit trail — non-repudiation
@app.route('/admin/delete-user', methods=['POST'])
@login_required
@require_role('admin')
def delete_user_fixed():
    user_id = request.json['user_id']
    target  = User.query.get_or_404(user_id)
    AuditLog.create(                            # ← written BEFORE the action
        actor_id   = current_user.id,
        actor_ip   = request.remote_addr,
        action     = 'USER_DELETE',
        target_id  = user_id,
        target_email = target.email,            # capture state BEFORE deletion
        timestamp  = datetime.utcnow(),
        session_id = current_user.session_id
    )
    User.query.filter_by(id=user_id).delete()
    db.session.commit()
    # AuditLog stored in append-only table — cannot be deleted by app code
    # Replicated to immutable S3 bucket for forensic use
ℹ️
What "immutable" means for logs: Logs must be written by the application to a destination where the application cannot delete or modify them — an append-only database table, AWS CloudWatch Logs with resource policies, or an S3 bucket with Object Lock. If an attacker (or malicious admin) can delete the logs after the fact, you have no non-repudiation.
I
Information Disclosure — "I can see things I shouldn't"
Violates: Confidentiality. Sensitive data is exposed to unauthorized parties — through error messages, APIs returning excess data, unencrypted storage, or side-channel leaks.

Information disclosure sources

SourceExampleWhat leaksFix
Verbose error messagesStack trace returned to user on 500 errorFile paths, library versions, SQL queries, internal hostnamesGeneric error messages in prod; log details server-side only
API over-fetchingGET /user returns password_hash, ssn, internal_notes in JSONPassword hashes, PII, internal stateResponse schemas: explicit field allowlist, never return * from ORM

# INFORMATION DISCLOSURE: API returning too much data
class User(db.Model):
    id            = db.Column(db.Integer)
    email         = db.Column(db.String)
    password_hash = db.Column(db.String)    # bcrypt hash
    ssn           = db.Column(db.String)    # Social Security Number
    internal_notes= db.Column(db.Text)      # admin-only notes

@app.route('/api/user/<int:uid>')
def get_user_bad(uid):
    user = User.query.get(uid)
    return jsonify(user.__dict__)   # ← returns ALL fields including password_hash, ssn!

# FIXED: explicit response schema — only return what clients need
from marshmallow import Schema, fields

class UserPublicSchema(Schema):
    id    = fields.Int()
    email = fields.Email()            # ← only these two fields
    # password_hash, ssn, internal_notes: NOT included → never in response

@app.route('/api/user/<int:uid>')
def get_user_fixed(uid):
    user = User.query.get_or_404(uid)
    return jsonify(UserPublicSchema().dump(user))   # ← schema enforces allowlist
D
Denial of Service — "I make the system unavailable"
Violates: Availability. Attacker prevents legitimate users from accessing the system by exhausting resources — CPU, memory, connections, bandwidth, or by crashing the process.

# DoS: No rate limiting on bcrypt login — CPU exhaustion attack
# bcrypt takes ~250ms per check. 100 concurrent requests = 25s CPU time.

@app.route('/login', methods=['POST'])
def login_bad():
    user = User.query.filter_by(email=request.json['email']).first()
    if user and bcrypt.check(request.json['pwd'], user.hash):  # no rate limit!
        return 'ok'

# FIXED: rate limit BEFORE bcrypt, plus account lockout
from flask_limiter import Limiter

limiter = Limiter(app, key_func=get_remote_address)

@app.route('/login', methods=['POST'])
@limiter.limit("5 per minute")           # ← rate limit runs BEFORE bcrypt
@limiter.limit("20 per hour")             # ← dual limits: per-minute AND per-hour
def login_fixed():
    user = User.query.filter_by(email=request.json['email']).first()
    if user and user.locked_until > datetime.utcnow():  # ← check lockout
        abort(429, "Account temporarily locked")
    if user and bcrypt.check(request.json['pwd'], user.hash):
        return 'ok'
E
Elevation of Privilege — "I have more power than I should"
Violates: Authorization. The attacker gains capabilities beyond what they were granted — regular user becomes admin, read-only becomes read-write, or unauthenticated becomes authenticated.

TypeDefinitionAttack exampleFix

# ELEVATION OF PRIVILEGE: JWT role claim trusted from token
# Attacker edits JWT payload to set role=admin

@app.route('/admin/export-users')
def export_users_bad():
    token = request.headers.get('Authorization').split()[1]
    payload = jwt.decode(token, SECRET, algorithms=['HS256'])
    # VULNERABLE: role comes from JWT payload — attacker modifies it
    if payload['role'] == 'admin':               # ← trusting user-supplied claim
        return jsonify(User.query.all())

# FIXED: role looked up from DB using token's user_id
@app.route('/admin/export-users')
def export_users_fixed():
    payload = jwt.decode(token, SECRET, algorithms=['HS256'])
    user = User.query.get(payload['sub'])    # ← fetch fresh from DB
    if user.role != 'admin':                    # ← role from DB, not token
        abort(403)                               # ← attacker's token change is ignored
    return jsonify(User.query.all())

🔴 Advanced — PASTA Methodology
PASTA — Process for Attack Simulation and Threat Analysis
PASTA is a 7-stage, risk-centric threat modeling methodology created by Tony UcedaVélez and Marco Morana. Unlike STRIDE (which is threat-centric), PASTA is attacker-centric — it simulates actual attack scenarios end-to-end and ties threats to business impact. Used by mature security teams at large organizations.
ℹ️
STRIDE vs PASTA: STRIDE asks "what category of threat is this?" — PASTA asks "would a real attacker bother, and what business damage would they cause?" STRIDE is fast and good for developer-level threat modeling. PASTA is deeper, takes longer, and is used for enterprise risk management decisions like "should we build this feature at all?" and "what is the residual risk after controls?"
1

Stage 1 — Define Business Objectives

Before analyzing any technical threat, understand what the business cares about. What would cause the most business damage? Regulatory fine? Customer churn? Brand damage? IP theft? This stage forces you to connect security to business outcomes — which is essential when presenting findings to executives.

Output: Business Impact Analysis (BIA) — ranked list of business risks (revenue, reputation, compliance, operations)
2

Stage 2 — Define the Technical Scope

Document the technical infrastructure: application components, third-party dependencies, network topology, cloud services, and data flows. This is equivalent to the DFD in STRIDE but with more technical depth — including OS versions, framework versions, and existing security controls.

Output: Technical Architecture Document — full system inventory with trust levels, data classifications, and existing control inventory
3

Stage 3 — Application Decomposition

Decompose the application into functional components: identify all use cases, actors (users, admins, services), trust levels, entry points (APIs, web forms, file uploads), and exit points (responses, logs, notifications). Every entry and exit point is a potential attack surface.

Output: Threat Surface Map — every entry point, actor, trust level, and data flow. This is the object of your threat analysis.
4

Stage 4 — Threat Analysis

Identify threat agents (who attacks you?) and their motives, capabilities, and likely attack vectors. Not all threats are equal — a nation-state APT has different capabilities than an opportunistic script kiddie. Consult threat intelligence: MITRE ATT&CK, historical breach data for your industry, bug bounty reports.

Output: Threat Agent Profiles — for each realistic attacker type: motivation, capability level, likely techniques, and probability of targeting your system
5

Stage 5 — Vulnerability and Weakness Analysis

Map known weaknesses (from SAST, SCA, pentest findings, CVE databases) to the threat surface identified in Stage 3. This is where you connect attacker capabilities (Stage 4) to actual exploitable weaknesses in your system. Use CWE (Common Weakness Enumeration) as the classification vocabulary.

Output: Vulnerability Risk Register — each vulnerability mapped to: threat agent, affected component, CWE ID, CVSS score, exploitability
6

Stage 6 — Attack Modeling (Attack Trees)

Build attack trees to model how a real attacker would chain vulnerabilities to achieve their goal. An attack tree starts with the attacker's goal (root) and branches into all the ways they could achieve it, with AND/OR logic. This reveals attack paths that no individual vulnerability scan would find.

Output: Attack Trees — visual maps of attack chains from attacker's perspective, with probability and impact at each node
7

Stage 7 — Risk and Impact Analysis

Quantify the residual risk after controls. Use the risk matrix: Likelihood × Impact = Risk Score. Present findings to business stakeholders with business language: "This attack path has a 40% probability of occurring within 12 months and would cost an estimated $2.3M in breach costs, regulatory fines, and customer loss." This is what gets budget approved for security controls.

Output: Residual Risk Report — risk matrix, prioritized remediation roadmap, cost-benefit analysis of proposed controls, executive summary
🔴 Advanced — Attack Trees
Attack trees — modeling attacker logic
An attack tree represents the attacker's goal as a root node and all the ways to achieve it as child nodes. AND nodes mean "attacker needs all children to succeed." OR nodes mean "any one child is enough." They reveal multi-step attack chains no single tool finds.
Attack Tree: Goal = Exfiltrate All User Data from Production DB
GOAL: Exfiltrate all user data from production DB
OR — any of these paths succeed
Path A: Direct DB access
Path B: App-layer SQLi
Path C: Compromise admin account
Path D: Cloud misconfiguration
Path B expanded — AND (attacker needs all of these)
B1: Find SQLi endpoint (recon)
B2: Craft UNION SELECT payload
B3: Exfiltrate via HTTP response
Controls added — Path B becomes infeasible
B1 blocked: Parameterized queries — no SQLi possible
B2 blocked: WAF blocks UNION SELECT patterns
B3 blocked: Response schema allowlist — DB data not in response
Path A expanded — AND (attacker needs all of these)
A1: DB port reachable from internet
A2: Brute-force DB credentials OR steal them
A3: Execute SELECT * FROM users
Controls — Path A partially blocked
A1 blocked: DB in private subnet, no internet route
A2 still possible if credentials leaked
A3 partially blocked: read-only user, row-level security
💡
Attack trees reveal what individual tools miss: No SAST tool, no DAST tool, and no SCA tool would detect "DB port open to internet + weak DB password = data exfiltration." But an attack tree that models Path A shows immediately that A1 (DB port open) and A2 (weak creds) together enable the attack — even if each individually might be rated as just "Medium" severity.

Time allocation for a new feature

Step 1: Draw the DFD together (30 min)
  → Everyone in the room agrees on what's being built before going further
  → Disagreements here are features, not bugs — document them

Step 2: STRIDE per element (45–60 min)
  → For each process, data store, and data flow:
  → "What S/T/R/I/D/E threats apply here?"
  → Write threats on sticky notes (physical or Miro)

Step 3: DREAD score and prioritize (20 min)
  → Quick group scoring for each threat
  → Controversial scores → discuss. Consensus, not dictating.

Step 4: Assign mitigations and owners (20 min)
  → For each CRITICAL/HIGH threat: who owns the fix? By when?
  → Create Jira/Linear tickets in the session

Step 5: Document and share (30 min after session)
  → AppSec engineer writes up the threat model
  → Stored with the feature spec → reviewed when system changes

Knowledge Check
Threat modeling interview questions
These exact questions appear in AppSec engineer interviews at top companies
Q1. A developer sends an HTTP request to a third-party payment API. The API is not under your control. What STRIDE threats apply to this data flow, and what controls would you require?
Only Denial of Service — the third party could go down and disrupt your service
Only Spoofing and Tampering — because it's an external party
Spoofing (is the API who it claims?), Tampering (can response be modified?), Information Disclosure (does the request leak card data if not encrypted?), Denial of Service (API unavailability). Controls: TLS + cert validation, HMAC response signing, timeout + circuit breaker, response schema validation
No STRIDE threats — the third party is trusted and out of scope
Every data flow has multiple STRIDE threats. External APIs are NOT trusted — they are external entities. Controls: Spoofing → certificate pinning or at minimum verify the TLS certificate. Tampering → validate response schema (Marshmallow), use HMAC webhook signing if available. Information Disclosure → ensure TLS is enforced (no HTTP fallback), don't log full API responses if they contain card data. DoS → set request timeout (e.g., 5s), implement circuit breaker pattern (if API is down, fail gracefully, don't cascade).
Q2. What is the difference between Vertical and Horizontal Privilege Escalation? Give a code-level example of each.
Vertical = gaining more bandwidth. Horizontal = gaining more features
Vertical = lower privilege user accesses higher privilege function (user → admin). Horizontal = same privilege user accesses another user's resource (User A → User B's data). Both are Elevation of Privilege in STRIDE.
Vertical = OS-level escalation. Horizontal = application-level escalation. They require different STRIDE categories.
Vertical escalation is in STRIDE-E. Horizontal escalation is in STRIDE-I (Information Disclosure).
Both are Elevation of Privilege (E in STRIDE). Vertical: GET /admin/users — regular user accesses admin function (no role check). Fix: if current_user.role != 'admin': abort(403). Horizontal: GET /invoice/1042 — User A reads User B's invoice by changing the ID. Fix: if invoice.owner_id != current_user.id: abort(403). Beginners often categorize horizontal escalation as Information Disclosure — but the root cause is authorization failure (E), and the information leak is the consequence, not the category.
Q3. What is the key difference between STRIDE and PASTA, and when would you use each?
STRIDE is for web apps, PASTA is for mobile apps
STRIDE is automated, PASTA requires a manual session
STRIDE is threat-centric (categorizes threat types, fast, good for developer sessions). PASTA is attacker-centric and risk-centric (simulates real attack scenarios, ties to business impact, 7 stages, used for enterprise risk decisions). Use STRIDE in sprint planning for new features. Use PASTA for annual risk assessments and new product launches.
They are equivalent — PASTA is just a newer version of STRIDE
STRIDE: fast, prescriptive, developer-friendly. 1–2 hour session. Identifies threat categories per DFD element. Output: list of threats with mitigations. Best for: agile teams, new features, developer training. PASTA: thorough, business-aligned, attacker-simulating. 2–5 day engagement for complex systems. Output: risk register, attack trees, residual risk report, executive briefing. Best for: new product launches, compliance requirements, executive risk reporting, high-value systems. Many teams use STRIDE at the sprint level and PASTA quarterly for their most critical systems.
